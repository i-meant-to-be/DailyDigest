# 채점 기준

## 대원칙 — 후하게 주지 않는다

이 사용자의 상황은 **서류는 통과하는데 면접에서 떨어지는 것**이다. 경험 목록은 충분하고, 그 경험을 지탱하는 기본기를 말로 꺼내지 못한다는 뜻이다.

여기서 진짜 문제는 "내 답이 통과 수준인지 스스로 판단이 안 되는 것"이다. **관대한 채점은 그 판단 착오를 그대로 재생산한다.** 잘했다고 말해 주는 것이 도움이 되지 않는 드문 경우다.

그러니 **면접관 기준으로 채점하라.** 좋게 봐주지 마라. 4점은 실제 면접에서 통과할 답에만 준다.

동시에, 채점은 벌이 아니다. 목적은 점수가 아니라 **"면접에서는 어떻게 말했어야 하는가"를 알려 주는 것**이다. 냉정하게 매기되 설명은 충실하게 하라.

## API 이름과 개념 이해를 구분한다

문제에는 실제 면접에서 쓰이는 함수·클래스·어노테이션·상수 이름이 나올 수 있다. 그러나 채점의 대상은 그 식별자를 답변에서 다시 말하거나 정확히 암기했는지가 아니라, **질문에 나온 대상의 역할·동작 조건·처리 과정·선택 근거를 이해했는지**다.

- 답변에서 구체적인 API 이름을 생략해도 설명의 대응 관계가 분명하고 핵심 원리가 맞으면 감점하지 않는다.
- API 이름을 약간 다르게 기억하거나 철자를 틀려도 어떤 역할을 하는지 정확히 설명했다면 점수와 `gaps`에 반영하지 않는다. 필요한 경우 채점 설명에서 보충 정보로만 바로잡는다.
- 질문에 여러 API가 제시됐다면 이름을 반복하지 않고 "첫 번째", "두 번째"처럼 답해도 된다. 다만 어느 대상이 어떤 역할을 하는지는 구분되어야 한다.
- API 이름을 틀린 것과 역할을 틀린 것을 구분한다. 이름은 부정확해도 역할이 맞으면 감점하지 않지만, 다른 API의 동작을 연결하거나 두 대상의 책임을 뒤바꾸면 개념 오류로 감점한다.
- 정확해야 하는 용어는 인가 코드와 PKCE, 프로세스와 스레드, 재할당과 객체 내부 변경처럼 개념 경계를 결정하는 전공 용어다. 라이브러리 식별자의 철자와 이름 재현은 여기에 포함하지 않는다.

예를 들어 `@Binds`와 `@Provides`의 차이를 묻는 질문에 "첫 번째는 인터페이스와 생성 가능한 구현체의 대응 관계를 선언하고, 두 번째는 객체를 만드는 로직을 직접 제공한다"고 답했다면 두 이름을 반복하지 않아도 정답이다. 반대로 두 역할을 바꿔 설명했다면 이름 암기가 아니라 동작 원리를 잘못 이해한 것이므로 감점한다.

## 0~4점 루브릭

| 점수 | 기준 |
| --- | --- |
| 4 | 핵심 개념과 관계가 정확하고, 근거나 트레이드오프까지 있다. 그대로 면접에서 말해도 통과할 답 |
| 3 | 핵심은 맞지만 개념 구분이 흐리거나 설명 구조가 없다. 면접관이 한 번 더 캐물으면 흔들릴 답 |
| 2 | 절반쯤 맞지만 중요한 것이 빠졌다. 또는 맞는 말과 틀린 말이 섞여 있다 |
| 1 | 방향만 잡았고 내용 대부분이 틀렸다 |
| 0 | 백지이거나 개념을 완전히 잘못 알고 있다 |
| `null` | **미응답.** 답변란이 비어 있다. 0점이 아니다 |

### 난이도별로 4점의 기준이 다르다

- **기초** — 정확한 정의와 핵심 개념의 올바른 구분. 여기서는 "대충 맞다"가 통하지 않는다. 기초 문항의 3점은 실무 문항의 3점보다 무겁게 봐야 한다
- **실무** — 정의에 더해 "언제 쓰고 언제 안 쓰는가", 실제로 겪는 문제까지
- **심화** — 트레이드오프, 내부 동작, 대안과의 비교까지. 여기서 3점은 자연스럽다

### 3점 밴드를 주목하라

이 사용자에게 가장 흔한 점수는 3점일 것이다. 그리고 3점이 가장 위험하다 — 본인은 맞혔다고 느끼는데 면접에서는 떨어지는 구간이기 때문이다.

3점을 줬다면 설명에서 **"무엇을 아는가"가 아니라 "어떻게 말했어야 하는가"**를 다뤄라. 모범 답변을 한 문단으로 보여 주는 것이 가장 효과적이다.

### 자주 나올 감점 사유

- 코루틴을 스레드라고 부르는 것처럼 **층위가 다른 개념을 섞어 쓰는 것**
- 인가 코드를 PKCE라고 부르는 것처럼 **서로 다른 개념이나 역할을 바꿔 말하는 것**
- "성능이 나쁘다" 같은 **근거 없는 단정**
- 써 본 적은 있는데 **왜 그렇게 하는지 설명하지 못하는 것**. 이 사용자에게 특히 자주 나올 유형이다
- 나열은 하는데 **비교나 선택 기준이 없는 것**

## `gaps` 작성

`gaps`는 다음 출제 때 같은 지점을 겨냥하는 근거이자, 사용자가 자기 약점의 성격을 파악하는 자료다. 한 문항에 1~3개, 짧게 쓴다.

구체적인 API 이름을 말하지 않았거나 철자를 틀린 사실만으로 `gaps`를 만들지 않는다. 이름은 기억하지 못했어도 역할과 흐름을 설명했다면 약점이 아니다. API가 담당하는 조건·과정·결과를 잘못 이해했을 때만 그 개념 오류를 기록한다.

**두 유형을 구분해서 적어라.**

- 몰라서 틀림 → `"TLS 핸드셰이크에서 인증서 검증 단계를 모름"`
- 알지만 설명하지 못함 → `"동작은 정확히 아는데 '멱등성'이라는 용어를 쓰지 못함"`

이 구분이 중요한 이유는 처방이 다르기 때문이다. 앞은 공부가, 뒤는 말하기 연습이 필요하다.

## result.md 형식

세션 디렉터리에 쓴다. 목적은 점수 통보가 아니라 **왜 틀렸는지 설명하는 것**이다.

```markdown
# 채점 결과 — 2026-09-02 14:30

6문항 중 5문항 응답 · 평균 2.4점

| # | 문항 | 점수 | 상태 |
| --- | --- | ---: | --- |
| 1 | [NET-002] TCP 3단 악수 | 2 | 오답 → 불안정 |
| 2 | [CMP-001] Recomposition과 remember | 4 | 미학습 → 불안정 |
| 3 | [AND-022] Activity 생명주기 | — | 미응답 |

---

## 1. [NET-002] TCP 3단 악수를 설명해 주세요 — 2점

**맞은 부분**
SYN과 SYN+ACK의 순서, 그리고 각 신호의 의미를 정확히 짚었습니다.

**빠진 부분**
마지막 세 번째 단계, A가 B의 SYN에 ACK를 보내는 과정이 없습니다. 이게 빠지면
"3단 악수"라는 이름 자체가 성립하지 않아서, 면접에서는 바로 되물어 옵니다.

**틀린 부분**
"B의 ACK를 받으면 연결이 수립된다"고 하셨는데, 그 시점에 연결이 선 것은 A쪽뿐입니다.
B는 아직 자기 SYN에 대한 응답을 못 받은 상태입니다.

**면접에서는 이렇게**
"양방향 통신이라 각 방향마다 '보내겠다'와 '받을 준비됐다'가 필요한데, B의 응답에서
이 둘이 한 번에 묶여서 총 3번이 됩니다." — 단계 나열보다 왜 3번인지를 먼저 말하면
그 다음 질문(왜 4단계가 아닌가, 왜 종료는 4단계인가)까지 자연스럽게 이어집니다.

**상태** 오답 → 불안정 (2점)
```

`### 내 답변`이 비어 있던 문항은 표에만 "미응답"으로 적고 개별 절을 쓰지 않는다.

마지막에 이번 세션에서 드러난 흐름을 두세 문장으로 정리한다. 과목이 문제인지, 특정 난이도가 문제인지, 아니면 아는데 표현이 문제인지 — 점수보다 이쪽이 사용자에게 더 쓸모 있다.

## 상태 전이는 네가 계산하지 않는다

점수를 `update` 명령에 넘기면 스크립트가 전이를 계산한다. 규칙은 알아 두되 직접 적용하지 마라.

| 점수 | 결과 |
| --- | --- |
| 0~1 | 오답 |
| 2~3 | 불안정 |
| 4 | 불안정. **연속 두 번째 4점부터 숙지** |

한 번 맞힌 것이 운인지 실력인지 구분하려고 두 번을 요구한다. 그래서 오답에서 숙지로 한 번에 올라가는 일은 없다.
