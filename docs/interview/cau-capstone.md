## 1. Proto DataStore 컴포지트 패턴 — 이력서 핵심 항목

### 1-1. 버린 대안이 코드에 그대로 남아 있다

**저장소에서 확인한 것**: `memo.proto`에 주석 처리된 안이 남아 있다.

```proto
/*
message ProtoMemoItemLeaf { int64 id = 1; string content = 2; }
message ProtoMemoItemGroup { int64 id = 1; string content = 2; repeated ProtoMemoItemLeaf items = 3; }
 */

message ProtoMemoItem {
  int64 id = 1; string content = 2; bool isLeaf = 3; repeated ProtoMemoItem items = 4;
}
```

Leaf와 Group을 나눈 안을 버리고 **자기 참조 메시지 하나에 `isLeaf` 플래그**를 붙이는 쪽으로
갔다. 이건 (b) 축의 완벽한 재료다 — 면접에서 그대로 쓸 수 있는 몇 안 되는 흔적이다.

**묻고 싶은 것**: 왜 바꿨나? 나눈 안의 문제가 **proto3에 다형성이 없어서**였나
(`oneof`로 감싸야 하고 그러면 중첩이 지저분해진다), 아니면 Kotlin 매핑이 번거로워서였나?

그리고 합친 안의 대가 — `isLeaf`가 `false`인데 `items`가 비어 있는, **말이 안 되는 상태가
표현 가능해진 것** — 은 인지했나? 그건 어떻게 다뤘나? (컴포지트 패턴의 고전적 트레이드오프라
면접관이 아는 주제일 가능성이 높다.)

### 답

첫 번째 이유는 컴포지트 패턴의 핵심은 하나의 자료형으로 그룹과 리프를 모두 표현하는 것이라고 생각했기 때문이었다. 내가 기억하는 게 정확한지 모르겠지만, Kotlin에서는 인터페이스 만들고 구현체로 리프와 그룹을 나누면 하나의 인터페이스로 2개 다 표현이 가능하지만, Protobuf 문법에서는 그게 안 됐던 걸로 기억한다.

두 번째 이유는 서비스 특성상 가능한 케이스가 리프, 그룹-리프 말고는 없었기 때문이다. 즉, 아무리 깊어봐야 트리 깊이가 2를 초과할 수 없다. 그럴 거라면 굳이 복잡한 구현보다는 직관적인 구현이 훨씬 이득이라고 봤다. 나는 복잡성은 진짜로 복잡성이 필요한 순간에 추가해야 한다고 생각하는 극단적 단순주의자이기 때문이다.

네가 물어본 대가에 관해서는 자세히 기억나지 않지만 현재 코드 상으로는 그룹을 감싸는 UI 안에서 `list.forEach`를 사용하여 세부 메모를 렌더링하고 있어, 아마 리스트에 아이템이 없다면 그냥 하위 UI가 아무것도 렌더링되지 않는 선에서 끝날 것 같다. 그러나 지금 보니 서비스 특성상 그룹 내 아무 메모도 없으면 메모 그룹 자체를 지우는 게 맞기 때문에, 아예 그룹을 감싸는 UI조차 렌더링하지 않고 해당 데이터를 지워버리는 쪽이 낫지 않았을까 싶다.

### 1-2. 도메인 모델은 어떻게 뒀나?

**묻고 싶은 것**: proto 생성 타입을 그대로 UI까지 올렸나, 아니면 Kotlin `sealed interface`
(Leaf / Group)로 변환해서 썼나? 후자라면 **저장소에서는 플래그로 합치고 도메인에서는
sealed로 나눈** 셈인데, 그게 의도한 설계였나? 그렇다면 그 이유가 좋은 답이 된다.

### 답

그대로 썼다.

그 당시에는 Android의 클린 아키텍처에 대한 이해가 부족했기에, Proto가 관리하는 데이터를 그대로 사용하는 편이 내가 데이터 조작을 하거나 별도 도메인 모델을 만들어 사용하면서 생길 수 있는 소스-도메인 간 불일치를 해결할 수 있는 방법이라고 생각했다.

그러나 현 시점에서 저걸 구현한다면 도메인 모델 분리할 것 같다. 당연한 문제지만 도메인 모델 분리하여 인터페이스를 단일화하지 않아 소스를 그대로 데이터로 사용하게 되면, 소스가 바뀌었을 때 관련 코드를 전부 고쳐줘야 하기 때문이다. 무엇보다도 Proto DataStore는 Protobuf와 Android DataStore에 의존하는 Android Native 라이브러리다. 도메인 모델은 도메인 지식이 바뀔 때에만 변경되어야 하는데 소스를 그대로 데이터로 사용하면 도메인에 의한 변경이 아니라 제3자에 의한 변경에 영향을 받게 된다. 결합도 상승이다. 따라서 도메인 모델과 소스 분리하는 게 좋을 것 같다는 게 지금의 내 판단.

### 1-3. Proto DataStore를 고른 기준

**묻고 싶은 것**: SharedPreferences / Preferences DataStore / Room 중 무엇을 검토했나?

"중첩 구조를 저장해야 해서 Room의 관계 테이블 대신 protobuf를 골랐다"는 흐름이면 좋은
답이 되는데, 실제로 그런 비교를 했나? Room으로 트리를 저장하려면 self-referencing FK와
재귀 조회가 필요한데 그 안을 검토했나?

### 답

예상되는 데이터 규모가 DB를 써야 할 만큼 크지 않았고, 서비스 특성상 메모가 생성되었다가 전부 클리어되는 플로우가 반복되기 때문에 Room까지 넣는 건 오버엔지니어링이라고 생각했다. 그리고 Shared Preferences는 그 시점 기준 DataStore에 비해 레거시인 것으로 인지해서 미채택했고, Preferences DataStore는 내가 다룰 데이터가 컴포지트 패턴 데이터였기 때문에 평문 문자열 저장보단 Proto DataStore가 더 적합하다고 봤다.

### 1-4. protobuf `lite`를 쓴 이유

**저장소에서 확인한 것**: `option("lite")`로 java lite 런타임을 쓰고 `protobuf-kotlin-lite`를
의존한다.

**묻고 싶은 것**: 이게 의도적 선택이었나 (안드로이드에서 메서드 수와 APK 크기 때문에 lite가
권장된다), 아니면 공식 문서 예제를 따라간 결과인가? lite가 못 하는 것(리플렉션 기반 기능,
`toString()`의 텍스트 포맷 등)을 아는가?

### 답

공식 문서 예제를 따라간 결과였다.

### 1-5. 전체 목록을 통째로 쓰는 구조의 한계

**저장소에서 확인한 것**: `ProtoMemoItemList` 하나를 `memo.pb` 파일 하나에 저장한다.
DataStore는 쓰기마다 **파일 전체를 다시 쓴다.**

**묻고 싶은 것**: 항목이 수백 개로 늘면 체크박스 하나 누를 때마다 전체 직렬화가 일어난다.
이걸 인지했나? 실제로 느려진 적이 있나? 지금이면 어떻게 하겠나?

### 답

인지한 적 없다. 실제로 느려진 적도 없다. 서비스에서 말하는 메모가 장 보기 메모라서 많아 봐야 30개를 넘을 수 없을 거라고 판단했다. 그리고 위에서 말했듯이 특정 시점에서 메모가 전부 비워진다. 그래서 쓰기 부하가 덜할 것이라고 생각했다.

### 1-6. `CorruptionException` — 복구 전략이 있나?

**저장소에서 확인한 것**: `MemoItemListSerializer`가 `InvalidProtocolBufferException`을
`CorruptionException`으로 바꿔 던진다. `dataStore(...)` 호출에 `corruptionHandler`는 없다.

**묻고 싶은 것**: 이 상태에서 파일이 실제로 깨지면 앱은 어떻게 되나? 그때 무슨 일이
벌어지는지 설명할 수 있나? 이건 면접관이 좋아하는 후속 질문이다 — 예외를 변환하는 코드를
써 놓고 그 예외가 던져진 뒤를 설명 못 하면 "예제를 따라 썼구나"로 읽힌다.

### 답

아마 크래시로 이어질 것이다. 당시 깊지 않았던 기술적 깊이의 잔여물이다.

## 2. Naver Map — XML 뷰의 Compose 리팩터링 (이력서 핵심 항목)

### 2-1. 리팩터링 전에는 정확히 무엇이었나?

**저장소에서 확인한 것**: 현재 `NaverMap.kt`(145줄)는 `AndroidView`로 `MapView`를 감싸고
`LifecycleEventObserver`로 `onCreate`~`onDestroy`를 수동 중계한다.

**묻고 싶은 것**: 이력서에 "XML 뷰를 Compose로 리팩터링"이라 적었는데 **전에는 무엇이었나**
— Fragment + XML 레이아웃이었나, `MapFragment`를 띄웠나, `AndroidViewBinding`이었나?
그리고 **왜 바꿨나**? 화면 전환이나 상태 전달에서 구체적으로 무엇이 불편했나?

면접관은 "before를 말해 보세요"부터 묻는다. before가 흐릿하면 after의 개선도 흐릿해진다.

### 답

전에는 다른 제3자가 네이버 지도 XML 뷰를 Compose로 포팅한 외부 라이브러리였다. 즉, 해당 라이브러리가 네이버 SDK를 내부 의존성으로 가지는 형태였다. 그런데 해당 라이브러리 업데이트가 느려서 최신 API 스펙을 반영하지 못하고 있었다. 그리고 문서도 너무 부실해서 뭐가 문제인지조차 원인을 찾기도 어려웠다.

그래서 해당 제3자 라이브러리 의존성을 제거하고 그냥 네이버 지도 SDK를 직접 의존성에 추가했다. 그리고 프로젝트 스펙상 필요했던 부분만 추가적으로 구현했다: 대표적으로 핀과 경로 선을 그리는 것이었다.

### 2-2. `MapFragment`를 안 쓰고 `MapView`를 직접 감싼 이유

**묻고 싶은 것**: Naver Maps SDK는 생명주기를 알아서 처리해 주는 `MapFragment`도 제공한다.
그쪽을 썼다면 이 중계 코드가 통째로 필요 없다. `MapView`를 고른 이유가 있나
(Compose 화면 안에 Fragment를 넣기 싫어서? Fragment 백스택과 섞이는 게 싫어서?),
아니면 `MapView` 예제를 먼저 봐서인가?

### 답

내가 기억하기로는 특정 생명주기 함수에 들어가야 하는 작업들이 있었을 것이다. 그래서 `MapView`를 사용했다.

### 2-3. 생명주기 콜백을 `launch`로 감싼 이유

**저장소에서 확인한 것**: `LifecycleEventObserver` 안에서 이렇게 부른다.

```kotlin
LifecycleEventObserver { _, event ->
    coroutineScope.launch {
        when (event) {
            Lifecycle.Event.ON_CREATE -> mapView.onCreate(Bundle())
            ...
        }
    }
}
```

즉 생명주기 콜백 처리가 **다음 프레임 이후로 미뤄진다.**

**묻고 싶은 것**: 왜 `launch`로 감쌌나? 지도 초기화가 무거워서 ANR이 났나, 아니면
컴포지션 중 호출 문제 때문이었나, 아니면 특별한 이유 없이 그렇게 됐나? 이 때문에
`onDestroy`가 늦게 불려 문제가 된 적은 없나?

**추가로**: `mapView.onCreate(Bundle())`에 항상 **새 빈 Bundle**을 넘긴다. 원래는
저장된 인스턴스 상태를 넘기는 자리인데, 이 때문에 지도 카메라 위치가 화면 회전 후 복원되지
않았을 것으로 보인다. 그런 증상을 겪었나?

### 답

이 부분 기억이 잘 나지 않는다. 네가 언급한 문제는 전부 겪은 적은 없으나 애초에 오류 원인이 될 수 있다는 점에서 가볍게 넘어갈 부분은 아닌 것 같다는 의견.

### 2-4. observer 해제와 `onDestroy`

**저장소에서 확인한 것**: `DisposableEffect`를 import하고 있다.

**묻고 싶은 것**: `onDispose`에서 observer를 떼고 `mapView.onDestroy()`를 부르고 있나?
`MapView`는 무거운 네이티브 리소스를 잡고 있어서 이걸 빠뜨리면 화면을 오갈 때마다 샌다.
기억나는 대로 적어 달라. (안 하고 있었다면 그게 (d) 축의 좋은 재료다.)

### 답

기억이 잘 나지 않는다.

### 2-5. 명령형 API를 선언형 상태에 맞추기

**저장소에서 확인한 것**: `pathOverlay`를 `remember`로 들고,
`LaunchedEffect(naverMap, pathPoints)` 안에서 `pathOverlay.map = null` → 좌표·색·너비 설정 →
`pathOverlay.map = naverMap` 순으로 **떼었다 다시 붙인다.**

**묻고 싶은 것**: 이 "지웠다 다시 붙이기" 패턴은 어떻게 알아냈나? 좌표만 갈아끼우면 반영이
안 되는 것을 겪어서 알게 된 건가, 문서에 있었나? 이게 **명령형 SDK를 Compose의 선언형
상태와 맞추는 일**의 핵심 사례라, 면접에서 잘 풀면 Compose 이해도를 보여주는 답이 된다.

한 가지 더 — `var pathOverlay = remember { PathOverlay() }`로 `var`로 선언돼 있는데
재할당하는 곳이 보이지 않는다. 의도가 있었나, 아니면 그냥 남은 건가?

### 답

이것도 잘 기억이 나지 않는다.

### 2-6. 리팩터링의 결과 — 나빠진 것도 함께

**묻고 싶은 것**: 무엇이 실제로 나아졌나 (코드량? 상태 전달? 재사용?).
반대로 **무엇이 나빠졌나** — 생명주기를 손으로 중계하는 코드가 새로 생긴 것은 명백한
비용이다. `MapFragment`를 썼다면 없었을 코드다.

면접에서 "좋아졌습니다"만 말하면 얕게 들린다. 남은 비용을 같이 말하는 답이 훨씬 강하다.

### 답

나아진 것은 제3자 라이브러리에 의존할 필요가 없어졌다는 것. 네이버 지도 공식 SDK 문서가 더 정확하고 잘 반영되어 있으며, 개발자가 손댈 수 있는 부분도 많아진다는 장점이 있음. 반대로 책임도 생김. 문제가 발생하면 다 개발자가 고쳐야 됨. 대신 이건 제3자 라이브러리를 쓸 경우에 오류 발생 시 아예 손도 못 쓰는 상황보다는 낫다는 점을 고려해야 한다고 봄. 생명주기도 마찬가지.

### 3-1. 경로 탐색과 API 키

**저장소에서 확인한 것**: `NaverMapRepo` / `NaverMapRepoImpl` / `NaverMapService` /
`NaverMapRoute`가 있다. 그리고 `app/google-services.json`이 저장소에 커밋돼 있다.

키는 어디에 뒀나 (`local.properties`? manifest에 하드코딩? 저장소에 커밋?).

이건 **면접에서 물으면 뼈아픈 질문**이라 미리 정리해 두는 게 낫다. 노출됐다면 "그때는
몰랐고 지금은 이렇게 한다"까지 준비하는 것이 정답이다. SEC-012와 이어진다.

### 답

클라이언트 키는 매우 매우 매우 당연하지만 `local.properties`에 두었다.

### 3-2. "장바구니 최적화" — 클라이언트 몫은 무엇이었나

**묻고 싶은 것**: 최적화 로직은 서버에 있었나? 클라이언트가 한 일은 입력 수집과 결과
표시뿐이었나?

면접관이 "최적화 어떻게 하셨어요?"라고 물으면, 서버 담당이었더라도 **문제의 성격**
(외판원 문제에 가까웠는지, 가격 비교 문제였는지, 무엇을 최소화하는 문제였는지)은 설명할
수 있어야 한다. 아는 만큼 적어 달라.

### 답

이건 서버 몫. 외판원 문제에 가까웠기에 TSP 알고리즘을 사용했다고 들었다.

## 4. 마지막 — 지금 다시 설계한다면

**묻고 싶은 것**: 가장 후회하는 결정 하나와 이유. 가장 잘했다고 보는 결정 하나와,
그것이 실제로 막아 준 문제.

이 프로젝트는 셋 중 **가장 이른 작업**이라 "그때는 몰랐는데 지금은 이렇게 한다"를 말하기
가장 좋은 소재다. 성장을 보여주는 답이 되므로 여기를 특히 채워 달라.

### 답

가장 후회하는 결정은 로직을 UI와 명확하게 분리하지 않은 것. 즉, MVI 패턴을 도입하지 않은 것.

나는 UI 코드와 로직 코드가 가능한 엄격히 분리되는 걸 좋아함. UI 코드 안에 로직이 섞여 있으면 가독성이 떨어지기 때문. 근데 이 프로젝트는 뷰 모델이 있음에도 불구하고 로직 일부가 UI 코드에 있거나 뷰 모델이 반 정도만 처리하고 UI 코드가 반 정도 처리하기도 하는 이상한 구조를 갖고 있음. 그리고 사소하게는 각 UI에 할당되는 함수(`onClick`이나 `onRefresh` 등)의 본문을 UI 코드 상단에 `handleSomething` 이런 식으로 빼 놓고 UI 코드에는 함수 호출만 하도록 적어두면 가독성이 훨씬 좋아졌을 텐데, 지금 코드는 UI 코드 내부 `onClick`에 전체 로직이 다 들어가 있으니 매우 코드가 더러워지는 문제가 발생.

가장 잘했다고 보는 결정은 네이버 지도 SDK를 직접 사용한 것.

생각보다 유지관리가 잘 되지 않는 외부 제3자 라이브러리는 매우 불편하다는 걸 알게 된 경험이었기 때문. 직접 구현하면 내가 모든 오류를 다 핸들링해야 하긴 하지만 적어도 오류를 못 고치는 일은 없음. 그런데 제3자 라이브러리는 개발자가 오류를 안 고쳐주면 내가 할 수 있는 게 없음. 그리고 이건 개인 프로젝트니까 별 생각 없이 제3자 라이브러리를 쓴 거지, 실제로 수익을 만들어내고 사업을 진행해야 하는 회사 서비스를 개발할 때 이렇게 취약한 의존성을 추가한다는 건 좀 큰 문제로 이어질 가능성도 있다고 생각함.
