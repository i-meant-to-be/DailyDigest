## 1. 멀티모듈 · 모듈 경계

### 1-1. Feature를 `api`와 `impl`로 나눈 것 — 어떤 대안을 버렸나?

**저장소에서 확인한 것**: `feature:{name}/api`는 route key와 args 계약만, `impl`은 Screen·
ViewModel·entry builder·DI를 갖는다. `impl` → 다른 `impl` 의존은 금지, 다른 Feature의 `api`만
참조한다.

**묻고 싶은 것**: `api`/`impl` 분리 없이 Feature 하나를 단일 모듈로 두고 route 계약만
`core:common`에 모으는 방법도 있었다. 실제로 그 안을 검토했나? 안 골랐다면 무엇 때문인가?
모듈 수가 화면당 2배가 되는 비용은 어떻게 정당화했나?

### 답

이 부분은 파트너 개발자가 결정한 거라 나는 배경을 잘 모른다. 근데 만약 내가 결정권자였다면 분리했을 것 같다. 애초에 현재 아키텍처 자체가 각 기능별 네비게이션 트리 구성의 책임을 각 기능 모듈에게 나누고 있기 때문이다. 앱 모듈의 네비게이션 관련 기능은 그렇게 모아진 트리를 합치는 책임만 갖는다. 이런 합의 하에서는 각 기능 모듈의 라우팅 테이블도 하나로 모으는 것보다는 각 기능 모듈에 나누는 게 낫다. 그래서 결론적으로 나는 현재 아키텍처 규칙에는 지금처럼 라우팅 테이블을 `api` 모듈로 분리한 게 맞다고 생각한다.

### 1-2. `:navigation` 모듈을 만들지 않기로 한 근거는?

**저장소에서 확인한 것**: `module-system.md`가 별도 `:navigation`이나 `:feature:navigator`
모듈 생성을 명시적으로 금지한다. 앱 루트 Navigation 3 조립은 `app`이 소유한다.

**묻고 싶은 것**: 이걸 금지 조항으로까지 못 박았다는 건 그 반대안이 실제로 논의됐다는
뜻으로 읽힌다. 어떤 안이었고 왜 접었나? `app`이 모든 Feature를 알게 되는 것은 문제가
아니었나?

### 답

위 질문 1-1의 답변으로 갈음한다. 네비게이션 트리 구성 책임을 각 기능 모듈에 나눴고, 합치는 건 앱 모듈이 하도록. 그리고 앱 모듈이 해도 기능 크기가 그렇기 크지 않아서 굳이 분리할 이유가 없다고 봤다.

### 1-3. `app` → `data` 의존 예외 — 지금도 같은 선택을 하겠나?

**저장소에서 확인한 것**: `app`은 Hilt binding과 composition root 목적으로만 `data`에
의존할 수 있다는 예외가 있다. 문서가 "Repository 구현을 직접 호출할 권한이 아니다"라고
따로 못 박았다.

**묻고 싶은 것**: 예외를 문서로 막는 것 말고 **컴파일 타임에 강제하는 방법**은 검토했나
(예: `:di` 모듈 분리, Konsist·ArchUnit 같은 아키텍처 테스트). 지금 다시 짠다면 이 예외를
없앨 수 있나?

### 답

아니. 컴파일 타임에 강제할 수 있다는 걸 몰랐다. 그리고 `:di` 모듈을 분리하지 않고 각 모듈별로 따로 만들어둔 건 그냥 파트너가 현업자라서 그 결정을 따른 것인데 뭐가 나은지 판단이 어렵다.

## 2. Convention Plugin

### 2-1. Base / Capability / Composite / Quality 4분류는 어떻게 나왔나?

**저장소에서 확인한 것**: `build-logic`에 30개 가까운 플러그인이 4분류로 있다.
`dminus14.android.feature`가 composite로 `feature:*:impl`에 적용된다.

**묻고 싶은 것**: 처음부터 4분류였나, 아니면 평평한 플러그인 목록에서 리팩터링된 건가?
`build-conventions.md`에 "같은 설정이 다른 모듈에서 반복되기 전에는 성급하게 capability
Plugin으로 추출하지 않는다"고 적었는데 — 이건 실제로 성급하게 추출해서 데인 적이 있어서
나온 문장인가?

### 답

리팩터링 된 거다. 원래는 구분 없이 한 디렉토리에 전부 있었다.

근데 내가 저거 리팩터링하면서 보니 하나의 디렉터리에 컨벤션 플러그인이 20개씩 있다 보니까 매우 어지럽더라. 그리고 파일 내용을 봐도 특정 파일은 의존성만 설정하고, 어떤 파일은 베이스 모듈 설정을 맡고, 이런 식으로 조금 역할이 구분되어 있는 게 보여 에이전트에게 작업할 때 플러그인을 별도 하위 디렉터리에 구분해달라고 했다.

"같은 설정이 다른 모듈에서 반복되기 전에는 성급하게 capability Plugin으로 추출하지 않는다"는 조항은 실제로 데인 적이 있다기보다는 내가 의도적으로 넣은 거였다. 왜냐하면 플러그인을 분리하는 작업 자체가 나름 규모가 조금 있기 때문이었다. 플러그인을 분리하면 플러그인 공통 코드를 식별하고, 아닌 애들은 또 빼고, 플러그인 파일을 build-logic에 넣고, 그걸 또 빌드 스크립트와 Gradle 설정 파일에 등록해야 한다. 가벼운 작업은 아니다. 그래서 반복을 줄임으로써 얻을 수 있는 실익이 반복을 줄이기 위해 컨벤션 플러그인을 만드는 비용보다 큰 경우에만 하도록 지침을 넣은 거였다.

### 2-2. Convention Plugin 없이 `subprojects {}` 블록으로 가는 안은?

**묻고 싶은 것**: 루트 `build.gradle.kts`에서 `subprojects`나 `allprojects`로 공통 설정을
거는 흔한 방식이 있다. 이건 왜 안 골랐나? Configuration cache나 빌드 캐시 관점에서 근거를
댈 수 있나?

### 답

## 3. 디자인 시스템 카탈로그 — 이력서 핵심 항목

### 3-1. Web/WASM 카탈로그 — 어떤 대안들과 겨뤘나?

**저장소에서 확인한 것**: `catalog`가 Compose Multiplatform Wasm 앱으로 빌드되고
(`wasmJsBrowserDistribution`), GitHub Pages 같은 정적 호스팅에 올릴 수 있는 산출물을 낸다.
`CatalogTheme`(도구 UI)과 `HilitTheme`(Story 내용)을 분리했다.

**묻고 싶은 것**: 후보로 놓고 버린 것을 알려 달라. 예를 들어 —
Compose Preview / Android 카탈로그 앱(APK를 디자이너에게 전달) / Showkase / Paparazzi 같은
스크린샷 테스트 / 디자이너를 Figma에 두고 코드 카탈로그를 아예 안 만드는 안.
각각 왜 탈락했나? Wasm 번들 크기나 초기 로딩 시간은 문제가 아니었나?

### 답

Storytale - Android에서 Storybook을 구현하려는 내 의도에 가장 근접한 시도였지만 유지보수가 멈춘 상태였으며 무엇보다 AGP랑 Kotlin 버전을 내렸어야 했어서 보안상 문제가 있을 수 있다고 판단해 각하.

Showkase - 얘 역시 1년 이상 유지보수가 멈춘 상태였고 얘는 무엇보다도 Android 기기가 없으면 Showkase 브라우저를 실행할 수 없으며 웹으로 빌드를 한다고 해도 스크린샷 기반이었다. 그래서 각하.

스크린샷 테스트와 카탈로그 앱 - Showkase에서 언급한 이유와 동일한 사유로 각하.

나는 1) 웹으로 배포 가능해 디자이너가 언제 어디서든 어떤 기기에서라도 접근 가능하도록 하고 싶었고 2) 단순 스크린샷 검토가 아니라 디자이너가 상태 값을 직접 조정하면서 개발 결과물을 테스트할 수 있기를 바랐음. 이 조건을 동시에 충족하는 건 없었기에 직접 만들기로 한 것.

### 3-2. 디자이너가 실제로 썼나?

**묻고 싶은 것**: 면접관이 반드시 묻는 질문이다. 만들어 둔 것과 쓰인 것은 다르다.
디자이너가 카탈로그를 보고 실제로 피드백을 준 사례가 있나? 없다면 왜 안 쓰였나?

### 답

썼다. 근데 디자인 시스템을 구현할 시기에만 집중적으로 사용했고, 구현한 디자인 시스템으로 실제 앱을 구현하는 단계에서는 거의 안 썼다.

이는 기본적으로 디자인 시스템 모듈이 KMP 모듈이었기 때문에 그렇다. 앱 개발을 하다 보면 아무리 UI 코드가 순수하다고 해서 어느 지점에서는 반드시 UI 코드에 Android Native 기능이 붙게 되는데, 그렇게 Android Native 기능이 붙은 페이지 전체는 KMP에서 사용할 수 없어서 카탈로그에 올릴 수 없었다. 이건 어쩔 수 없는 한계인 것 같은데 개선 방향이 있을지 항상 아쉽긴 했다.

### 3-3. `@CatalogControls`를 adapter에 붙인 것 — 원본에 붙이는 안은 왜 버렸나?

**저장소에서 확인한 것**: `designsystem`의 실제 Composable에는 annotation을 붙이지 않고,
`catalog`에 `internal` adapter Composable을 따로 만들어 거기에 붙인다.

**묻고 싶은 것**: 원본에 직접 붙였다면 어댑터를 하나하나 쓰는 수고가 없다. 그런데도
분리한 이유가 "designsystem이 catalog:annotations에 의존하게 되니까"였다면 — 그 의존이
실제로 무엇을 망가뜨리나? adapter를 손으로 유지하는 비용(원본 시그니처가 바뀌면 adapter도
같이 고쳐야 함)은 어떻게 감당했나?

### 답

일단 코드를 에이전트가 쳐 주므로 어댑터를 하나하나 쓰는게 사람 입장에선 그렇게 큰 비용이 아니라 생각했다. 그리고 가장 큰 문제는 원시형과 문자열, 열거형이 아닌 커스텀 자료형은 컨트롤 UI를 생성하기가 매우 어려웠다는 점이다. 그래서 어댑터로 기존 UI 코드에서 공개하고 싶은 매개변수만 드러내도록 한 것이다. 어댑터가 없었으면 아마 커스텀 자료형도 전부 감당 가능하게 KSP 코드를 짜야 했을 텐데 그건 매우 어려운 일이었을 거라고 생각한다.

### 3-4. KSP 코드 생성 — 리플렉션이나 수동 작성 대비 무엇을 얻었나?

**저장소에서 확인한 것**: `catalog:processor`가 kotlinpoet-ksp로 `${Adapter}Args`와
`${Adapter}Controls`를 생성한다. 지원 타입은 String, Boolean, 정수형, 실수형, Enum.

**묻고 싶은 것**: Wasm에서 Kotlin 리플렉션이 제약된다는 것이 KSP를 고른 결정적 이유였나,
아니면 다른 이유였나? "KSP는 함수 본문의 argument mapping을 검증하지 않는다"고 문서에
적었는데 — 이 구멍 때문에 실제로 사고가 난 적이 있나?

### 답

리플렉션이 뭔지 잘 모르겠다. KSP를 채택한 이유는 KSP가 컴파일 타임에 코드를 생성해주는 도구라고 들었고, 나에게 필요한 것도 어댑터 스펙에 맞는 컨트롤을 컴파일 타임에 생성해주는 것이었기 때문이다. 정확히는 컨트롤 구현 비용을 사람에게 전가하지 않고 KSP가 하도록 하고 싶었기 때문.

### 3-5. 지금 다시 만든다면?

**묻고 싶은 것**: 지원 타입에 컬렉션·nullable·sealed가 없고, parameter별 설명 annotation도
없다. 이건 의도적으로 자른 범위인가 아니면 시간 때문인가? 다시 만든다면 무엇부터 바꾸겠나?

### 답

다 의도적으로 자른 범위이다. 거기까지 고려하려면 너무 개발해야 할 게 많았기 때문이다. 다시 만든다면 parameter별 설명 annotation을 가장 우선순위에 두고 싶은데 이는 이 기능 자체가 디자이너와의 협업 흐름을 개선하는 걸 목적으로 두는 만큼 이걸 사용할 디자이너에게 기능 제약을 설명해주는 건 매우 중요한 일이기 때문이다.

## 4. AI 에이전트 기반 — 이력서 핵심 항목

### 4-1. `CONSTITUTION.md` → `ARCHITECTURE.md` → 세부 문서 → `AGENTS.md` 권위 순서

**저장소에서 확인한 것**: 문서 해석 우선순위가 명시돼 있고, 작업별 필수 읽기 표가
17행이다. `docs/` 커밋의 대부분이 본인 것이다.

**묻고 싶은 것**: 이 체계를 만들기 전에는 어땠나? 에이전트가 아키텍처를 어긴 **구체적인
사고**가 있어서 나온 대응인가, 아니면 예방 차원이었나? 전자라면 그 사례가 면접에서 가장
강한 근거가 된다.

### 답

예방 차원이었다. 프로젝트 초기 파트너와 에이전트로 개발한다는 건 합의했는데 둘이 쓰는 에이전트도 달랐고 (Claude, Codex, Cursor, Antigravity) 코드 품질 일관성에 대한 우려도 있었다. 그래서 초기부터 에이전트 규칙을 제공하기로 했고, 절대로 바뀔 일 없는 규칙과 개발 상황에 따라 바뀔 수 있는 아키텍처 문서로 계층화하여 한 쪽에는 융통성을 두는 편이 유연할 거라고 생각했다.

### 4-2. 문서로 강제하는 것의 한계 — 검증은 어떻게 했나?

**묻고 싶은 것**: 문서는 읽으라고 해도 안 읽으면 그만이다. 계약이 지켜졌는지 **자동으로**
확인하는 장치를 뒀나 (Detekt 커스텀 룰, 모듈 의존성 검사, CI 게이트, PR 리뷰 체크리스트)?
안 뒀다면 지금 다시 한다면 무엇을 넣겠나?

### 답

안 두었다. 그러나 일부 복잡한 작업에 대해서는 내가 자체적으로 진행한 바 있다. 같은 에이전트에서 다른 세션을 열거나 아예 다른 에이전트를 열어 구현 에이전트가 남긴 계획 문서와 구현 결과 문서를 바탕으로 평가를 한다던지의 방식이었다.

### 4-3. 팀원도 이 체계를 썼나?

**묻고 싶은 것**: 본인만 쓰는 규칙이었는지, 팀 표준이었는지. 팀원이 안 따랐다면 왜인가?
"문서가 너무 많아서"라는 답이 나올 법한데, 그 트레이드오프를 어떻게 봤나?

### 답

팀원도 썼다.

애초에 우리가 쓰는 에이전트들이 별다른 설정 없이도 자료를 학습할 수 있게 체계를 구현해뒀기 때문에 자동으로 자료를 먹는 구조였다. AGENTS.md와 CLAUDE.md가 모두 존재했으니까.

## 6. 마지막 — 지금 다시 설계한다면

**묻고 싶은 것**: 이 프로젝트에서 **가장 후회하는 결정 하나**와 그 이유. 그리고 반대로
**가장 잘했다고 보는 결정 하나**와, 그것이 실제로 어떤 문제를 막았는지.

면접에서 "아쉬운 점 있으세요?"는 거의 반드시 나오고, 여기서 구체적으로 답하지 못하면
그 앞의 설명 전체가 남의 이야기처럼 들린다.

### 답

가장 후회하는 결정은 도메인 문서를 도입하지 않은 것.

프로젝트에는 아키텍처 문서는 있는데 이건 기술적인 규칙과 컨벤션만 다루지 도메인 지식은 다루지 않는다. 도메인 지식은 다른 영역이다. 더 나아가 이 프로젝트는 iOS와 Android 양측에서 개발되었는데 도메인 지식은 같아도 폼 팩터에 따라 세부 구현 논리가 달라질 수 있다. 즉, 도메인 + OS에 따른 특성까지 도메인과는 별도로 고려를 했어야 한다는 뜻이다. 실제로 iOS는 이렇게 했기 때문에 이 방식이 매우 좋았다고 평가했는데 우리는 도메인 문서를 단 하나도 남기지 않아 다른 기능끼리 연결할 때 고생을 좀 했다.

가장 잘했다고 보는 결정은 카탈로그 도입한 것.

디자이너와의 협업 경험 개선도 좋은 장점이지만 의외로 더 좋았던 건 디자인 시스템 모듈이 Android Native에 의존하지 않았다는 점이었다. 순수 Kotlin 코드가 되었으므로 테스트 용이성도 늘어났으며, 이 프로젝트의 사례에서처럼 멀티 플랫폼을 목적으로 한다면 아마 UI 코드 재사용도 가능했을 것이다. 내가 재능이 더 좋았다면 가능한 페이지 단위까지 KMP 위에서 구현하였을지도 모를 일이고.
