## 1. NDK와 SEAL 채택 — 이력서 핵심 항목

### 1-1. 왜 클라이언트에서 동형암호를 돌려야 했나?

**저장소에서 확인한 것**: `app/src/main/cpp/`에 Microsoft SEAL 전체 소스가 들어 있고,
`JNIBridge`가 `initContext`, `generateKeys`, `encrypt`, `decrypt`, `addCiphertexts`,
`multiplyCiphertexts`를 노출한다. `BatchEncoder`를 쓰는 것으로 보아 BFV 스킴이다.

**묻고 싶은 것**: 익명 투표라면 서버에서 동형 연산을 하고 클라이언트는 암호화만 하는
구조도 가능하다. 왜 클라이언트에 SEAL을 통째로 넣었나? 이게 **강의 요구사항**이었나,
아니면 팀 설계 판단이었나? 면접관은 "굳이 클라이언트에?"를 반드시 묻는다.

### 답

첫 번째 이유는 1인 프로젝트였는데 서버 개발 역량이 없었기 때문. 나는 Android 개발만 해 봤기 때문에 서버를 만져본 적이 거의 없었음. 이런 상황에서는 차라리 디바이스에 연산을 몰아넣는 게 빠른 개발이 가능할 거란 판단이었음.

두 번째 이유는 Android에서 C++을 사용해보는 경험이 궁금해서. SEAL이 C++ 기반 라이브러리였는데 Android에서 사용 가능한지 배경을 조사해보니 가능하더라. 단 한 번도 안 해본 거라서 해 보고 싶었음.

세 번째 이유는 서버도 믿지 못한다는 전제를 깔고 있었기 때문. 서버가 암/복호화를 할 수 있는 역량을 가진다는 건 곧 공격자가 서버를 탈취할 경우 데이터가 뺏길 수 있음을 의미. 그래서 나는 클라이언트끼리 소통하고 서버는 바보로 두는 게 보안상 더 나은 선택일 수도 있다고 생각했음.

### 1-2. SEAL을 소스째 저장소에 넣은 것 — 어떤 대안을 버렸나?

**저장소에서 확인한 것**: `add_subdirectory(SEAL)`로 앱 빌드 때 SEAL을 함께 컴파일한다.
저장소에 SEAL 전체 트리가 커밋돼 있고, 크로스 컴파일용 `..._FOUND_EXITCODE` 캐시 변수를
손으로 박아 넣은 흔적이 있다.

**묻고 싶은 것**: 후보였을 법한 것들 — git submodule / 미리 빌드한 `.a`·`.so`를 링크 /
Prefab이나 Maven으로 배포된 바이너리 / CMake `FetchContent`. 왜 소스 vendoring을 골랐나?
빌드 시간과 저장소 크기는 얼마나 늘었나? **라이선스**(SEAL은 MIT)는 확인하고 넣었나?

### 답

네가 추측한 대안 전부 몰랐음. 미리 빌드한 결과물을 링크하는 건 고려했지만 내가 데스크톱과 랩탑에서 작업을 하기에 빌드한 파일을 옮기는 게 귀찮아서 걍 저장소를 통째로 올렸음. 라이선스는 확인 안 했고 그 이유는 학부 프로젝트에서 끝날 비공개 서비스였기 때문. 빌드 시간과 저장소 크기는 기억 안 남.

### 1-3. 크로스 컴파일 문제를 어떻게 뚫었나?

**저장소에서 확인한 것**: CMakeLists에 이런 줄들이 있다.

```cmake
set(SEAL___BUILTIN_CLZLL_FOUND_EXITCODE 0 CACHE STRING "Manually set exit code for cross-compiling")
set(SEAL__ADDCARRY_U64_FOUND_EXITCODE 0 CACHE STRING "Manually set exit code for cross-compiling")
```

**묻고 싶은 것**: 이게 무엇을 우회한 것인지 지금 설명할 수 있나? (SEAL이 `try_run`으로
호스트에서 컴파일러 내장 함수 지원 여부를 실행해 보는데, 크로스 컴파일에서는 타깃 바이너리를
호스트에서 실행할 수 없어 실패한다.) 이걸 스스로 진단했나, 이슈나 검색으로 찾았나?
**이 종류의 문제를 어떻게 디버깅했는지**가 면접에서 NDK 경험의 진위를 가른다.

### 답

스스로 진단했다. 빌드가 계속 실패하길래 뭔가 봤더니 위처럼 특정 오류 코드가 1이 되어 컴파일이 종료되는 경우가 반복적인 패턴으로 발생하더라. 그래서 관련 오류가 모두 해결될 때까지 전부 저렇게 처리했음.

### 1-4. 성능은 실제로 어땠나?

**저장소에서 확인한 것**: `ui/benchmark`, `domain/benchmark`, `JNIBenchmark.cpp`가 있고
`config.isBenchmarkEnabled` 플래그로 켜고 끈다. 벤치마크 화면이 마지막 커밋(#72)이다.

**묻고 싶은 것**: 무엇을 측정했고 **숫자가 어떻게 나왔나**. 암호화 1회 몇 ms, 암호문 크기
몇 KB, 곱셈 비용, 기기별 차이. "동형암호를 앱에 넣었다"는 문장은 숫자가 붙어야 실제로
해 본 것으로 들린다. 기억나는 수치를 최대한 적어 달라.

### 답

측정 대상은 Kotlin Coroutines vs. Java ExecutorService(via `Dispatchers`를 통해 fixed 스레드 풀을 생성하는 API) vs. C++ `thread` 간 실행 속도. 변수는 위에서 언급한 병렬 처리 환경과 스레드 수였다. 실험 환경은 코어 10개짜리 내 스마트폰.

암호문 크기는 아마 Kotlin 측 벤치마킹 코드에 하드코딩되어 있었던 걸로 기억한다.

결과는 C++ 10 스레드가 승리. 그러나 Coroutines 10 스레드도 거의 차이가 안 났다. 그래서 나는 결론을 "미세하지만 성능 우위를 원하고 디버깅 편의성 버릴 수 있으면 C++, 성능은 이 정도면 충분하고 디버깅이 편했으면 좋겠다면 Kotlin"으로 내렸다.

### 1-5. 암호 파라미터는 어떻게 골랐나?

**묻고 싶은 것**: `poly_modulus_degree`, `coeff_modulus`, `plain_modulus`를 무슨 기준으로
정했나? 보안 수준(128비트?)과 지원 가능한 곱셈 깊이(noise budget)의 트레이드오프를 설명할
수 있나? 예제 기본값을 그대로 썼다면 그것도 그대로 적어 달라 — 면접에서는 그렇게 말하는
편이 낫다.

### 답

내가 기억하기로는 최대 참여 가능 투표자 수가 10명, 제공 가능한 후보 수가 최대 3개였는데, LLM과 함께 해당 조건에 적합하고 보안성이 확보되면서도 너무 비현실적이지 않은 수치로 결정했던 걸로 기억한다.

### 1-6. 16KB 페이지 정렬

**저장소에서 확인한 것**: `arm64-v8a`와 `x86_64`에 `-Wl,-z,max-page-size=16384`를 건다.

**묻고 싶은 것**: 이게 무엇 때문인지 아는가? (Android 15부터 16KB 페이지 크기 기기가
생기면서 네이티브 라이브러리 정렬 요건이 바뀌었다.) 빌드가 깨져서 찾아 넣은 건가,
문서를 보고 선제적으로 넣은 건가?

### 답

안다. 이거 때문에 블로그 게시물도 썼다. 페이지 크기가 기존 4KB였나에서 16KB로 바뀌었다는 거.

## 2. JNI 경계 설계

### 2-1. `jbyteArray`로 암호문을 주고받는 설계 — 대안은?

**저장소에서 확인한 것**: `encrypt`가 `jlongArray`를 받아 `jbyteArray`를 반환하고,
`addCiphertexts`는 `jbyteArray` 두 개를 받아 다시 `jbyteArray`를 낸다. 즉 연산 한 번마다
암호문을 **직렬화·역직렬화**한다. 키도 바이트 배열로 매번 넘긴다.

**묻고 싶은 것**: 네이티브 핸들(포인터를 `jlong`으로 넘기고 Kotlin이 들고 있기)로 두는 안이
있다. 왕복 직렬화 비용을 알면서도 바이트 배열을 고른 이유가 있나 (직렬화된 암호문을 어차피
서버로 보내야 해서? 수명 관리가 단순해서?), 아니면 그때는 그 대안을 몰랐나? **후자여도
괜찮다** — 면접에서는 "지금이면 핸들 방식을 검토한다"가 좋은 답이 된다.

### 답

몰랐다. 네 말도 잘 이해가 안 가는게 포인터를 넘길 수 있다는 건 C++의 포인터가 가리키는 주소에 JVM이 접근할 수 있다는 말인가? 그게 된다면 그렇게 했을 거다.

### 2-2. 전역 포인터 — 위험을 인지하고 있었나?

**저장소에서 확인한 것**: `g_context`, `g_evaluator`, `g_encoder`가 `std::unique_ptr` 전역이고
`initContext()`가 이들을 세팅한다.

**묻고 싶은 것**: 여러 스레드에서 동시에 JNI 함수를 부르면 어떻게 되나? 실제로 그럴 일이
있었나? `initContext` 전에 다른 함수가 불리면? 그때 인지하고 감수한 건지, 지금 처음 보는
문제인지 솔직하게 적어 달라. PROFILE의 "C++ 스레드 동시성" 경험과 이어지는 질문이다.

### 답

여러 스레드에서 불러도 안전한 것으로 알고 있다. 검토하면서 SEAL의 내부 로직들이 멀티 스레드 환경에서 안전하게 개발되었다는 사실을 알았다. 예를 들어 `g_context`는 값만 가지고 있으며, 반대로 `g_evaluator`와 `g_encoder`는 값은 하나도 없고 로직만 가지고 있는 식으로 안전 장치를 쳐 놨다고 들었다. 다만 `g_context`가 여러 쓰기 작업이 동시에 들어올 때를 대비해 임계 영역을 포함하고 있는지에 대해서는 기억이 안 난다. 만약 없다면 아마 코드 개선이 필요하지 않을까 싶다.

그리고 전역 포인터로 선언한 것은 그렇게 선언해둔 것들이 전부 공용이기 때문이다. 서비스를 사용하면서 암호화도 복호화도 반복적으로 하게 될 텐데, 저걸 매번 호출해서 초기화를 하고 있으면 인스턴스도 여러 개 생성해야 하고 생성 시간도 걸리니까 비효율적일 가능성이 높다고 판단했다. 그래서 코드를 보면 저거처럼 전역으로 선언된 것도 있는데 지역적으로 선언된 것도 찾아볼 수 있을 거다. 그건 가벼운 것들이었다.

### 2-3. 예외와 메모리

**묻고 싶은 것**: SEAL이 C++ 예외를 던지면 JNI 경계에서 어떻게 처리했나 (`try/catch` 후
`ThrowNew`? 아니면 그냥 터지게 뒀나?). `Get<Type>ArrayElements` 계열을 쓴 뒤 `Release`를
빠뜨리면 새는데 그 점을 신경 썼나? 네이티브 크래시를 겪었다면 어떻게 잡았나
(logcat tombstone, `ndk-stack`, addr2line 등).

### 답

1인 개발에 일정이 매우 빡빡하여 처리하진 않았다.

## 3. CI/CD — 이력서 핵심 항목

### 3-1. 캐시 전략의 효과는 얼마였나?

**저장소에서 확인한 것**: `CI.yml`이 NDK 디렉터리와 `~/.android/build-cache`를 캐시하고,
AVD를 `avd-33` 키로 캐시하며, `dorny/paths-filter`로 Android 소스가 바뀐 PR에서만 계측
테스트를 돌린다. KVM도 켠다.

**묻고 싶은 것**: 캐시 도입 전후로 CI 시간이 몇 분에서 몇 분이 됐나? SEAL 컴파일이
캐시되지 않으면 매번 몇 분씩 걸렸을 텐데 그게 동기였나?

한 가지 더 — NDK 캐시 키를 `hashFiles('**/build.gradle.kts', '**/local.properties')`로
잡았는데, `local.properties`는 그 직전 스텝에서 secret으로 새로 만든다. 이 키가 의도대로
동작했나? 캐시 히트를 확인해 봤나? (동작하지 않았다면 그것도 좋은 답이다 — "다시 한다면
NDK 버전 자체를 키로 잡는다"로 이어진다.)

### 답

그렇게 크진 않았다. Gradle 동작 자체가 가장 큰 부하였기 때문이다. 에뮬레이터도 큰 부하였긴 하지만. 가장 큰 동기는 Android 계측 테스트에 걸리는 시간이 매우 컸기 때문이었다. 그래서 어떻게든 계측 테스트 비용을 줄여보고자 에뮬레이터를 캐싱하는 방향으로 갔다.

### 3-2. CD는 어디까지 했나?

**묻고 싶은 것**: 이력서에 "CI와 CD"라고 적혀 있는데 저장소에는 `CI.yml` 하나뿐이고
내용도 빌드·테스트·린트까지다. CD는 다른 곳에 있나, 아니면 `assembleDebug`까지를 CD로
표현한 건가?

**후자라면 이력서 문구를 손보는 것을 권한다.** 면접에서 "CD 파이프라인 설명해 주세요"가
들어오면 곤란해진다. 실제로 무엇을 했는지 적어 달라.

### 답

안 했다. CD는 제거해야 할 듯.

### 3-3. `secrets.LOCAL_PROPERTIES` — 이 방식의 한계를 아나?

**저장소에서 확인한 것**: CI가 `echo "${{ secrets.LOCAL_PROPERTIES }}" > local.properties`로
파일을 만들고, `build.gradle.kts`가 그 값을 `buildConfigField`로 굽는다.

**묻고 싶은 것**: `BuildConfig`에 구운 문자열은 APK를 디컴파일하면 그대로 보인다.
`API_BASE_URL` 정도면 감수할 만하지만, 그 한계를 그때 알고 있었나?
`platform/security`의 SEC-012(앱에 비밀 값 넣기)와 이어지는 답이다.

### 답

알고 있다. 그래서 경우에 따라서는 `LOCAL_PROPERTIES` 값을 암호화해두고, 그걸 빌드 스크립트에서 Kotlin이 모르는 외부 수단(C++ 등)으로 복호화하는 경우도 있다고 들었다.

## 4. 그 밖의 설계

### 4-1. 단일 모듈을 고른 이유

**묻고 싶은 것**: Hilit에서는 멀티모듈을 했는데 여기는 `:app` 하나다. 패키지는
`core/crypto`, `data`, `domain`, `ui`로 나눠 뒀다. 규모 때문인가, 시기 때문인가,
아니면 NDK 빌드 때문에 모듈을 나누기 어려웠나?

### 답

멀티 모듈 아키텍처 자체를 모르고 있었음. 알았다면 적어도 암호화 모듈 정도는 공용 모듈로 뺐을 거다.

### 4-2. `isMockEnabled`, `isDevModeEnabled` 같은 플래그

**묻고 싶은 것**: 빌드 타입(`debug`/`release`)이나 product flavor 대신 `local.properties`
플래그로 간 이유는? 이 방식의 문제(팀원마다 파일이 달라 빌드가 재현되지 않음)를 겪었나?

### 답
