## [JK-001] (실무) 중위 표기 함수(infix function)란 무엇인가요?

```kotlin
infix fun Int.add(other: Int): Int {
    return this + other
}
```

- 중위 표기 함수는 온점(.)을 찍지 않고도 함수 호출을 할 수 있게 해 주는 기능
- 다음과 같은 조건이 충족되어야 함:
  - `infix` 키워드 필수
  - 매개변수는 무조건 1개
  - 멤버 함수 또는 확장 함수여야 함

## [JK-002] (실무) `by` 키워드란 무엇인가요?

기본적으로 위임하는 것을 말함.

- 인스턴스 수준 변수와 함께 사용할 시
  - 원래 각 인스턴스 수준 변수에는 값을 저장하는 필드가 있음
  - `by` 사용 시 해당 필드를 생성하지 않고 개발자가 지정한 객체로 바로 리다이렉트
- 클래스 수준 변수와 함께 사용 시
  - 클래스 매개변수에 주어진 인터페이스를 전부 위임
  - 데코레이터 패턴의 구현 시 편리하게 쓰임 (타 언어에서는 매번 반복해야 하는 `override` 키워드 및 함수를 `by`로 생략 가능)

## [JK-003] (기초) `val`과 `var`의 차이는 무엇인가요?

- `val`
  - 변경 불가능한 참조
  - 한 번 선언하면 참조를 변경할 수 없음
  - 그러나 참조에 의해 가리켜진 값의 내부 변수는 변경될 수 있음
- `var`
  - 변경 가능한 변수
  - 언제든 재할당 가능

## [JK-004] (기초) Java와 Kotlin의 차이점은 무엇인가요?

공통점:

- JVM 위에서 동작함
- 서로 상호 운용성이 보장됨

차이점 (Kotlin이 더 생산성 높은 이유):

- Kotlin에서는 Null Safety가 지원됨
  → Java에서는 모든 **참조 타입**이 Nullable하기 때문에 (원시 타입인 `int`, `boolean` 등은 null이 될 수 없음), Kotlin에 비해 더 많은 Null check 코드가 포함되어야 해서 생산성이 떨어짐
- 비동기 처리가 더 유연하고 효율적
  → 러닝 커브가 높은 RxJava나 직접 다루기 번거로운 Java Thread 대신, 더 높은 수준에서 추상적으로 비동기를 표현할 수 있는 Coroutines 덕분에 Kotlin이 비동기 처리에 강점이 있음
- 보일러플레이트 감소
  → Java에서는 Lombok 등으로 Getter/Setter를 추가로 붙여줘야 하고 `hashCode` 등을 작성해줘야 하는 보일러플레이트가 있음. 물론 경우에 따라서는 직접 `hashCode`를 구현해줘야 하지만, 대부분의 경우 생략된다는 점에서 생산성이 더 높음

## [JK-005] (기초) `data class`란 무엇인가요?

데이터를 보유하는 것에 특화된 클래스

| 구분 | `class` | `data class` |
| --- | --- | --- |
| 목적 | 로직 및 상태 관리 | 순수한 데이터 보관 |
| 자동 생성 메소드 | 없음 (직접 구현 필요) | `equals`, `hashCode`, `toString`, `copy`, `componentN` |
| 상속 | `open` 키워드 붙은 경우 상속 가능 | 다른 클래스가 상속 불가능 |
| 생성자 | 생성자에 프로퍼티 없어도 됨 | 최소 1개 필수 |

## [JK-006] (실무) `data class` 사용 시 주의할 점은 무엇인가요?

`data class`는 데이터를 보관하고 전달하는 게 유일한 목적인 경우에만 사용. 아래 상황에서 사용 시 안티 패턴이 될 수 있음:

- 식별자 하나(ID)로만 동등성을 비교해야 할 경우. `data class`는 내부적으로 모든 인스턴스 변수를 비교하기 때문에 ID는 같은데 변수 하나만 달라도 다른 인스턴스라고 판단해 문제가 생길 수 있음. 이걸 방지하고 싶다면 `hashCode`나 `equals`를 오버라이딩해야 함
- 인스턴스 변수가 없을 경우. `data class`는 무조건 1개 이상의 인스턴스 변수를 주 생성자에서 요구하기 때문. 예를 들어 로딩 중과 같은 특정 상태를 나타내는 클래스 등이 있음
- 상속이 필요할 때. `data class`에는 `open`이나 `abstract`를 붙일 수 없기 때문에 하위 클래스가 필요하다면 일반 `class`로 선언해야 함

## [JK-007] (실무) `data class`에서 인스턴스 변수를 `var`이 아닌 `val`로 선언해야 하는 이유는 무엇인가요?

- 첫 번째는 목적과 맞지 않기 때문. `data class`는 데이터의 단순 표현을 위해 만들어졌는데, 특정 인스턴스 변수를 `var`로 지정한다는 것은 해당 데이터를 조작하겠다는 말과 같기 때문에 원래 목적을 위반하는 것
- 두 번째는 멀티 스레딩 환경에서의 신뢰성을 보장하기 위함. 보통 특정 객체를 여러 코드에서 읽으면서 사용하는 경우가 대부분인데, 만약 특정 변수가 `var`로 선언된다면 나도 모르게 그 변수 값이 바뀌는 상황이 생길 수 있음

## [JK-008] (실무) Coroutines에 대해 설명해 주세요.

- 중단 가능한 계산 단위. 컴파일러가 `suspend` 함수를 상태 기계로 변환해 구현하며, 자체 스택을 갖지 않음
- 사용자 수준 스레드(ULT)와 성질이 비슷하다고 자주 비유되지만 엄밀히는 스레드가 아님. 스케줄링을 응용 계층에서 제어한다는 점만 닮았음
- Java Thread 위에서 동작함
- 비선점형 (이미 돌아가는 작업을 억지로 멈추고 비집어 들어갈 수 없음 → 안정)
- Dispatchers에 의해 전략적인 관리 가능
- M:N 구조로서, 정확히는 M개의 Coroutines를 N개의 Java Thread에 대응시키는 모델

## [JK-009] (실무) `coroutineScope`와 `supervisorScope`의 차이는 무엇인가요?

- `coroutineScope`는 자식 중 하나가 실패하면 모든 코루틴이 즉시 실패
- `supervisorScope`는 자식 중 하나가 실패해도 나머지는 실행됨

## [JK-010] (실무) Dispatchers에 대해 설명해 주세요.

- 코루틴을 어떤 스레드 풀에서 실행할지 결정하는 것으로, 한 단어로 말하면 일종의 전략에 해당. (스레드 풀은 스레드로 이루어지고, 코루틴은 그 위에서 실행되는 작업)
- 4가지가 있는데, 주로 3가지만 활용되고 하나는 특수한 경우에만 사용:
  - `Dispatchers.IO` | 백그라운드 동작, 입출력에 쓰이며, 최대 64개 또는 CPU 코어 개수 중 큰 값까지 생성됨
  - `Dispatchers.Default` | 백그라운드 동작, 부하가 큰 연산 등 고성능 처리가 필요한 작업에 사용, 최대 CPU의 코어 개수까지 생성됨
  - `Dispatchers.Main` | 주 스레드이며 플랫폼에 따라서 사용되는 양상이 크게 다름. Android의 경우 UI 렌더링을 위해 사용되며 중단되는 경우 ANR이 발생
  - `Dispatchers.Unconfined` | 첫 중단 지점까지는 호출한 스레드에서 그대로 실행되고, 중단 후 재개될 때는 그 재개를 일으킨 스레드에서 이어짐. 실행 스레드가 예측하기 어려워지므로 초기 화면 렌더링이나 앱 실행 전 세팅처럼 매우 특수한 경우에만 신중히 사용해야 함. 호출자 스레드에서 바로 시작하는 것만 원한다면 `start = CoroutineStart.UNDISPATCHED`가 더 안전한데, 이 경우 이후 자식 코루틴은 처음 지정해 준 `Dispatchers`를 따르기 때문

## [JK-011] (심화) ULT와 KLT의 차이점은 무엇인가요?

- ULT는 사용자 수준 스레드
  - 커널은 이에 대해 전혀 알지 못함
  - 응용 위에서 동작하기 때문에 가벼움 (KLT에 할당되는 스택 용량이 보통 MB 단위인 데 반해 훨씬 적은 메모리로 동작)
  - 사용자가 원하는 대로 스케줄링 정책 변경 가능 (선입선출, 라운드 로빈 등)
  - 그러나 동시성은 충족해도 병렬성은 충족하지 못할 수 있는데, 구현을 잘못해서 코어 1개에서만 돌아가게 될 경우 ULT 수준에서는 작업을 나눈다고 해도 결국 물리적으로 동작하는 건 코어 1개이기 때문
- KLT는 커널 수준 스레드
  - 시스템 API를 통해 접근 가능
  - 병렬성은 확실히 보장 (만약 CPU가 여러 코어를 가진다면)
  - ULT에 비해 무거움 (용량 문제에 더해 사용자 모드에서 커널 모드로의 전환이 필요할 수도 있기 때문)
  - ULT는 한 번 구현하면 플랫폼과 무관하게 동작하는 것과 달리, KLT는 플랫폼마다 따로 구현해줘야 해서 번거로움

## [JK-012] (심화) Coroutines에서 부모-자식 관계와 예외 전파는 어떻게 이루어지나요?

자식에서 발생한 예외가 부모까지 전파되며, 이 경우 부모가 취소되면서 그 부모에 속한 다른 자식 코루틴까지 함께 취소됨. 이를 방지하려면 자식의 실패를 부모로 전파하지 않는 `supervisorScope`를 사용하면 됨. 단 `supervisorScope`를 쓰더라도 실패한 자식 자체의 예외는 그 자식 쪽에서 처리해줘야 함.
