# 의존성 주입 (Hilt & Dagger)

## [DI-001] (기초) 의존성 주입이란 무엇이고 왜 중요한가요?

- 정의
  DI란 객체가 의존성을 내부에서 생성하는 전통적 방식 대신, 스코프 외부에서 생성 후 필요한 코드에 넣어주는 방식을 의미
- 중요성
  코드, 컴포넌트, 구성 요소 간 결합도(coupling)를 줄일 수 있기 때문. 한 컴포넌트와 다른 컴포넌트 사이 결합도가 크다면, 하나가 망가졌을 때 다른 하나도 같이 망가지는 불상사가 발생. 그러나 둘을 가능한 분리해 둔다면 하나가 망가져도 다른 하나가 받는 영향이 줄어들며, 테스트 시에도 단위별로 나누기가 편해 용이함
- 부수적으로 객체 생성 책임이 외부로 나가므로 테스트에서 가짜 구현을 주입하기 쉬워짐

## [DI-002] (실무) Hilt를 통한 DI가 수동 DI에 비해 좋은 점은 무엇인가요?

- 컴파일 시점 검증
  - Hilt는 Dagger를 기반으로 하므로 필요한 바인딩이 빠졌거나 의존성 그래프를 구성할 수 없으면 빌드 시 오류를 알려 줌
- Android 생명주기에 연결된 표준 컴포넌트와 범위
  - Application·Activity·Fragment·ViewModel 등에 맞는 컴포넌트 계층을 제공해, 수동 DI에서 직접 정해야 할 생성 위치와 주입 연결을 줄여 줌
  - 범위를 지정한 바인딩은 해당 컴포넌트 인스턴스 안에서 공유되며, 컴포넌트는 자신의 수명 동안 그 인스턴스를 보관함. 범위를 지정하지 않은 바인딩은 요청할 때마다 생성될 수 있음
- 반복 코드 감소
  - 컴포넌트 생성·연결과 Android 구성요소 주입을 위한 코드가 줄고, `@AndroidEntryPoint`나 `@HiltViewModel` 등으로 주입 지점을 드러낼 수 있음
- Hilt가 임의의 자원을 자동으로 닫거나 메모리 누수를 막아 주는 것은 아님. 잘못된 장기 참조와 명시적 해제가 필요한 자원은 개발자가 관리해야 함. 수동 DI에서도 참조가 끊긴 일반 객체는 가비지 컬렉션 대상이 됨

## [DI-003] (실무) Hilt에서 `@Binds`와 `@Provides`의 차이점은 무엇인가요?

- Binds는 묶어준다는 의미
  - Hilt가 이미 생성하는 방법을 알고 있는 경우 사용 (`@Inject constructor()`가 붙어 있는 구현체 등)
  - 인터페이스에서 특정 구현체를 직접 연결할 때 사용
  - 본문이 없는 abstract 함수로 작성됨
  - 구현체가 특정되어야 하므로 반드시 제공할 구현체를 매개변수 1개로 넣어줘야 함
  - Hilt가 어차피 만드는 방법을 아니까 개발자가 "둘을 만들어서 묶어줘"라고 지시하는 것으로 이해하면 됨
- Provides는 제공한다는 의미
  - Hilt가 생성하는 방법을 모르는 외부 라이브러리 등에서 사용
  - 구체적인 구현 방법을 프로그래머가 알려줘야 함
  - 따라서 abstract 함수로 작성할 수 없고 (함수 본문이 반드시 필요하기 때문), `class` 또는 `abstract class`로 작성 (후자는 Provides와 Binds를 한 모듈에서 함께 쓰는 경우)
  - 단, `abstract class`로 넣어줄 경우에는 `@Provides` 어노테이션이 붙은 함수들은 `companion object` 블록 안에 넣어서, 클래스(모듈) 수준 변수로 정적 선언해주는 것이 성능상 유리함
  - 구현체가 상황에 따라 달라질 수 있으므로 경우에 따라 추가적인 매개변수가 들어갈 수 있음
  - Hilt가 만드는 방법을 모르니까 개발자가 "내가 만드는 방법을 구체적으로 제공해줄게"라는 것으로 이해하면 됨
