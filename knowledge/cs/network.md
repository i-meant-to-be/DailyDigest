# 네트워크

## [NET-001] (기초) TCP와 UDP는 무엇이고 어떤 차이가 있나요?

둘 다 전송 계층(4계층) 프로토콜. 응용에서는 소켓이라는 운영체제 API를 통해 둘 중 하나를 골라 쓰게 됨. (소켓 자체는 프로토콜이 아니라 프로토콜을 사용하는 인터페이스)

두 프로토콜은 신뢰성과 연결 방식에서 갈림:

- TCP
  - 신뢰성 있는 전송을 목표로 하며, 재전송·순서 보장·흐름 제어·혼잡 제어를 채택하기 때문에 신뢰성은 높으나 그만큼 느림
  - 연결을 수립한 뒤 닫기 전까지 유지되는 연결형
- UDP
  - 신뢰성을 고려하지 않아 위 장치가 전혀 없어 속도는 빠르지만 오류 복구는 온전히 개발자의 몫
  - 연결을 수립하지 않고 그냥 던지기만 하는 비연결형

## [NET-002] (기초) TCP 3단 악수를 설명해 주세요.

- 단말 A가 연결 의사를 표명 (SYN)
- 단말 B가 A의 SYN을 수락(ACK)하면서 자신도 연결 의사를 표명 (SYN+ACK)
- 단말 A가 B의 SYN에 대해 ACK를 보냄 → 이 ACK가 도착하면 양쪽 모두 연결 수립

3단계인 이유는 양방향 통신이기 때문. 각 방향마다 "보내겠다(SYN)"와 "받을 준비됐다(ACK)"가 필요한데, B의 ACK와 SYN이 한 번에 묶여서 총 3번이 됨.

## [NET-003] (심화) TCP가 UDP 기반 QUIC으로 대체되는 이유는 무엇인가요?

- TCP+TLS는 연결 수립에 왕복이 여러 번 필요한데 QUIC은 이를 1회로 줄임 (재접속 시에는 0회도 가능)
- TCP 프로토콜이 제정된 지 오래되어 현대의 기술적 상황과 맞지 않는 일부 옵션이 포함되어 있음
- TCP는 데이터 순서를 엄격히 보장하기 때문에 패킷 하나가 유실되면 뒤의 모든 데이터가 함께 막힘(HOL 블로킹). QUIC은 독립적인 스트림을 사용해 이 문제를 해결
- 모바일에서 Wi-Fi에서 LTE로 넘어가면 IP가 바뀌고 TCP는 IP가 바뀌면 연결이 끊기지만, QUIC은 IP 대신 별도의 Connection ID를 사용하기에 연결이 유지됨

## [NET-004] (기초) 주요 HTTP 상태 코드를 설명해 주세요.

- 200 OK | 성공
- 201 Created | 성공 + 데이터 생성 완료
- 204 No Content | 성공했으나 반환할 값 없음
- 301 Moved Permanently | URL이 영구적으로 변경되었을 때 사용
- 304 Not Modified | 변경 안 되었음 → 다시 다운 안 받아도 됨 → 캐시 히트
- 400 Bad Request | 요청 자체가 잘못됨 (형식 오류, 필수 값 누락 등)
- 401 Unauthorized | 인증이 안 됨. 이름과 달리 "인증 실패"이지 "권한 없음"이 아님
- 403 Forbidden | 인증은 됐으나 그 자원에 접근할 권한이 없음
- 404 Not Found | 자원이 없음
- 500 Internal Server Error | 서버 쪽에서 처리 중 예외 발생
- 503 Service Unavailable | 서버가 일시적으로 요청을 처리할 수 없음
