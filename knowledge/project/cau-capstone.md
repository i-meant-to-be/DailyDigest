## [CAP-001] (실무) 트리 구조 데이터를 protobuf로 모델링할 때 Leaf와 Group을 어떻게 나누나요?

**결정**: 별도 메시지로 나누지 않고 **자기 참조 메시지 하나에 `isLeaf` 플래그**를 두었다.

```proto
message ProtoMemoItem {
  int64 id = 1;
  string content = 2;
  bool isLeaf = 3;
  repeated ProtoMemoItem items = 4;
}
```

**버린 대안** — `ProtoMemoItemLeaf`와 `ProtoMemoItemGroup`을 따로 정의하는 안. 코드에 주석으로 남아 있다.

**합친 이유**

1. **컴포지트 패턴의 핵심은 하나의 자료형으로 그룹과 리프를 모두 표현하는 것**이라고 봤다. Kotlin이라면 인터페이스 하나에 구현체 둘로 표현할 수 있지만 protobuf 문법에서는 그게 되지 않는다
2. **서비스 특성상 가능한 형태가 리프, 그룹-리프뿐이었다.** 트리 깊이가 2를 넘을 수 없다. 그렇다면 복잡한 구현보다 직관적인 구현이 낫다고 봤다 — 복잡성은 정말 복잡성이 필요한 순간에 넣는다는 원칙

**합친 대가**

- `isLeaf`가 `false`인데 `items`가 비어 있는, **말이 안 되는 상태가 표현 가능해진다**
- 현재 코드는 그룹을 감싸는 UI에서 `list.forEach`로 세부 메모를 그리므로, 항목이 없으면 하위 UI가 아무것도 렌더링되지 않는 선에서 끝난다
- 다만 서비스 성격상 **그룹 안에 메모가 하나도 없으면 그룹 자체를 지우는 것이 맞다.** 빈 그룹 UI를 그리지 않는 데서 멈출 게 아니라 데이터를 지웠어야 했다

## [CAP-002] (실무) 저장소 생성 타입을 도메인 모델로 그대로 쓰면 어떤 문제가 생기나요?

**당시 판단**: proto 생성 타입을 UI까지 그대로 올렸다. 클린 아키텍처 이해가 부족했고, 별도 도메인 모델을 만들어 변환하는 과정에서 생길 **소스-도메인 간 불일치**를 피하는 방법이라고 생각했다.

**지금 판단**: 분리한다.

- 도메인 모델로 인터페이스를 단일화하지 않고 소스 타입을 그대로 쓰면, **소스가 바뀔 때 관련 코드를 전부 고쳐야 한다**
- 더 중요한 이유가 있다. **Proto DataStore는 Protobuf와 Android DataStore에 의존하는 Android 라이브러리다.** 도메인 모델은 도메인 지식이 바뀔 때만 변해야 하는데, 소스 타입을 그대로 쓰면 도메인이 아니라 제3자에 의한 변경에 흔들린다. 결합도 상승이다

## [CAP-003] (실무) Proto DataStore를 SharedPreferences·Preferences DataStore·Room 대신 고른 기준은 무엇인가요?

| 후보 | 판단 |
| --- | --- |
| Room | 예상 데이터 규모가 DB를 쓸 만큼 크지 않았다. 게다가 서비스 특성상 **메모가 생성됐다가 전부 지워지는 흐름이 반복**되므로 오버엔지니어링이라고 봤다 |
| SharedPreferences | 그 시점 기준 DataStore에 비해 레거시로 인지해 제외 |
| Preferences DataStore | 다뤄야 할 것이 **컴포지트 패턴 데이터**였다. 평문 문자열로 저장하는 것보다 Proto DataStore가 적합했다 |

## [CAP-004] (실무) 제3자 래퍼 라이브러리를 걷어내고 공식 SDK를 직접 쓰기로 한 이유는 무엇인가요?

**바꾸기 전 상태** — 제3자가 네이버 지도의 XML 뷰를 Compose로 포팅한 외부 라이브러리를 쓰고 있었다. 그 라이브러리가 네이버 SDK를 내부 의존성으로 갖는 구조였다.

**문제**

- **라이브러리 업데이트가 느려 최신 API 스펙을 반영하지 못했다**
- 문서가 부실해 무엇이 문제인지 원인조차 찾기 어려웠다

**대응** — 제3자 의존성을 제거하고 네이버 지도 SDK를 직접 의존성에 넣었다. 그리고 프로젝트에 필요한 부분만 직접 구현했다 — 대표적으로 핀과 경로 선 그리기. `MapView`를 `AndroidView`로 감싸고 `LifecycleEventObserver`로 생명주기를 중계하는 코드가 여기서 나왔다.

## [CAP-005] (실무) 외부 라이브러리 대신 SDK를 직접 감싸면 무엇을 얻고 무엇을 잃나요?

**얻는 것**

- 제3자 라이브러리에 의존하지 않는다. 공식 SDK 문서가 더 정확하고 최신 스펙이 반영돼 있다
- 개발자가 손댈 수 있는 부분이 많아진다

**잃는 것**

- 책임이 생긴다. 문제가 나면 전부 직접 고쳐야 한다. 생명주기 중계 코드가 새로 생긴 것도 그 비용이다

**그럼에도 낫다고 보는 이유**

- 제3자 라이브러리는 **오류가 나도 개발자가 안 고쳐 주면 할 수 있는 게 없다.** 직접 구현하면 다 감당해야 하지만 적어도 못 고치는 일은 없다
- 개인 프로젝트라 별생각 없이 제3자 라이브러리를 썼던 것이고, **수익을 내야 하는 회사 서비스에서 이렇게 취약한 의존성을 넣는 것은 큰 문제로 이어질 수 있다**

## [CAP-006] (실무) 이 프로젝트에서 가장 후회하는 결정과 가장 잘한 결정은 무엇인가요?

**가장 후회하는 것 — 로직과 UI를 명확히 분리하지 않은 것 (MVI 미도입)**

- 뷰 모델이 있는데도 **로직 일부가 UI 코드에 있거나, 뷰 모델이 절반만 처리하고 UI가 나머지 절반을 처리하는 구조**가 됐다
- 사소하게는 `onClick`·`onRefresh` 같은 콜백의 본문이 UI 코드 안에 통째로 들어가 있다. `handleSomething` 형태로 상단에 빼 두고 UI에서는 호출만 했다면 가독성이 훨씬 좋았을 것이다

**가장 잘한 것 — 네이버 지도 SDK를 직접 쓴 것** (CAP-004·CAP-005 참고)

- 유지관리가 잘 되지 않는 외부 의존성이 얼마나 불편한지 알게 된 경험이었다
