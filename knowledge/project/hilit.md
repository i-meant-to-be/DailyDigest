## [HIL-001] (실무) 멀티모듈에서 Feature를 `api`와 `impl`로 나누는 이유는 무엇인가요?

> 이 결정 자체는 파트너 개발자가 내렸다. 아래는 그 구조를 지지하는 본인의 판단이다.
> 면접에서는 "제가 정한 것은 아니지만 이 구조가 맞다고 봅니다"로 시작하는 편이 안전하다.

- `api`는 route key와 args 계약만, `impl`은 Screen·ViewModel·entry builder·DI를 갖는다
- `impl`은 다른 Feature의 `impl`에 의존하지 않고, 이동이 필요할 때 그 Feature의 `api`만 참조한다
- 근거는 이 프로젝트의 네비게이션 소유권 구조에 있다. **각 기능 모듈이 자기 네비게이션 트리 구성을 책임지고, 앱 모듈은 그렇게 모인 트리를 합치는 책임만 갖는다**
- 이 합의 아래에서는 라우팅 테이블을 한곳(`core:common` 등)에 모으는 것보다 각 기능 모듈에 나누는 것이 일관된다. 그래서 라우팅 계약을 `api` 모듈로 분리한 현재 구조가 맞다고 본다
- 대가는 화면당 모듈 수가 2배가 되는 것이다

## [HIL-002] (실무) 별도 `:navigation` 모듈을 두지 않고 앱 모듈이 네비게이션을 조립하도록 한 이유는 무엇인가요?

- 네비게이션 트리 구성 책임은 각 기능 모듈이 나눠 갖고, 합치는 일만 앱 모듈이 한다. 그래서 조립을 전담할 별도 모듈이 필요하지 않다
- 앱 모듈이 맡아도 그 부분의 크기가 크지 않아 분리할 실익이 없다고 봤다
- `module-system.md`에 별도 `:navigation` 또는 `:feature:navigator` 모듈을 만들지 않는다는 금지 조항으로 못 박았다

## [HIL-003] (실무) Gradle Convention Plugin을 Base·Capability·Composite·Quality로 나눈 기준은 무엇인가요?

- 처음부터 4분류가 아니었다. **원래는 구분 없이 한 디렉터리에 20개 넘게 평평하게 있었고, 그것을 리팩터링한 결과다**
- 파일 내용을 보니 역할이 이미 갈려 있었다 — 의존성만 설정하는 것, 베이스 모듈 설정을 맡는 것 등. 그 결을 따라 하위 디렉터리로 나눴다
- 분류 기준: Base는 platform과 compiler 기본값, Capability는 Compose·Hilt·Navigation 같은 기능 하나, Composite는 child 조합, Quality는 도구 하나씩(leaf)과 그 조합(bundle)
- **"같은 설정이 반복되기 전에는 성급하게 capability Plugin으로 추출하지 않는다"는 조항을 의도적으로 넣었다.** 데인 적이 있어서가 아니라, 플러그인 분리 자체가 가벼운 작업이 아니기 때문이다 — 공통 코드를 식별하고, 아닌 것을 빼고, `build-logic`에 파일을 넣고, 빌드 스크립트와 Gradle 설정에 등록해야 한다. 반복을 줄여 얻는 실익이 그 비용보다 클 때만 하도록 지침을 세웠다

## [HIL-004] (실무) 디자인 시스템 카탈로그를 Compose Multiplatform Web/WASM으로 직접 만든 이유는 무엇인가요?

요구 조건이 두 가지였다.

1. **웹으로 배포 가능**해서 디자이너가 언제 어디서든 어떤 기기로든 접근할 수 있을 것
2. **단순 스크린샷 검토가 아니라** 디자이너가 상태 값을 직접 조정하며 결과물을 테스트할 수 있을 것

검토하고 각하한 대안:

| 후보 | 각하 사유 |
| --- | --- |
| Storytale | 의도에 가장 근접했으나 유지보수가 멈췄고, 쓰려면 AGP와 Kotlin 버전을 내려야 해서 보안상 문제 소지 |
| Showkase | 1년 이상 유지보수 정지. Android 기기가 없으면 브라우저를 띄울 수 없고, 웹 빌드도 스크린샷 기반 |
| 스크린샷 테스트 · 카탈로그 APK | Showkase와 같은 이유 — 기기 의존과 정적 스크린샷 |

두 조건을 동시에 만족하는 것이 없어서 직접 만들었다.

## [HIL-005] (실무) 디자인 시스템 모듈에 Android Framework 의존을 금지하면 무엇을 얻고 무엇을 잃나요?

**얻은 것**

- 순수 Kotlin 코드가 되어 **테스트 용이성**이 올라간다
- Compose Multiplatform 위에서 돌아가므로 **UI 코드 재사용**이 가능해진다. 이 프로젝트처럼 멀티플랫폼을 겨냥한다면 실익이 크다
- Web/WASM 카탈로그에 올릴 수 있다. 카탈로그 도입의 부수 효과 중 이것이 가장 좋았다

**잃은 것 — 실제로 겪은 한계**

- 디자이너는 **디자인 시스템을 구현하는 시기에는 카탈로그를 집중적으로 썼지만, 그 디자인 시스템으로 실제 앱 화면을 만드는 단계에서는 거의 쓰지 않았다**
- 이유는 KMP 제약이다. 앱을 만들다 보면 아무리 UI 코드가 순수해도 어느 지점에서는 Android Native 기능이 붙는다. **그렇게 Native가 붙은 화면은 통째로 KMP에서 쓸 수 없어 카탈로그에 올릴 수 없다**
- 그래서 카탈로그의 효용이 컴포넌트 단위에 머물고 화면 단위로 올라가지 못했다

## [HIL-006] (실무) 카탈로그 Controls annotation을 실제 Composable이 아니라 별도 adapter에 붙인 이유는 무엇인가요?

- `designsystem`의 실제 Composable에는 `@CatalogControls`를 붙이지 않는다. `catalog`에 조작할 값만 매개변수로 받는 `internal` adapter Composable을 따로 두고 거기에 붙인다
- **가장 큰 이유는 타입이다.** 원시형·문자열·열거형이 아닌 커스텀 타입은 Controls UI를 자동 생성하기가 매우 어렵다. adapter를 두면 기존 UI에서 **공개하고 싶은 매개변수만 골라 드러낼 수 있다**
- adapter가 없었다면 커스텀 타입까지 전부 감당하는 KSP 코드를 짜야 했고, 그건 훨씬 어려운 일이었다
- adapter를 하나하나 쓰는 수고는 에이전트가 코드를 써 주므로 사람 입장에서 큰 비용이 아니라고 봤다
- 부수적으로 `designsystem`이 `catalog:annotations`에 의존하지 않아도 된다

## [HIL-007] (실무) 카탈로그 Controls를 KSP 코드 생성으로 만든 이유는 무엇인가요?

- **Controls 구현 비용을 사람에게 전가하지 않고 도구가 지게 하려는 것**이 목적이었다. 필요한 것은 adapter 시그니처에 맞는 Controls를 컴파일 타임에 만들어 내는 일이고, KSP가 정확히 그 역할을 한다
- `catalog:processor`가 kotlinpoet-ksp로 adapter와 같은 패키지에 `${Adapter}Args`와 `${Adapter}Controls`를 생성한다

**대안이었을 런타임 리플렉션이 이 환경에서는 불가능하다**

- 같은 일을 하는 다른 방법은 리플렉션이다. adapter 함수를 **실행 중에** 들여다보고 매개변수 타입을 읽어 그 자리에서 Controls를 만드는 방식이다
- 그런데 이 카탈로그는 **Kotlin/Wasm**으로 빌드된다. Wasm 타깃에서는 `kotlin-reflect`를 쓸 수 없고 리플렉션이 극히 제한적이라, 런타임에 함수 시그니처를 읽는 접근 자체가 성립하지 않는다
- 즉 **플랫폼이 컴파일 타임 코드 생성을 사실상 유일한 선택지로 만든다.** 부수적으로 잘못된 시그니처가 런타임이 아니라 빌드에서 걸리고, 리플렉션 메타데이터가 산출물에 들어가지 않아 Wasm 번들도 얇게 유지된다

> 이 근거는 당시 본인이 명시적으로 짚은 것이 아니라, 에이전트와 함께 설계하며 반영됐을
> 가능성이 높은 항목이다. 면접에서는 "설계 당시 Wasm의 리플렉션 제약을 근거로 잡았다"보다
> **"Wasm 타깃이라 컴파일 타임 생성 외에 선택지가 없었다"**로 사실만 말하는 편이 안전하다.
- 지원 타입을 `String`·`Boolean`·정수형·실수형·`Enum`으로 **의도적으로 잘랐다.** 컬렉션·nullable·sealed까지 넣으려면 개발량이 너무 커진다
- 다시 만든다면 **매개변수별 설명 annotation을 최우선으로 넣겠다.** 이 기능의 목적이 디자이너와의 협업 개선인 만큼, 사용할 디자이너에게 기능 제약을 설명해 주는 것이 중요하기 때문이다

## [HIL-008] (실무) AI 에이전트와 협업할 때 문서를 계층화한 이유는 무엇인가요?

- 프로젝트 초기에 파트너와 에이전트로 개발한다는 합의는 있었으나, **둘이 쓰는 에이전트가 서로 달랐다**(Claude, Codex, Cursor, Antigravity). 코드 품질 일관성에 대한 우려가 있었다
- 그래서 초기부터 에이전트 규칙을 제공하기로 했고, **절대 바뀌지 않을 규칙(`CONSTITUTION.md`)과 개발 상황에 따라 바뀔 수 있는 아키텍처 문서(`ARCHITECTURE.md` 이하)로 계층화**했다. 한쪽에 융통성을 두는 편이 유연하다고 봤다
- 문서 해석 우선순위: `CONSTITUTION.md` → `ARCHITECTURE.md` → `docs/architecture/*.md` → `AGENTS.md` → `README.md`
- 예방 차원이었지 특정 사고에 대한 대응은 아니었다
- **팀원도 실제로 썼다.** `AGENTS.md`와 `CLAUDE.md`를 모두 두어 별도 설정 없이 각 에이전트가 자동으로 문서를 읽는 구조였기 때문이다

## [HIL-009] (실무) 에이전트가 만든 결과물이 아키텍처 계약을 지켰는지 어떻게 검증했나요?

- **자동화된 장치는 두지 않았다.** Detekt 커스텀 룰, 모듈 의존성 검사, CI 게이트 모두 없다
- 대신 복잡한 작업에 한해 수동으로 교차 검토했다. **같은 에이전트의 다른 세션을 열거나 아예 다른 에이전트를 띄워, 구현 에이전트가 남긴 계획 문서와 구현 결과 문서를 근거로 평가하게 했다**
- 이 방식의 한계는 사람이 개입해야 하고 복잡한 작업에만 적용된다는 것이다

## [HIL-010] (실무) 이 프로젝트에서 가장 후회하는 결정과 가장 잘한 결정은 무엇인가요?

**가장 후회하는 것 — 도메인 문서를 도입하지 않은 것**

- 아키텍처 문서는 기술 규칙과 컨벤션만 다루고 **도메인 지식은 다루지 않는다.** 이 둘은 다른 영역이다
- 이 프로젝트는 iOS와 Android 양쪽에서 개발됐다. 도메인 지식이 같아도 **폼 팩터에 따라 세부 구현 논리가 달라진다.** 즉 도메인과 별개로 "도메인 + OS 특성"을 따로 정리했어야 했다
- iOS 쪽은 그렇게 했고 평가가 좋았다. 우리는 도메인 문서를 하나도 남기지 않아 **서로 다른 기능을 연결할 때 고생했다**

**가장 잘한 것 — 카탈로그 도입**

- 디자이너와의 협업 개선도 좋았지만, 의외로 더 큰 이득은 **디자인 시스템 모듈이 Android Native에 의존하지 않게 된 것**이었다
- 순수 Kotlin이 되면서 테스트 용이성이 올라갔고, 멀티플랫폼을 겨냥한다면 UI 코드 재사용도 가능해진다
