## [CNS-001] (실무) 동형암호 연산을 서버가 아니라 클라이언트에서 수행하기로 한 이유는 무엇인가요?

세 가지 이유가 있었고, 셋의 성격이 다르다.

1. **역량 제약** — 1인 프로젝트였고 서버 개발 경험이 거의 없었다. 이 상황에서는 연산을 기기에 몰아넣는 편이 빠른 개발이 가능하다고 판단했다
2. **학습 동기** — SEAL이 C++ 라이브러리인데 Android에서 쓸 수 있는지 조사해 보니 가능했다. 해 본 적 없는 일이라 해 보고 싶었다
3. **위협 모델** — 서버도 믿지 못한다는 전제를 깔았다. **서버가 암·복호화 역량을 갖는다는 것은 공격자가 서버를 탈취하면 데이터를 가져갈 수 있다는 뜻**이다. 클라이언트끼리 소통하고 서버는 아무것도 모르게 두는 편이 보안상 나을 수 있다고 봤다

> 면접에서는 3번을 먼저 말하는 것이 낫다. 1번과 2번은 사실이지만 설계 근거가 아니라 사정과 동기다.

## [CNS-002] (심화) C++ 라이브러리를 NDK로 크로스 컴파일할 때 부딪히는 문제를 어떻게 진단하고 우회했나요?

- SEAL 빌드가 계속 실패했다. 로그를 보니 **특정 검사의 종료 코드가 1이 되어 컴파일이 중단되는 패턴이 반복**되고 있었다
- 원인은 SEAL이 CMake의 `try_run`으로 컴파일러 내장 함수(`__builtin_clzll`, `_addcarry_u64` 등) 지원 여부를 **실제로 실행해 확인**한다는 점이다. 크로스 컴파일에서는 타깃(ARM) 바이너리를 호스트(x86)에서 실행할 수 없어 이 검사가 무조건 실패한다
- 우회는 해당 검사의 종료 코드를 캐시 변수로 미리 박아 넣는 것이다

```cmake
set(SEAL___BUILTIN_CLZLL_FOUND_EXITCODE 0 CACHE STRING "Manually set exit code for cross-compiling")
set(SEAL__ADDCARRY_U64_FOUND_EXITCODE 0 CACHE STRING "Manually set exit code for cross-compiling")
```

- 반복되는 오류를 모두 같은 방식으로 처리해 빌드를 통과시켰다. **검색이나 이슈가 아니라 로그 패턴을 보고 직접 진단했다**
- 이 밖에 불필요한 빌드 대상(테스트, 예제, `SEAL_C`, 벤치마크, MSGSL·ZSTD·Intel HEXL)을 모두 꺼서 빌드 시간과 산출물을 줄였다

## [CNS-003] (실무) 병렬 처리 방식을 벤치마크로 고른 과정과 결과를 설명해 주세요.

**측정 대상** — 같은 동형암호 연산을 세 가지 병렬 실행 환경에서 비교했다.

| 환경 | 비고 |
| --- | --- |
| Kotlin Coroutines | `Dispatchers` |
| Java `ExecutorService` | 고정 스레드 풀 |
| C++ `std::thread` | 네이티브 |

**변수** — 병렬 처리 환경과 스레드 수. **실험 기기** — 코어 10개 스마트폰.

**결과**

- C++ 10 스레드가 가장 빨랐다. 다만 **Coroutines 10 스레드와 차이가 거의 없었다**
- 조건에 따라서는 **최대 4배 이상 차이가 나는 경우도 있었다**
- 결론: 미세한 성능 우위를 원하고 디버깅 편의를 포기할 수 있으면 C++, 이 정도 성능이면 충분하고 디버깅이 편했으면 하면 Kotlin

**이 벤치마크를 이 프로젝트에서 가장 잘한 결정으로 본다.** 그냥 구현했다면 사용자가 실제로 FHE 곱셈 연산을 쓰는 기능에서 큰 부하가 걸렸을 것이다.

## [CNS-004] (심화) SEAL 컨텍스트를 JNI 전역 포인터로 들고 있게 한 이유와 스레드 안전성은 어떻게 봤나요?

**전역으로 둔 이유**

- `g_context`, `g_evaluator`, `g_encoder`는 전부 **공용**이다. 서비스를 쓰는 동안 암호화와 복호화가 반복되는데, 매번 초기화하면 인스턴스도 여러 개 만들고 생성 시간도 든다
- 그래서 무거운 것만 전역으로 두고, 가벼운 것은 지역 변수로 두는 식으로 나눴다

**스레드 안전성 — 두 층을 나눠서 봐야 한다**

*(1) SEAL 객체 자체* — 안전한 편이다. `SEALContext`는 생성 시점에 파라미터를 검증해 만들어 두고 그 뒤로는 **읽기만 하는 불변 객체**이고, `Evaluator`와 `BatchEncoder`는 컨텍스트를 참조해 연산만 수행할 뿐 자체 가변 상태를 들고 있지 않다. 그래서 **한 번 만든 뒤 여러 스레드에서 동시에 읽는 사용은 안전하다.**

*(2) 이 코드가 그 객체를 담아 둔 방식* — **여기가 실제 위험 지점이다.**

- `g_context`, `g_evaluator`, `g_encoder`는 전역 `std::unique_ptr`이고 `initContext()`가 이들을 **재대입**한다
- 즉 문제는 SEAL 내부가 아니라 **`initContext()`가 포인터를 갈아 끼우는 시점과 다른 스레드가 그 포인터를 읽는 시점 사이의 경합**이다. `unique_ptr` 재대입은 원자적이지 않다
- 그리고 `initContext()`가 불리기 전에 다른 JNI 함수가 호출되면 널 포인터 역참조로 이어진다
- 대응은 초기화를 한 번만 보장하는 것이다 — `std::call_once`나 함수 지역 정적 변수(C++11 이후 초기화가 스레드 안전하다)로 감싸면 두 문제가 함께 해결된다

**전역으로 둔 이유는 여전히 타당하다.** 고쳐야 할 것은 "전역이라는 선택"이 아니라 "초기화 시점 보호가 없다는 것"이다.

## [CNS-005] (실무) CI에서 NDK와 AVD를 캐시하고 계측 테스트를 조건부로 실행한 이유는 무엇인가요?

- **가장 큰 동기는 Android 계측 테스트 시간이었다.** 에뮬레이터를 띄우는 비용이 커서 어떻게든 줄이려고 AVD 스냅샷을 캐시하는 방향으로 갔다
- `dorny/paths-filter`로 Android 소스가 실제로 바뀐 PR에서만 계측 테스트를 돌리고, KVM을 켜 에뮬레이터를 가속했다
- **캐시로 줄인 시간은 기대만큼 크지 않았다.** Gradle 동작 자체가 가장 큰 부하였기 때문이다. 에뮬레이터도 큰 부하이긴 했다

## [CNS-006] (실무) `BuildConfig`에 구운 비밀 값의 한계는 무엇인가요?

- CI가 `secrets.LOCAL_PROPERTIES`로 `local.properties`를 만들고, 빌드 스크립트가 그 값을 `buildConfigField`로 굽는다
- **`BuildConfig`에 구운 문자열은 APK를 디컴파일하면 그대로 보인다.** `API_BASE_URL` 정도면 감수할 만하지만 진짜 비밀 값을 여기 두면 안 된다
- 대응으로 값을 암호화해 두고 빌드 산출물에서 Kotlin이 아닌 다른 수단(C++ 등)으로 복호화하는 방식이 쓰인다고 들었다

> 위 마지막 항목은 **난독화이지 보안이 아니다.** 복호화 키가 결국 앱 안에 있어야 하므로
> 시간을 들이면 뚫린다. 클라이언트에 둔 비밀은 공개된 것으로 봐야 한다는 것이 정답이고,
> 저 방식은 "비용을 올릴 뿐"으로 말해야 한다. SEC-012와 이어진다.

## [CNS-007] (실무) 빌드 타입이나 flavor 대신 `local.properties` 플래그로 개발 모드를 나눈 이유는 무엇인가요?

- `isDevModeEnabled`, `isHttpLoggingEnabled`, `isMockEnabled`, `isBenchmarkEnabled`를 `local.properties`에서 읽어 `BuildConfig` 필드로 굽는다
- **디버그 빌드라도 실제 서버에 요청을 보내고 싶을 때가 있고, 반대로 모방(mock) API를 쓰고 싶을 때가 있다.** 빌드 타입 하나로는 이 조합을 표현할 수 없어 축을 분리했다
- React에서 쓰던 방식을 가져온 것이다
- 팀원이 없어서 "사람마다 파일이 달라 빌드가 재현되지 않는다"는 이 방식의 통상적 단점은 문제가 되지 않았다

## [CNS-008] (실무) 이 프로젝트에서 가장 후회하는 결정과 가장 잘한 결정은 무엇인가요?

**가장 후회하는 것 — 멀티모듈 아키텍처를 도입하지 않은 것**

- 당시에는 멀티모듈 아키텍처 자체를 몰랐다
- **암호화 매니저를 따로 뺀 것부터가 모듈로 분리하기 좋은 대상이었다.** 알았다면 최소한 그것만이라도 공용 모듈로 뺐을 것이다

**가장 잘한 것 — 벤치마크로 최적 옵션을 걸러낸 것** (CNS-003 참고)
