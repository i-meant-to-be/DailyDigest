## 1. [CMP-008] 외부 리스너와 DisposableEffect — 2점

**맞은 부분**

효과 본문에서 등록하고 `onDispose`에서 해제한다는 위치, 키 변경 시 정리 후 재등록하고 Composition 이탈 시 정리한다는 순서는 맞았습니다. 이전 오답에서 개선된 부분입니다.

**틀린 부분과 빠진 부분**

질문에서 관리하는 것은 외부 리스너인데 두 차례 모두 정리 대상을 코루틴이라고 답했습니다. `DisposableEffect`는 자체적으로 코루틴을 실행·취소하는 구조가 아닙니다. 여기서는 등록했던 리스너를 직접 해제해야 합니다. 키가 그대로인 재구성에서는 다시 등록하지 않는다는 조건도 덧붙이면 좋습니다. API 이름의 문제가 아니라 자원의 종류와 책임을 혼동한 것이므로 2점입니다.

**면접에서는 이렇게**

“Composition에 들어오면 효과 본문에서 리스너를 등록하고 `onDispose`에 해제 코드를 둡니다. 키가 바뀌면 기존 리스너를 해제한 뒤 새 대상에 등록합니다. Composition에서 나가면 현재 리스너를 해제합니다. 같은 키로 재구성될 때는 유지됩니다.”

근거: [Compose 부수 효과 공식 문서](https://developer.android.com/develop/ui/compose/side-effects#disposableeffect).

## 2. [SEC-007] AES-GCM의 IV 관리 — 0점

**맞은 부분**

IV 관리가 보안에 영향을 준다는 방향만 있습니다. 핵심인 공개 가능 여부, 고유성의 범위, 재사용 결과를 모두 반대로 설명했습니다. 답변은 있으나 핵심 개념을 완전히 잘못 이해한 경우여서 0점입니다.

**틀린 부분과 빠진 부분**

IV는 비밀 키가 아니며 암호문과 함께 저장할 수 있습니다. IV를 안다고 AES 키를 유추할 수 있다는 설명은 틀렸습니다. 중요한 조건은 **같은 키를 사용하는 모든 암호화에서 IV를 재사용하지 않는 것**입니다. 키마다 하나씩 다른 IV를 정해 두고 반복 사용해도 되는 것이 아닙니다.

같은 키·IV를 재사용하면 같은 키스트림이 쓰여 두 암호문의 XOR에서 두 평문의 XOR 관계가 드러납니다. 인증 보장도 깨져 위조 공격으로 이어질 수 있습니다. 이는 AES 비밀 키가 곧바로 복구된다는 뜻과 구분해야 합니다.

**면접에서는 이렇게**

“AES-GCM에서는 같은 키로 암호화할 때마다 고유한 IV를 사용해야 합니다. IV는 비밀이 아니어서 암호문·인증 태그와 함께 저장할 수 있습니다. 같은 키·IV를 재사용하면 평문 사이의 관계가 노출되고 인증 위조도 가능해질 수 있으므로, 키의 사용 기간 전체에서 중복되지 않게 관리합니다.”

근거: [NIST의 IV 정의](https://csrc.nist.gov/glossary/term/iv), [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final), [Java Cipher의 GCM 주의사항](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Cipher.html).

## 3. [DI-007] Dagger의 컴파일 시점 검증 — 3점

**맞은 부분**

어노테이션을 바탕으로 의존 관계를 구성하고 규칙을 검증한다는 설명, 순환 의존성이라는 오류 사례, 런타임 전에 발견한다는 목적은 정확합니다.

**빠진 부분**

“규칙에 맞는지 확인한다”에서 한 단계 더 들어가 무엇을 연결하는지 설명해야 심화 문항의 통과 답이 됩니다. 요청한 타입과 한정자에 해당하는 바인딩이 있는지, 그 바인딩을 만들기 위한 의존성까지 해결되는지가 핵심입니다. 누락·중복 바인딩이나 컴포넌트와 스코프의 불일치도 예로 들 수 있습니다. 여러 객체가 하나의 의존성을 공유할 수 있으므로 엄밀히는 트리보다 그래프가 정확합니다.

순환의 구체적인 형태에는 지연 제공을 통한 예외가 있고, 그래프가 유효하더라도 객체 생성 로직 내부의 예외까지 모두 막지는 못합니다. 모든 런타임 오류를 예방한다는 식으로 확대하면 안 됩니다.

**면접에서는 이렇게**

“Dagger는 컴포넌트가 요청하는 객체에서 출발해 생성자와 모듈의 바인딩을 연결하고, 필요한 타입과 한정자를 만족하는 제공 경로가 있는지 컴파일 시 확인합니다. 제공자가 없거나 중복되거나, 해결할 수 없는 순환·스코프 문제가 있으면 빌드가 실패합니다. 유효한 그래프로 객체 생성 코드를 만들지만 생성 로직 자체의 런타임 오류까지 보장하지는 않습니다.”

근거: [Dagger 기본 사용법·컴파일 검증](https://dagger.dev/dev-guide/basic-usage).

## 4. [AND-035·신규] Gradle 빌드 시간 개선 — 2점

**맞은 부분**

느린 태스크를 먼저 찾겠다는 접근과 증분 빌드·빌드 캐시를 활용하겠다는 방향은 맞습니다.

**틀린 부분과 빠진 부분**

컨벤션 스크립트는 공통 빌드 설정을 재사용하는 수단입니다. 파일을 나눈 것만으로 태스크의 입력이나 모듈 의존 관계가 달라져 변경 전파가 줄어드는 것은 아닙니다. 어떤 의존 경계를 바꾸거나 어떤 불필요한 입력을 제거할 것인지 설명해야 합니다.

또 “증분 빌드와 캐시를 활용한다”는 이름만 있고 줄이는 작업이 없습니다. 입력·출력이 그대로면 태스크 실행을 생략하는 것, 지원하는 태스크에서 변경분만 처리하는 것, 같은 입력으로 만든 과거 산출물을 캐시에서 복원하는 것을 구분해야 합니다. 최초 빌드와 변경 후 반복 빌드도 나누어 측정해야 합니다.

**면접에서는 이렇게**

“먼저 프로파일 보고서 등으로 구성 단계와 태스크 실행 시간을 나눠 확인하고, 같은 변경 조건으로 반복 측정합니다. 반복 빌드가 느리면 태스크 입력·출력과 재실행 원인을 확인해 불필요한 전체 실행을 줄입니다. 빌드 캐시는 같은 입력의 산출물을 재사용해 실행 비용을 줄이고, 구성 캐시는 호환성을 확인한 뒤 구성 단계의 재계산을 줄이는 데 사용합니다. 모듈 의존성이 과도하다면 변경 영향 범위도 줄이되, 컨벤션 플러그인 분리 자체를 속도 개선으로 보지는 않습니다.”

근거: [Gradle 성능 개선](https://docs.gradle.org/current/userguide/performance.html), [빌드 캐시](https://docs.gradle.org/current/userguide/build_cache.html), [구성 캐시](https://docs.gradle.org/current/userguide/configuration_cache.html).

원격 이력을 통합하면서 같은 주제가 앞선 세션에서 AND-035로 등록된 것을 확인했습니다. 기존 ID에 이번 2점을 반영했고, 문항을 중복 등록하지 않았습니다. 지식 파일의 질문과 `> (미작성)` 답은 원격 원문을 유지했습니다. 질문지의 `[신규]` 표시는 출제 당시의 기록입니다.

## 5. [HIL-003] Convention Plugin 분류 기준 — 2점

**맞은 부분**

Base가 기반 설정, Quality가 코드 품질 관련이라는 큰 방향과, 실제 재사용이 생긴 뒤 추출한다는 판단은 맞습니다. “2~3곳”이라는 수치 자체를 틀렸다고 보지는 않습니다.

**틀린 부분과 빠진 부분**

Composite의 기준은 “부가적으로 쓰는 스크립트”가 아니라 **하위 플러그인을 조합하는 역할**입니다. 선택적으로 적용하는지는 조합 책임과 다른 축입니다. Capability도 단순히 기반 위에서 돌아간다는 설명으로는 다른 분류와 구별되지 않습니다. Compose·Hilt 같은 단일 기능을 더하는 역할이라고 설명해야 합니다.

Quality는 개별 도구를 설정하는 단위와 이를 묶는 조합으로 나뉜다는 점, 추출로 줄어드는 반복과 등록·유지 비용을 비교했다는 근거가 빠졌습니다. 프로젝트 원문에 이미 있는 설계 결정을 충분히 재현하지 못했습니다.

**면접에서는 이렇게**

“기존 플러그인들을 실제 책임에 따라 분류했습니다. Base는 플랫폼·컴파일러 기본값, Capability는 Compose나 Hilt 같은 기능 하나, Composite는 하위 플러그인의 조합을 맡습니다. Quality는 품질 도구별 단위와 그 묶음으로 나눴습니다. 공통 설정이 반복되고, 추출·등록·유지 비용보다 반복 제거의 실익이 커질 때 플러그인으로 분리했습니다.”

대조 원문: `knowledge/project/hilit.md` HIL-003.

## 6. [JK-004] Java·Kotlin과 코루틴·스레드 — 3점

**맞은 부분**

Java와 Kotlin/JVM이 JVM 바이트코드로 컴파일된다는 공통점, 널 가능성을 타입으로 구분한다는 차이, `data class`와 기본 접근자를 통한 반복 코드 감소를 짚었습니다. 중단된 실행 상태를 보존하고 실행 자원을 내어 준다는 설명도 이전보다 구체적입니다.

**틀린 부분과 빠진 부분**

코루틴은 **스레드 위에서 실행되는 중단 가능한 계산**이라는 관계를 먼저 밝혀야 합니다. 중단하면 다른 코루틴이 반드시 배정되는 것이 아니라 실행하던 스레드가 다른 작업에 쓰일 수 있습니다. 코루틴 안에서 블로킹 함수를 호출하면 그 스레드는 여전히 막힙니다.

“스레드는 멈추기 때문에 유휴 스레드가 자원을 사용할 수 없다”는 설명은 범위가 모호합니다. 블로킹된 스레드는 다른 코루틴 실행에 재사용되지 못하지만, 운영체제는 다른 실행 가능한 스레드를 CPU에서 실행할 수 있습니다. 스레드 하나가 멈춘 것과 CPU 사용 불가를 구분해야 합니다. 동시성이 항상 병렬성인 것도 아닙니다.

프로퍼티는 `val`에 getter, `var`에 getter·setter가 기본 제공됩니다. 모든 경우에 setter가 있는 것은 아닙니다. Kotlin 전체에는 다른 컴파일 대상도 있으므로 공통 실행 기반 설명은 Kotlin/JVM으로 한정하고, `data class`가 생성하는 함수의 예까지 말하면 좋습니다.

**면접에서는 이렇게**

“Java와 Kotlin/JVM은 바이트코드로 컴파일되어 JVM에서 실행됩니다. Kotlin은 널 가능성을 타입으로 구분하고, 프로퍼티 접근자와 data class의 동등성 비교·문자열 표현 등으로 반복 코드를 줄입니다. 코루틴은 스레드 위에서 실행되는 중단 가능한 작업입니다. 비차단 대기 중에는 상태를 보존하고 스레드를 다른 작업에 내어 줄 수 있지만, 블로킹 호출을 하면 그 스레드는 막힙니다. 여러 코루틴은 한 스레드에서도 번갈아 진행할 수 있고 병렬 실행 여부는 실행 환경에 달려 있습니다.”

근거: [Kotlin 코루틴 기초](https://kotlinlang.org/docs/coroutines-basics.html), [프로퍼티](https://kotlinlang.org/docs/properties.html), [데이터 클래스](https://kotlinlang.org/docs/data-classes.html).

## 이번 세션에서 드러난 흐름

등록 위치·바이트코드·코루틴 상태 보존 등 구체적으로 설명하는 부분은 늘었습니다. 다만 자원의 종류, 고유성의 범위, 플러그인의 분류 축처럼 개념 사이의 경계를 바꾸어 말하는 문제가 남아 있습니다. 다음 연습에서는 각 개념을 “무엇을 대상으로, 어떤 조건에서, 무엇이 달라지는가”의 순서로 설명하고, 특히 AES-GCM의 IV는 공개 가능성과 동일 키 내 고유성을 먼저 다시 학습해야 합니다.
