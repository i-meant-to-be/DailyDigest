## 1. [AND-031] Android App Bundle을 게시하면 사용자 기기에 앱이 어떤 형태로 설치되나요? APK 직접 배포와의 차이를 설명하고, 자주 쓰지 않는 기능을 동적 기능 모듈로 분리할 때 전달 방식과 미설치·설치 실패 상태를 어떻게 처리할지 말해 주세요.

`platform/android` · 실무 · 이전 오답 · 지난 지적: AAB의 게시 형식과 기기별 APK 생성 관계, 동적 기능 전달 방식과 미설치·설치 실패 처리를 설명하지 못함

### 내 답변

사용자 기기 및 환경에 최적화된 소스 코드, 데이터 및 리소스만 포함하는 APK가 설치됨.

앱 번들은 모든 가능한 환경 및 디바이스에서의 소스 코드를 전부 포함하고 있는 하나의 묶음으로, 개발자가 앱 번들을 Play 콘솔에 업로드하면 Play 콘솔은 가능한 모든 경우에 따른 최적화된 APK들을 생성하고 서명 키로 서명. 사용자가 앱 다운로드 요청을 하면 사용자 환경과 디바이스 스펙을 보고, APK들 중 최적의 하나를 골라 내려보냄.

APK 직접 배포와의 차이점은 크게 3가지로, 앱 번들 버전 코드 통일에 따른 버전 관리 편의성, APK 파일 크기 최적화와 다수 APK를 단일 앱 번들 하나로 배포 가능하게 하여 배포 경험 개선이 있음.

자주 안 쓰는 기능을 동적 기능 모듈로 분리할 경우 앱 설치 시 함께 또는 설치 후 기능이 필요할 때 요청 및 수령이 가능하며, 해당 기능 모듈 미설치/실패 시에는 데이터 다운로드 실패를 알리고 사용자가 기능을 사용할 수 없게 막아야 함.

## 5. [CMP-006] Compose에서 `LaunchedEffect`는 언제 코루틴을 시작하고 취소하나요? 같은 키로 재구성될 때, 키가 바뀔 때, 해당 Composable이 Composition에서 빠질 때의 동작을 각각 설명해 주세요.

`platform/compose` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

가장 기본적인 조건 먼저 보면 구성(Composition)에 진입할 경우 코루틴이 시작되고, Composable이 폐기(Disposal)될 경우 코루틴이 취소.

그 외 `LaunchedEffect`는 코루틴 호출을 트리거하는 `key`를 여러 개 가질 수도 있고 가지지 않을 수도 있음.

- 가지지 않는다면 최초 구성 진입 시에만 1회 호출됨
- 키를 여러 개 가진다면, 키가 변경될 때마다 호출됨

## 6. [JK-005] Kotlin의 `data class`가 자동으로 제공하는 기능과 선언 제약을 설명해 주세요. 주 생성자에 선언한 속성과 클래스 본문에 선언한 속성이 동등성 비교·복사에서 어떻게 다뤄지는지, 일반 클래스의 기본 동등성 비교와 무엇이 다른지도 말해 주세요. 가변 리스트 속성이 있을 때 `copy()`로 만든 객체를 수정하면 원본에 어떤 영향이 있나요?

`lang/java-kotlin` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-18) · 지난 지적: 자동 생성 기능과 주 생성자 속성의 참여 범위 누락, 일반 클래스의 동등성 비교에 대한 오해, 얕은 복사와 선언 제약 설명 부족

### 내 답변

자동 제공 기능은 다음과 같음:

- 함수 `componentN`: 구조 분해를 위한 함수
- 함수 `copy`: 특정 인스턴스를 바탕으로 새 인스턴스를 생성하는 함수
- 함수 `equals`: 단순 해시코드 비교가 아닌 전체 인스턴스 매개변수의 동일 여부를 반환하는 함수

선언 제약으로는 `data class`는 `open` 키워드를 가질 수 없어 상속될 수 없으며, 주 생성자 `()` 안에 반드시 1개 이상의 매개변수가 필요하고 해당 매개변수는 반드시 `val` 또는 `var`로 선언되어야 함.

위에서 말했듯이 동등성 비교는 기본적으로는 주 생성자의 모든 매개변수가 동일한지 여부에 대한 판단으로 이루어지며, 이 때 주 생성자가 아닌 클래스 본문에 선언된 매개변수는 기본 `equals` 함수에서 고려되지 않음. 원한다면 함수 오버라이딩 필요.

또한 `copy` 함수는 얕은 복사라는 점에 주의해야 함. 그렇기 때문에 만약 리스트를 복사할 경우 리스트 자체는 새로운 참조를 가지게 되지만 안에 있는 원소들의 참조는 그대로 따라옴. 이러한 맹점으로 인해 원본 리스트 원소를 수정하면 복사된 리스트의 원소도 수정되는 문제가 발생할 수 있음. (단, 이 부분은 정수, 실수 등 Java에서 Primitive로 간주되는 원소에는 해당되지 않으며 커스텀 클래스 등 참조로 처리되는 자료형으로 지정된 원소만 해당)
