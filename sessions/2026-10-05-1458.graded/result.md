## 1. [AND-031] 앱 번들과 동적 기능 모듈 — 3점

**맞은 부분**
AAB를 Play에 게시하고 기기에 필요한 코드·리소스를 담은 APK를 전달한다는 큰 흐름, 배포 관리와 다운로드 크기 측면의 이점을 설명했습니다. 동적 기능의 설치 시 전달과 필요 시 전달, 실패 안내와 기능 진입 차단도 맞습니다.

**빠진 부분**
요청부터 설치 완료까지의 진행 상태와 재시도 처리가 없습니다. 미설치는 정상적인 초기 상태일 수 있으므로 실패와 구분해야 합니다. 다운로드가 끝났다는 이유만으로 진입시키지 않고 설치 완료를 확인해야 합니다.

**틀린 부분**
기기에 최적화된 APK 하나를 고르는 설명은 정확하지 않습니다. 일반적으로 기본 APK와 기기 설정에 맞는 구성 APK, 필요한 기능 APK가 함께 설치됩니다. AAB에는 원본 소스 코드가 아니라 컴파일된 코드와 리소스가 들어갑니다. APK 직접 배포도 크기를 최적화할 수 있고, AAB의 장점은 기기별 APK 생성·서명·관리를 Play에 맡기는 것입니다. [Android 공식 문서](https://developer.android.com/guide/app-bundle)

**면접에서는 이렇게**
“AAB는 게시 형식이고, Play가 기기 구성에 맞는 기본·구성·기능 APK를 만들어 전달합니다. 개발자가 기기별 APK를 직접 관리하는 부담과 사용자의 다운로드 크기가 줄어듭니다. 자주 쓰지 않고 초기 실행에 필요 없는 큰 기능은 필요 시 설치하도록 분리할 수 있습니다. 앱은 미설치·설치 중·완료·실패를 구분하고, 완료 후에만 기능으로 진입시키며 실패하면 재시도를 제공합니다.”

## 2. [DI-011] Hilt 없이 Dagger 사용 — 2점

**맞은 부분**
Android 생명주기와 그래프 계층을 개발자가 관리해야 한다는 방향, 컴파일 시점 의존성 연결 검증은 맞습니다. 지난 답변의 컴파일 시점 검증에 대한 오해는 교정됐습니다.

**빠진 부분**
앱 컴포넌트를 Application에 보관하고 화면별 하위 컴포넌트를 화면 수명에 맞게 생성·보관하는 구체적인 책임 구분이 없습니다. 컴파일 시점 그래프 검증과 실행 중 생명주기 관리의 한계를 구분해야 합니다.

**틀린 부분**
Dagger가 스코프 지정과 컴포넌트 보관을 알아서 하지는 않습니다. 개발자가 범위를 선언하고 컴포넌트 인스턴스의 참조를 관리합니다. 스코프는 해당 컴포넌트 안에서 객체를 재사용하는 규칙이며 Android 수명을 자동으로 관리하는 장치가 아닙니다. 시스템이 생성하는 Activity를 생성자 주입으로 만드는 설명도 틀립니다. 일반적인 Dagger 사용에서는 필드 주입을 선언하고 컴포넌트의 주입 함수를 호출합니다. [Android 공식 문서](https://developer.android.com/training/dependency-injection/dagger-android)

**면접에서는 이렇게**
“Dagger는 선언된 그래프를 검증하고 객체 생성·주입 코드를 생성합니다. 앱과 화면의 컴포넌트 계층, 범위 선언, 생성·보관·참조 해제 시점은 개발자가 정합니다. 앱 컴포넌트는 Application에 보관하고 화면 컴포넌트는 화면 수명에 맞춰 관리합니다. Activity는 시스템이 생성하므로 의존성을 필드에 선언하고 초기화 시 컴포넌트의 주입 함수를 호출합니다. 누락된 바인딩 같은 그래프 오류는 컴파일 때 검증하지만 잘못된 장기 참조나 주입 호출 누락까지 생명주기에 맞게 해결해 주지는 않습니다.”

## 3. [SEC-010] 토큰 재발급과 재시도 — 2점

**맞은 부분**
인증 실패 요청을 모으고, 임계 영역과 진행 플래그로 중복 재발급을 막고, 새 토큰 저장 후 원래 요청을 재시도하는 흐름은 맞습니다. 재발급을 무한 반복하지 않으려는 제한도 있습니다.

**빠진 부분**
재발급 중 들어온 요청이 같은 결과를 기다리도록 하고, 성공·실패 어느 경우에도 플래그를 해제하고 대기 요청을 완료해야 합니다. 늦게 도착한 이전 토큰의 실패 응답은 현재 토큰과 비교해 이미 갱신됐다면 재발급 없이 재시도할 수 있습니다. 재발급 횟수만 제한하면 원래 요청의 인증 실패가 다시 재발급을 유발하는 순환은 막지 못하므로 원래 요청에도 인증 재시도 횟수 제한이 필요합니다.

**틀린 부분**
재발급이 두 번 실패했다는 사실만으로 리프레시 토큰을 지우는 것은 과도합니다. 네트워크 단절·서버 장애와 토큰 만료·폐기 같은 영구적인 인증 실패를 구분해야 합니다. OAuth의 `invalid_grant`는 무효·만료·폐기된 리프레시 토큰 등을 나타내지만 모든 실패가 이 경우는 아닙니다. [OAuth 2.0 오류 정의](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)

**면접에서는 이렇게**
“만료로 확인된 인증 실패는 하나의 재발급 작업을 공유하도록 묶습니다. 잠금 안에서 토큰이 이미 바뀌었는지 확인하고, 갱신이 필요하면 한 요청만 재발급하고 나머지는 결과를 기다립니다. 성공하면 새 토큰을 저장하고 원래 요청을 인증 재시도 한도 안에서 다시 보냅니다. 실패하면 대기 요청도 종료하고 진행 상태를 해제합니다. 일시적 통신 실패는 자격 증명을 유지하고, 리프레시 토큰이 무효라는 응답이면 세션을 정리하고 재로그인을 요구합니다.”

위 동시성 처리와 재시도 한도는 이 질문의 상황에 대한 설계 판단입니다. 인증 외의 실패를 모두 폐기하기보다는 각 요청의 호출자에게 원인을 전달해야 합니다. 요청 본문을 다시 보낼 수 있는지와 쓰기 요청의 중복 실행 가능성도 확인해야 합니다.

## 5. [CMP-006] LaunchedEffect — 2점

**맞은 부분**
Composition 진입 시 코루틴 시작, 이탈 시 취소, 여러 키를 사용할 수 있고 키 변화가 실행을 유발한다는 방향은 맞습니다.

**빠진 부분**
같은 키로 재구성되면 기존 코루틴을 유지하고 새로 시작하지 않는다는 설명이 빠졌습니다. 키 변경은 단순히 추가 호출하는 것이 아니라 기존 코루틴을 취소하고 새 코루틴을 시작하는 과정입니다. [Compose 부수 효과 문서](https://developer.android.com/develop/ui/compose/side-effects)

**틀린 부분**
키를 생략하고 최초 한 번만 실행한다는 설명은 틀립니다. 최소 하나의 키가 필요합니다. 일정한 키를 쓰는 경우와 키 자체가 없는 경우를 구분해야 합니다. 이것은 키 이름의 암기 문제가 아니라 실행 정체성과 재시작 조건에 대한 오해입니다. [LaunchedEffect 공식 API 문서](https://developer.android.com/reference/kotlin/androidx/compose/runtime/LaunchedEffect.composable)

**면접에서는 이렇게**
“LaunchedEffect가 Composition에 들어오면 코루틴을 시작합니다. 같은 키로 재구성되면 다시 시작하지 않고, 어느 키든 바뀌면 기존 코루틴을 취소하고 새로 시작합니다. Composition에서 빠지면 취소됩니다. 해당 진입 동안 한 번 실행하려면 Unit 같은 일정한 키를 사용하지만, 빠졌다가 다시 진입하면 다시 실행됩니다.”

## 6. [JK-005] data class — 2점

**맞은 부분**
구조 분해, 새 객체 생성, 주 생성자 속성 중심의 동등성 비교를 설명했습니다. 본문 속성이 기본 동등성 비교에서 제외된다는 점과 주 생성자의 최소 한 개 val·var 제약, 다른 클래스가 상속할 수 없다는 점도 맞습니다. 지난 답변보다 비교 범위를 정확히 짚었습니다.

**빠진 부분**
자동 생성 기능에서 `hashCode`와 `toString`이 빠졌습니다. 단순히 함수 이름을 말하지 않아서가 아니라 해시 기반 컬렉션과 문자열 표현에 제공되는 기능을 설명하지 못한 부분입니다. 일반 클래스의 기본 `equals`는 참조 동일성을 비교한다는 대비, 본문 속성의 현재 값은 기본 `copy()`로 복사되지 않는다는 설명도 없습니다.

**틀린 부분**
`data class.copy()`와 리스트 자체를 별도로 복사하는 연산을 혼동했습니다. `copy()`는 새 data class 객체를 만들지만, 리스트 속성을 별도로 바꾸지 않으면 리스트 객체 자체를 공유합니다. 따라서 정수 리스트라도 복사 객체에서 `add`·`remove`·원소 대입을 하면 원본에서도 보입니다. 각 속성이 참조하는 객체를 복제하지 않는다는 뜻이 얕은 복사입니다. [Kotlin 공식 문서](https://kotlinlang.org/docs/data-classes.html)

**면접에서는 이렇게**
“data class는 주 생성자 속성을 기준으로 동등성·해시 코드·문자열 표현·구조 분해·복사 기능을 제공합니다. 기본 equals는 주 생성자 속성 값을 비교하고, 일반 클래스의 기본 equals는 같은 객체인지 비교합니다. 본문 속성은 기본 비교 대상에 포함되지 않고 copy도 그 현재 값을 옮기지 않습니다. 주 생성자에는 최소 한 개의 val·var가 필요하고 abstract·open·sealed·inner로 선언할 수 없습니다. copy는 새 객체를 만들지만 참조 속성은 공유하므로, 가변 리스트를 독립적으로 수정하려면 리스트를 따로 복사해 전달해야 합니다.”

```kotlin
data class Basket(val items: MutableList<Int>)
val original = Basket(mutableListOf(1))
val copied = original.copy()
// original.items === copied.items 는 true
copied.items.add(2)
// original.items 역시 [1, 2]
```

이번에는 용어를 기억하지 못한 문제보다 생성·보관 책임과 참조 공유, 실패 후 상태 전환을 잘못 연결한 문제가 컸습니다. 앱 번들과 Dagger의 컴파일 시점 검증에는 진전이 있었지만, 기본 동작을 짧은 예제로 확인하고 “누가 생성하고 무엇을 공유하며 언제 종료하는가”를 정확하게 설명하는 연습이 필요합니다. Baseline Profile은 별도의 기초 학습이 필요합니다.

**원문 갱신 제안**
JK-005의 주 생성자 속성 참여 범위와 val·var 제약은 이번 답변이 원문보다 정확해 `docs/AUDIT.md`의 H-05에 보충 제안을 기록했습니다. 기존 지식 원문은 수정하지 않았으며 승인 후 반영할 수 있습니다.
