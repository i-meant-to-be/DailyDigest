## 1. [AND-032] Baseline Profile — 2점

**맞은 부분**

핵심 사용자 흐름에 관련된 코드를 사전 컴파일하여 초기 실행에서 컴파일 부담을 줄인다는 방향은 맞습니다. 시작 지점과 자주 사용하는 기능을 대상으로 고르고 성능을 측정해야 한다는 설명도 적절합니다.

**빠진 부분**

실제 사용자 흐름을 자동화해 실행하며 프로필을 수집하고, 빌드에 포함하는 과정이 없습니다. 효과는 같은 기기·빌드·사용자 흐름에서 프로필 적용과 미적용 조건을 비교해야 합니다. 시작 시간뿐 아니라 스크롤 등 해당 흐름의 프레임 지연도 측정 대상으로 삼을 수 있습니다. 설치 시간 측정만으로 실행 성능 개선을 확인할 수는 없습니다.

**틀린 부분**

Baseline Profile은 컴파일러 자체나 미리 만든 기계어 바이너리가 아니라 최적화할 메서드·클래스를 지정하는 프로필입니다. 앱에는 이 프로필을 배포하고 ART가 기기에서 대상 코드를 AOT 컴파일합니다. “AOT로 컴파일한 바이너리를 앱 패키지에 포함한다”는 설명은 Android의 프로필 기반 최적화 흐름과 다릅니다. JIT도 호출할 때마다 모든 코드를 즉시 컴파일하는 방식은 아니며, 실행 중 수집한 정보를 바탕으로 자주 실행하는 코드를 컴파일합니다.

**면접에서는 이렇게**

“Baseline Profile은 시작과 핵심 사용자 흐름에서 실행되는 코드를 ART가 사전 컴파일할 수 있도록 제공하는 프로필입니다. 자동화된 테스트로 앱 시작·목록 탐색 같은 흐름을 실행해 프로필을 생성하고 릴리스 빌드에 포함합니다. 기기에서 프로필에 따라 컴파일하므로 첫 실행부터 인터프리터와 JIT 부담을 줄일 수 있습니다. 동일 조건에서 프로필 적용·미적용을 비교하는 벤치마크로 시작 시간과 프레임 지연을 확인합니다.”

근거: [Android Baseline Profile 개요](https://developer.android.com/topic/performance/baselineprofiles/overview), [생성 과정](https://developer.android.com/topic/performance/baselineprofiles/create-baselineprofile), [적용 전후 측정](https://developer.android.google.cn/topic/performance/baselineprofiles/measure-baselineprofile?hl=en).

**상태** 오답 → 불안정. 목적은 이해했지만 배포·컴파일 위치와 생성·비교 절차를 보완해야 합니다.

## 2. [SEC-007] AES-GCM의 IV 조건 — 1점

**맞은 부분**

IV가 키스트림 생성에 관여하고, 키스트림이 암호화 결과에 영향을 준다는 방향은 맞습니다.

**빠진 부분**

재사용 시 두 암호문의 XOR에서 두 평문의 XOR가 드러나고, 한 평문을 알면 다른 평문을 복원할 수 있다는 기밀성 문제를 설명하지 못했습니다. 인증 태그의 구조도 공격받아 인증 위조 위험이 생긴다는 점이 빠졌습니다.

**틀린 부분**

“하나의 키당 하나의 IV”는 키를 쓰는 내내 같은 IV를 고정한다는 뜻으로 읽히며 요구 조건과 반대입니다. 같은 키로 암호화할 때마다 IV가 고유해야 합니다. “각 IV를 같은 키에서 한 번만 사용한다”로 표현해야 합니다. IV는 비밀일 필요가 없어 암호문과 함께 저장·전송할 수 있습니다. 비밀이어야 하는 키 및 키로 생성한 키스트림과 IV를 구분해야 합니다. 답변의 “벡터 유출”은 이 구분을 설명하지 못합니다.

**면접에서는 이렇게**

“AES-GCM에서는 같은 키로 암호화하는 동안 IV가 중복되지 않아야 합니다. IV 자체는 공개해도 되지만 같은 키와 IV를 재사용하면 같은 키스트림이 생성됩니다. 그러면 암호문 사이에서 평문의 관계가 드러나고, 인증 태그도 공격받아 위조 위험이 생깁니다. 보통 96비트 IV를 사용하며, 생성 방식과 키 사용량을 관리해 중복을 방지합니다.”

근거: [NIST SP 800-38D](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=51288), 특히 8절과 부록 A.

**상태** 오답 유지. 키스트림과 IV의 역할, 고유성 조건을 다시 공부해야 합니다.

## 3. [CMP-018] Compose의 세 단계 — 2점

**맞은 부분**

Composition이 화면의 구성 요소를 결정하고, Layout이 크기를 측정하며, Drawing이 그리기를 수행한다는 큰 흐름은 맞습니다. 상태가 변해도 항상 모든 단계를 반복하지는 않는다는 결론도 맞습니다.

**빠진 부분**

Layout에는 크기 측정뿐 아니라 각 요소의 위치 배치도 포함됩니다. 어떤 단계에서 상태를 읽었는지에 따라 필요한 단계가 다시 실행된다는 원리를 설명해야 합니다.

**틀린 부분**

“재구성을 건너뛰면 Layout과 Drawing도 필요하지 않다”는 인과관계는 성립하지 않습니다. 구성은 그대로여도 위치가 변하면 배치와 그리기가 필요하고, 색상만 변하면 그리기만 필요할 수 있습니다. 구성 단계 생략과 나머지 단계 생략은 별도로 판단합니다. 또한 픽셀을 그리는 명령을 내는 단계가 Drawing이며, Layout이 최종 픽셀 데이터를 결정하는 단계는 아닙니다.

**면접에서는 이렇게**

“Composition은 어떤 UI 요소를 만들지 결정하고, Layout은 요소의 크기와 위치를 정하며, Drawing은 실제 그리기 명령을 실행합니다. Compose는 각 단계에서 읽은 상태를 추적하므로 상태 변화가 발생한 단계를 중심으로 필요한 작업만 수행할 수 있습니다. 예를 들어 그리기 단계에서만 읽는 색상이 바뀌면 구성과 배치는 생략할 수 있습니다. 재구성을 생략했다고 배치와 그리기까지 항상 생략되는 것은 아닙니다.”

근거: [Compose 단계와 단계별 상태 읽기](https://developer.android.com/develop/ui/compose/phases?hl=en).

**상태** 미학습 → 불안정. 단계 이름보다 상태 변화가 각 단계에 미치는 관계가 약점입니다.

## 4. [AND-033] 접근성 대응 — 2점

**맞은 부분**

아이콘 버튼의 설명을 접근성 정보로 제공해 화면 읽기 기능이 동작하게 해야 한다는 점은 맞습니다. 시스템 글자 크기 확대에 대응해야 한다는 방향도 맞습니다.

**빠진 부분**

입력 필드의 의미 있는 레이블, 오류·필수 입력 안내, 논리적인 초점 이동 순서가 빠졌습니다. 글자 확대에 대해서도 실제 대응을 설명해야 합니다. 글자가 잘리거나 겹치지 않도록 고정 높이를 피하고 줄바꿈·스크롤 등을 고려해야 합니다. TalkBack으로 버튼 탐색부터 입력·제출·오류 확인까지 직접 수행하고, 최대 글자 크기에서도 내용과 기능이 유지되는지 확인하는 과정이 필요합니다.

**틀린 부분**

음성 입력은 보조적인 입력 수단이며, 폼의 레이블과 상태를 읽고 조작할 수 있게 만드는 일을 대신하지 못합니다. 청각 장애인을 위한 툴팁도 핵심 대응으로 보기 어렵습니다. 소리로만 전달하던 정보를 텍스트나 시각 신호로 함께 제공해야 하며, 필수 안내를 길게 누르는 동작으로만 숨겨서는 안 됩니다.

**면접에서는 이렇게**

“아이콘 버튼에는 ‘검색’처럼 동작을 나타내는 설명을 제공하고, 장식용 아이콘은 중복해서 읽히지 않게 합니다. 폼에는 레이블·오류 상태를 제공하고 TalkBack 초점 순서와 조작 가능 여부를 확인합니다. 글자 크기를 확대해도 잘림이나 겹침 없이 입력과 제출이 가능하도록 유연한 배치를 사용합니다. 실제 기기에서 TalkBack으로 전체 흐름을 수행하고 최대 글자 크기로 확인하며, 소리로 전달하는 정보에는 시각적 안내도 제공합니다.”

근거: [Android 접근성 구현과 검증](https://developer.android.com/guide/topics/ui/accessibility/apps).

**상태** 신규 등록 → 불안정. 2점이므로 지식 원문에는 `> (미작성)`으로 등록했습니다.

## 5. [DSG-001] 오버라이드와 오버로딩 — 4점

**맞은 부분**

상속받은 메서드 구현을 바꾸는 것과 같은 이름에 다른 매개변수 조합을 제공하는 것을 정확히 구분했습니다. 예시가 각각의 정의에 대응하고, 오버라이드는 실제 객체의 타입을 기준으로 실행 시 구현이 결정되며 오버로딩은 컴파일 시 선택된다고 설명했습니다. 기초 면접에서 통과할 답입니다.

**보충할 부분**

오버로딩 선택은 인자의 컴파일 시 타입을 기준으로 한다고 명시하면 더 정확합니다. 오버라이드 대상으로는 해당 언어에서 재정의가 허용된 메서드가 전제됩니다. Kotlin의 철자 오류는 감점하지 않았습니다. 컴파일러 최적화로 특정 호출 대상을 미리 알 수 있어도 언어 의미상 동적 디스패치라는 구분은 유지됩니다.

**면접에서는 이렇게**

“오버라이드는 상속받은 메서드를 하위 타입에서 재정의하는 것이고, 오버로딩은 같은 이름의 함수를 매개변수의 타입이나 개수를 달리해 선언하는 것입니다. 오버라이드된 구현은 실제 객체 타입에 따라 실행 시 결정되고, 오버로딩은 인자의 컴파일 시 타입을 기준으로 컴파일 시 선택됩니다.”

**상태** 미학습 → 불안정 · 연속 만점 1회.

## 6. [OS-001] 프로세스와 스레드 — 3점

**맞은 부분**

자원 소유와 실행·스케줄링의 단위를 구분했습니다. 프로세스의 공유 자원과 스레드별 호출 스택을 구분했고, PCB가 커널이 관리하는 자료구조라는 점을 정확히 설명했습니다. 지난번 PCB 관련 오류는 이번 답변에서 바로잡았습니다.

**빠진 부분**

공유 자원에는 힙과 주소 공간, 열린 파일 등도 포함됩니다. 개별 실행 문맥에는 스택뿐 아니라 프로그램 카운터와 레지스터 값이 있습니다. 질문이 공유 자원과 개별 자원을 명시적으로 요구했으므로, 스택만 말한 답변은 실행 문맥의 구분을 완성하지 못해 3점입니다.

**표현을 다듬을 부분**

“프로세스는 실행하지 않는다”는 표현은 의도는 이해되지만 너무 절대적입니다. 프로세스는 실행 중인 프로그램이며, 그 안에서 CPU가 실행·스케줄링하는 흐름이 스레드라고 설명하면 됩니다. “스레드 지역 스택”은 호출 스택과 별개의 필수 스택 종류처럼 나열할 필요가 없습니다. 스레드별 호출 스택과 스레드 지역 저장소는 구분해야 합니다. 스레드별 스택도 같은 프로세스 주소 공간 안에 있으므로 메모리 접근이 서로 격리된다는 뜻은 아닙니다.

**면접에서는 이렇게**

“프로세스는 실행 중인 프로그램의 자원과 주소 공간을 묶는 단위이고, 스레드는 그 안의 실행 흐름이자 스케줄링 단위입니다. 같은 프로세스의 스레드는 코드·전역 데이터·힙·열린 파일 등을 공유하지만 각자 스택과 프로그램 카운터·레지스터 문맥을 가집니다. PCB는 커널이 프로세스 상태와 자원 등을 관리하기 위한 자료구조이며 사용자 프로그램의 데이터 영역과 구분됩니다.”

**상태** 불안정 유지. 이전 오류는 해결했으므로 이번 약점은 공유 힙과 개별 실행 문맥의 누락으로 갱신했습니다.

---

오버라이드·오버로딩은 정의·예시·결정 시점이 연결되어 설명이 완결됐습니다. 반면 실무 문항에서는 큰 목적은 알지만 조건과 처리 과정이 빠지거나 뒤바뀌었습니다. AES-GCM과 Compose는 개념 관계를 다시 공부하고, Baseline Profile과 접근성은 실제 준비·검증 절차까지 말하는 연습이 필요합니다.

OS-001의 기존 원문에는 이번 답변에서 정확히 설명한 PCB 관리 주체와 스레드별 스택 구분이 없습니다. `docs/AUDIT.md`의 I-01에 보완 제안을 기록했으며, 기존 원문은 수정하지 않았습니다.
