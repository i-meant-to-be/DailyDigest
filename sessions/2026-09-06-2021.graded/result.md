## 1. [AND-022] Activity 생명주기 — 2점

**맞은 부분**

다른 Activity에 완전히 가려질 때 `onPause → onStop`, 정상적으로 종료할 때 `onPause → onStop → onDestroy`를 제시했습니다. 지난번과 달리 콜백 이름과 종료 흐름 일부를 알고 있습니다.

**빠진 부분**

최초 실행의 `onCreate → onStart → onResume`, 중지 상태에서 복귀하는 `onRestart → onStart → onResume`가 없습니다. 일부만 가려져 일시정지된 경우와 완전히 가려져 중지된 경우의 차이도 설명하지 않았습니다. 질문의 시작·복귀·종료 중 종료만 완결되어 2점입니다.

**틀린 부분**

`onPause → onStop`은 가려지는 과정이지 돌아오는 과정까지 포함한 순서가 아닙니다. 뒤로 가기는 파괴의 한 원인일 뿐이며, `finish()`나 구성 변경에 따른 재생성에서도 파괴될 수 있습니다. 프로세스를 강제로 종료할 때는 `onDestroy` 호출을 보장하지 않습니다.

**면접에서는 이렇게**

“일반적인 단일 화면 전환에서 처음에는 `onCreate → onStart → onResume`가 호출됩니다. 다른 Activity가 완전히 덮으면 `onPause → onStop`, 살아 있는 기존 Activity로 돌아오면 `onRestart → onStart → onResume`입니다. 일부가 보이지만 상호작용을 잃어 일시정지되면 `onPause`까지이고, 다시 활성화되면 `onResume`입니다. 문제에서 가정한 정상 종료는 `onPause → onStop → onDestroy`입니다. 파괴는 종료 외에 구성 변경에서도 일어나며, 프로세스 종료에는 종료 콜백이 보장되지 않습니다.” [Android 생명주기 문서](https://developer.android.com/guide/components/activities/activity-lifecycle)

일부를 가린다고 항상 일시정지하는 것은 아닙니다. 같은 Activity의 Dialog나 다중 창은 별도 조건을 고려해야 하며, 위 답은 다른 Activity로 전환하는 일반적인 상황을 전제로 합니다.

## 2. [ALG-003] 퀵 정렬의 최악 조건과 피벗 — 2점

**맞은 부분**

최악 시간 복잡도를 `O(n²)`로 수정했고, 균형 잡힌 피벗이 유리하다는 방향과 세 값의 중앙값·Median of Medians라는 대안을 제시했습니다. Median of Medians를 올바르게 적용한 퀵 정렬은 최악 `O(n log n)`을 보장할 수 있으므로, introsort를 말하지 않았다는 이유로 감점하지 않았습니다.

**빠진 부분**

유리한 것은 피벗의 배열상 위치 자체보다 **값의 순위가 중앙에 가까워 분할 크기가 균형을 이루는 것**입니다. 매 단계의 작업량이 `n, n-1, n-2, …`로 줄어드는 합을 설명해야 제곱 복잡도의 근거가 됩니다. 무작위 선택이나 세 값의 중앙값은 나쁜 분할 가능성을 줄이지만 최악 복잡도를 없애지는 않습니다.

**틀린 부분**

내림차순 배열의 맨 오른쪽은 최댓값이 아니라 최솟값입니다. 피벗을 기준으로 분할한다고 극단값이 중앙에 놓이는 것도 아닙니다. 예를 들어 `[5, 4, 3, 2, 1]`에서 피벗 1을 선택하면 작은 쪽은 비고 큰 쪽에 4개가 남습니다. 이후에도 극단값이 선택되면 현재 부분 배열의 대부분이 다음 재귀 호출로 넘어갑니다.

Median of Medians는 배열을 **5개 그룹으로** 나누는 것이 아니라 **원소 5개씩 약 n/5개 그룹으로** 나눕니다. 각 그룹의 중앙값을 모은 뒤 그 중앙값들의 실제 중앙값을 재귀적인 선택 알고리즘으로 구합니다. 단순히 중앙값을 몇 번 모으는 설명만으로는 선형 선택 시간의 보장이 성립하지 않습니다.

**면접에서는 이렇게**

“서로 다른 값이 정렬된 배열에서 매번 첫 원소나 마지막 원소를 피벗으로 고르면 0개와 n-1개로 갈리는 최악 분할이 반복될 수 있습니다. 분할 비용의 합이 n+(n-1)+…이므로 `O(n²)`입니다. 무작위 피벗이나 세 후보의 중앙값으로 위험을 낮출 수 있지만 최악을 없애지는 못합니다. 최악까지 보장하려면 Median of Medians로 선형 시간에 균형 있는 피벗을 선택해 퀵 정렬을 구성할 수 있습니다. 다만 피벗을 고르는 추가 비용이 있습니다.” [CMU 알고리즘 강의 자료](https://www.cs.cmu.edu/afs/cs/academic/class/15451-s06/www/lectures/lects1-5.pdf)

## 3. [DI-005] Singleton 생성과 수명 — 1점

**맞은 부분**

Activity보다 긴 애플리케이션 범위에서 인스턴스를 공유한다는 방향은 맞습니다.

**빠진 부분**

컴포넌트가 만들어지는 시점과 그 안의 개별 객체를 최초로 요청하는 시점, 참조를 보유하는 기간과 실제 메모리 회수를 구분하지 않았습니다. 이 구분이 질문의 핵심입니다.

**틀린 부분**

`@Singleton`은 앱 시작 때 모든 객체를 즉시 생성하라는 표시가 아닙니다. 주입 과정 등에서 해당 바인딩이 처음 요청될 때 만들고 같은 컴포넌트에서 재사용합니다. 앱 시작 중 요청된다면 그때 생성되지만, 한 번도 요청하지 않으면 생성되지 않을 수 있습니다. “모든 코드”도 부정확합니다. 같은 Hilt 컴포넌트 계층을 통해 같은 바인딩을 요청하는 범위이며, 직접 생성한 객체나 다른 프로세스까지 하나로 합치지 않습니다.

**면접에서는 이렇게**

“`@Singleton` 바인딩은 처음 필요해졌을 때 생성되고, 같은 `SingletonComponent`와 하위 컴포넌트에서 공유됩니다. 컴포넌트는 보통 애플리케이션 프로세스가 살아 있는 동안 인스턴스를 유지하므로 Activity 종료만으로 해제되지 않습니다. 일반적으로 모든 강한 참조가 사라져야 GC 대상이 되며, 그 순간에 바로 회수된다는 보장은 없습니다. 앱 프로세스가 종료되면 OS가 프로세스 메모리를 회수합니다.” [Hilt 컴포넌트와 수명](https://dagger.dev/hilt/components.html), [Dagger 바인딩과 지연 요청](https://dagger.dev/dev-guide/basic-usage)

## 4. [DI-010] Assisted Injection — 0점

**맞은 부분**

평가할 수 있는 개념 설명이 없습니다.

**빠진 부분**

DI가 제공하는 의존성과 실행 중 호출자가 정하는 값을 조합하는 목적, 생성자와 팩터리의 역할이 모두 빠졌습니다. 용어 표현의 문제가 아니라 개념 학습이 필요한 응답입니다.

**틀린 부분**

잘못된 설명을 하지는 않았지만, “잘 모름”만으로는 면접 질문에 답한 것으로 평가할 수 없습니다.

**면접에서는 이렇게**

“저장소처럼 DI 그래프에서 구하는 값과 화면 식별자처럼 생성 시 호출자가 넘기는 값을 함께 써서 객체를 만들 때 Assisted Injection을 씁니다. 생성자에는 `@AssistedInject`, 식별자에는 `@Assisted`를 붙입니다. `@AssistedFactory`의 생성 메서드는 식별자를 인자로 받고, Dagger가 생성한 팩터리가 저장소와 합쳐 객체를 만듭니다. 사용하는 쪽은 대상 객체 대신 팩터리를 주입받고 `create(id)`를 호출합니다. 모든 인자를 DI로 해결할 수 있으면 일반 생성자 주입으로 충분합니다.” [Dagger Assisted Injection 문서](https://dagger.dev/dev-guide/assisted-injection.html)

## 5. [CMP-003] State Hoisting — 3점

**맞은 부분**

상태 소유자를 상위로 이동하고 하위에는 값과 변경 콜백을 전달한다는 핵심이 정확합니다. ViewModel 자체를 넘기지 않는 이유와 공용 UI의 재사용·테스트 이점도 설명했습니다.

**빠진 부분**

단순히 “두 하위를 포함하는 상위”보다, 상태를 읽는 모든 Composable의 최소 공통 조상과 상태를 변경하는 위치를 고려해 소유자를 정한다고 말하면 선택 기준이 명확해집니다. 모든 상태를 무조건 올릴 필요는 없습니다.

**틀린 부분**

“정적 렌더링”은 부정확합니다. 상태를 소유하지 않는 Composable도 입력이 달라지면 재구성되어 화면이 바뀌고, 콜백으로 사용자 동작을 전달합니다. 입력에 따라 표현이 결정된다는 취지는 맞지만, 정적이라는 말을 반복해 상태 소유 여부와 UI 갱신 여부를 혼동하게 합니다. 핵심 설계는 맞아 3점이며, 면접에서는 이 표현을 고쳐야 합니다.

**면접에서는 이렇게**

“State Hoisting은 상태를 공통 소유자로 옮겨 하위에는 현재 값과 변경 요청 콜백을 전달하는 패턴입니다. 두 하위가 공유한다면 상태를 읽는 최소 공통 조상을 기준으로 변경 위치까지 고려해 소유자를 정합니다. 하위는 해당 상태를 직접 소유하지 않지만 입력이 바뀌면 UI를 갱신하고 사용자 동작은 콜백으로 올립니다. 그래서 화면별 ViewModel에 묶이지 않고, 값과 콜백을 넣어 재사용하거나 표시·동작을 테스트하기 쉽습니다.” [Compose 상태 문서](https://developer.android.com/develop/ui/compose/state)

## 6. [OS-001] 프로세스·스레드와 PCB — 2점

**맞은 부분**

프로세스를 자원 소유 단위, 스레드를 스케줄링·실행 단위로 구분했습니다. 이전에 반대로 설명했던 부분은 바로잡혔습니다. 코드·전역 데이터의 공유와 스레드별 스택도 맞습니다.

**빠진 부분**

공유 자원에는 힙과 열린 파일 등의 자원도 있고, 스레드별 실행 문맥에는 프로그램 카운터와 레지스터가 있습니다. 지역 변수는 흔히 스택에 놓이지만 레지스터 등에 배치될 수도 있어 별도의 고정 “지역 변수 공간”으로 단정하지 않는 편이 정확합니다.

**틀린 부분**

일반적인 커널 스레드의 CPU 실행 대상을 고르는 주체는 프로세스가 아니라 OS 스케줄러입니다. 애플리케이션이 작업을 분배하는 것과 CPU 스케줄링은 구분해야 합니다. PCB도 주소 공간을 가리키는 포인터 하나가 아니라, OS가 프로세스 상태·식별자·스케줄링·메모리 관리·자원 정보를 보관하는 자료구조입니다. 주소 공간 관련 정보를 포함할 수 있지만 PCB 자체와 주소 공간은 다릅니다. 이 부분은 지난 지적이 아직 해결되지 않았습니다.

**면접에서는 이렇게**

“프로세스는 실행 중인 프로그램의 자원 소유 단위이고, 스레드는 그 안의 실행 흐름이자 일반적으로 OS가 스케줄링하는 단위입니다. 같은 프로세스의 스레드는 코드·전역 데이터·힙 등을 공유하고 스택과 레지스터·프로그램 카운터는 각각 갖습니다. PCB는 커널이 프로세스를 관리하는 정보를 담는 자료구조입니다. 프로세스 주소 공간은 코드·데이터·힙·스택 등이 배치되는 가상 주소의 범위로, PCB와는 역할과 위치가 다릅니다.” [UIC 운영체제 강의: 프로세스와 PCB](https://www.cs.uic.edu/~jbell/CourseNotes/OperatingSystems/3_Processes.html)

---

이번에는 용어를 회상하는 수준은 일부 개선됐지만, 퀵 정렬의 분할 과정·객체 생성 시점·PCB처럼 실제 동작과 자료구조를 설명할 때 개념 오류가 남았습니다. Compose는 새 개념을 공부하기보다 “상태를 소유하지 않아도 입력에 따라 UI는 바뀐다”는 식으로 표현을 다듬는 연습이 필요하고, DI 두 문항은 개념 학습이 먼저입니다.
