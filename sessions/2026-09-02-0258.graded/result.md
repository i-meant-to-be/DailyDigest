## 1. [AND-022] Activity 생명주기 콜백 순서 — 1점

**맞은 부분**
"생성 → 시작 → 가려짐 → 종료"라는 큰 흐름의 방향은 잡으셨습니다.

**틀린 부분**
"다른 화면에 가려지는 경우 액티비티 파괴 함수 호출"이 결정적으로 틀렸습니다. 가려지는 것과 파괴되는 것은 전혀 다른 사건입니다. 다른 Activity가 위에 올라오면 `onPause()` → `onStop()`까지만 가고, 인스턴스는 살아 있습니다. `onDestroy()`는 `finish()`가 호출되거나 시스템이 프로세스를 회수할 때만 불립니다. 이 구분이 안 되면 "화면 복귀 시 상태 복원", "ViewModel이 왜 필요한가" 같은 후속 질문이 전부 무너집니다.

**빠진 부분**
콜백 이름을 하나도 말씀하지 못했습니다. 기초 문항에서 이건 치명적입니다. 정답은 이렇습니다.

- 최초 생성·표시: `onCreate()` → `onStart()` → `onResume()`
- 다른 화면에 가려짐: `onPause()` → `onStop()`
- 돌아옴: `onRestart()` → `onStart()` → `onResume()`
- 종료: `onPause()` → `onStop()` → `onDestroy()`

**면접에서는 이렇게**
"콜백은 세 쌍으로 대칭입니다. `onCreate`/`onDestroy`가 인스턴스의 수명, `onStart`/`onStop`이 화면에 보이는지 여부, `onResume`/`onPause`가 포커스를 가진 상호작용 가능 상태입니다." — 순서를 외운 목록으로 나열하는 것보다 이 대칭 구조로 말하면 "그럼 다이얼로그가 뜨면 어디까지 가나요?"(`onPause`까지) 같은 변형 질문에 바로 답할 수 있습니다.

**상태** 미학습 → 오답 (1점)

## 2. [AND-028] Navigation 백스택 관리 — 3점

**맞은 부분**
LIFO 스택 구조, `startDestination`이 바닥에 깔린다는 점, push/pop 동작을 정확히 설명하셨습니다. 로그인 화면 처리에서 "출발지를 목적지로 대체한다"는 것도 동작 자체는 맞게 이해하고 계십니다.

**빠진 부분**
API 이름이 하나도 안 나왔습니다. 이건 "몰라서"가 아니라 "써 봤는데 이름을 못 꺼내는" 유형으로 보입니다 — 면접에서 가장 아깝게 감점되는 지점입니다. 필요한 단어는 `NavController`, `popUpTo`, `inclusive`, `launchSingleTop` 넷입니다. 특히 `popUpTo`와 `inclusive`는 한 세트로 말해야 합니다. `popUpTo("login")`만 하면 login은 스택에 남고, `inclusive = true`를 붙여야 login 자신까지 제거됩니다.

`launchSingleTop`도 실무 문항이라면 나왔어야 합니다. 하단 탭이나 버튼 연타로 같은 화면이 여러 장 쌓이는 문제를 막는 옵션입니다.

**면접에서는 이렇게**
"NavController가 목적지를 LIFO 스택으로 관리하고, `navigate()`에 NavOptions를 얹어 스택을 조작합니다. 로그인처럼 되돌아오면 안 되는 화면은 `navigate("home") { popUpTo("login") { inclusive = true } }`로 이동과 동시에 걷어냅니다. 인증 흐름이 여러 화면이면 중첩 그래프로 묶어서 그래프 단위로 popUpTo를 겁니다." — 마지막 문장이 "써 봤다"와 "설계해 봤다"를 가르는 지점입니다.

**상태** 신규 등록(AND-028) → 불안정 (3점)

## 3. [CMP-001] Recomposition과 `remember` — 2점

**맞은 부분**
"상태가 바뀌면 화면이 다시 그려지는 과정"이라는 정의, `remember`로 감싼 값이 Recomposition 사이에 유지된다는 점은 맞습니다.

**틀린 부분**
"Composition, Recomposition, Decomposition의 3단계"— **Decomposition이라는 단계는 Compose에 없습니다.** 실제 생애주기는 Composition(진입) → Recomposition(0회 이상) → Disposal(이탈)입니다. 없는 용어를 확신 있게 말하면 면접관은 나머지 답까지 의심합니다.

"원칙적으로 Recomposition 동안에는 모든 상태가 초기화됨"도 부정확합니다. 초기화되는 게 아니라, Composable 함수가 **다시 실행되면서 지역 변수가 새로 만들어지는** 것입니다. 결과는 비슷해 보여도 원인이 다르고, 면접관은 이 인과를 묻습니다.

**빠진 부분**
가장 중요한 게 빠졌습니다 — **`remember`는 Recomposition을 유발하지 않습니다.** 보관만 합니다. Recomposition을 일으키는 것은 `mutableStateOf` 같은 관찰 가능한 상태의 변경입니다. 이 역할 분리를 말하지 못하면 "그럼 `remember { 0 }`을 바꾸면 화면이 갱신되나요?" 한 방에 막힙니다. 참고로 `knowledge/platform/compose.md`에 적어 두신 원문에는 이 구분이 정확히 들어 있습니다. **아는데 못 꺼낸 케이스입니다.**

**면접에서는 이렇게**
"`remember`는 값을 잃지 않게 해 주는 장치이고, `MutableState`는 값이 바뀌었음을 알리는 장치입니다. 역할이 다르기 때문에 보통 `remember { mutableStateOf(...) }`로 둘을 겹쳐 씁니다." — 이 두 문장이면 4점입니다.

**상태** 미학습 → 불안정 (2점)

## 4. [DI-001] 의존성 주입의 정의와 중요성 — 3점

**맞은 부분**
정의가 정확합니다. "생성 책임이 사라진다 → 결합도가 낮아진다 → 클래스는 사용법만 알면 된다"로 이어지는 인과도 잘 잡으셨습니다. 이번 세션에서 가장 구조가 좋은 답입니다.

**빠진 부분**
**테스트 용이성**이 없습니다. DI를 물었을 때 면접관이 듣고 싶어하는 실질적 이득 1번이 이겁니다. 생성 책임이 밖으로 나갔다는 건 곧 **테스트에서 가짜 구현(Fake/Mock)을 끼워 넣을 수 있다**는 뜻인데, 이 한 걸음을 더 가지 않으셨습니다.

"사용법만 알면 된다"도 절반만 말한 것입니다. 정확히는 **구현이 아니라 인터페이스에 의존하게 된다**는 뜻이고, 그래서 구현체를 갈아 끼울 수 있는 겁니다. 이 문장이 있어야 다음 질문(왜 인터페이스를 두나요, `@Binds`는 왜 쓰나요)으로 이어집니다.

기초 문항이라 4점 기준이 엄격합니다. 정의는 맞지만 이득이 하나 빠져서 3점입니다.

**면접에서는 이렇게**
"객체가 필요한 의존성을 직접 생성하지 않고 외부에서 주입받는 방식입니다. 구현이 아니라 인터페이스에 의존하게 되므로 결합도가 낮아지고, 실제 얻는 이득은 두 가지입니다 — 구현체 교체가 쉬워지는 것, 그리고 테스트에서 가짜 구현을 주입할 수 있게 되는 것입니다." — 정의 한 문장 + 이득 두 개, 이 구조로 고정해 두세요.

**상태** 미학습 → 불안정 (3점)

## 5. [JK-001] 중위 표기 함수 — 2점

**맞은 부분**
"온점 없이 `a add b` 형태로 쓰는 함수"라는 형태와 `infix` 키워드 필수 조건은 맞습니다.

**틀린 부분**
**"피연산자는 꼭 2개"가 틀렸습니다.** 조건은 **매개변수가 정확히 1개**여야 한다는 것입니다. `a add b`에서 `a`는 매개변수가 아니라 **리시버(수신 객체)**입니다. 눈에 보이는 항이 2개라서 헷갈리신 것 같은데, 시그니처상으로는 리시버 1 + 파라미터 1입니다. 이 구분이 안 되면 "그럼 확장 함수의 리시버는 뭔가요"에서 막힙니다.

"두 연산자 중간에 오는 함수"에서 **연산자**도 **피연산자**의 오용입니다. 사소해 보여도 면접에서는 용어를 정확히 안 쓰는 사람으로 기록됩니다.

**빠진 부분**
세 번째 조건 — **멤버 함수이거나 확장 함수여야 한다**(최상위 함수는 안 됨)가 없습니다. 조건 세 개 중 하나만 맞으셨습니다. 추가로 `vararg`나 기본값 매개변수는 쓸 수 없다는 것, 중위 호출은 산술 연산자보다 우선순위가 낮다는 점까지 말하면 실무 문항에서 4점입니다.

**면접에서는 이렇게**
"`infix` 키워드를 붙이면 점과 괄호 없이 `a to b`처럼 호출할 수 있습니다. 조건은 세 가지로 — 멤버 함수나 확장 함수여야 하고, 매개변수가 정확히 하나여야 하고, 그 매개변수에 `vararg`나 기본값이 없어야 합니다. 표준 라이브러리의 `to`나 `until`이 대표적인 예입니다." — 조건은 항상 개수를 먼저 말하고 세는 게 안전합니다.

**상태** 미학습 → 불안정 (2점)

## 6. [ALG-003] 퀵 정렬 최악 복잡도 — 1점

**맞은 부분**
"이미 정렬된 배열일 때"는 조건부로 맞습니다. 다만 이건 **첫 원소나 마지막 원소를 피벗으로 고를 때**만 성립합니다. 그 전제를 빼고 말하면 절반만 맞은 답입니다.

**틀린 부분**
**최악 시간 복잡도는 O(n)이 아니라 O(n²)입니다.** 이건 그냥 틀린 게 아니라 위험한 오답입니다. O(n)은 평균 O(n log n)보다도 빠른 값이라, 최악이 평균보다 좋다는 모순이 됩니다. 면접에서 이렇게 답하면 알고리즘 파트는 그 자리에서 접힙니다.

왜 O(n²)인지: 피벗이 매번 최솟값이나 최댓값으로 잡히면 분할이 n-1과 0으로 쪼개져, 재귀 깊이가 n이 되고 각 단계에서 n번 비교하므로 n × n입니다. 덤으로 재귀 깊이도 O(n)이라 스택 오버플로 위험이 붙습니다.

"실무에서는 정렬된 데이터에 안 쓴다"는 회피책이 아닙니다. 입력 분포를 미리 알 수 없는 게 보통이고, 무엇보다 **퀵 정렬 쪽을 고치면 되는 문제**입니다. 실제 해법은 세 가지입니다.

- **랜덤 피벗** — 특정 입력이 최악을 유발할 확률을 없앰
- **median-of-three** — 첫·중간·마지막 값의 중앙값을 피벗으로. 정렬된 입력에 특히 효과적
- **introsort** — 재귀 깊이가 임계치를 넘으면 힙 정렬로 전환해 최악을 O(n log n)으로 보장. C++ `std::sort`가 쓰는 방식

**면접에서는 이렇게**
"평균 O(n log n)이지만 피벗이 계속 한쪽 끝으로 잡히면 분할이 n-1 대 0이 되어 O(n²)이 됩니다. 첫 원소를 피벗으로 쓰면 정렬된 입력이 바로 이 경우입니다. 그래서 실무 구현은 랜덤 피벗이나 median-of-three로 확률을 낮추고, `std::sort`처럼 재귀 깊이를 감시해 힙 정렬로 전환하는 introsort로 최악을 보장합니다." — 복잡도는 반드시 **왜 그 값인지**(분할이 어떻게 쪼개지는지)와 함께 말하세요. 숫자만 외운 답은 한 번 더 물으면 무너집니다.

**상태** 미학습 → 오답 (1점)
