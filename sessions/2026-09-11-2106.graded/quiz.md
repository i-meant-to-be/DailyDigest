## 2. [SEC-004] 네이티브 앱이 OAuth 2.0 인가 코드 흐름으로 로그인한다고 할 때, 참여 주체와 코드·토큰이 오가는 과정을 PKCE를 포함해 단계별로 설명해 주세요.

`platform/security` · 실무 · 답을 적어 둔 적 없는 문항

### 내 답변

참여 주체는 사용자, 앱, 서버, 인증 서비스 제공자.

PKCE는 뭔지 모르기 때문에 일단 아는 선에서 얘기하겠음.

1. 사용자가 앱에서 로그인 시도.
2. 앱은 인증 서비스 제공자의 로그인 화면을 열어줌. 이 때, 인증 서비스 제공자가 이 앱을 신뢰할 수 있음을 알리기 위해 API 키 등을 로그인 요청 시 함께 보내줘야 함.
3. 로그인이 성공하면, 인증 서비스 제공자는 앱에 인증 서비스 제공자 액세스 토큰을 제공.
4. 앱은 받은 인증 서비스 제공자 액세스 토큰을 서버에 전달.
5. 서버는 받은 인증 서비스 제공자 액세스 토큰을 다시 인증 서비스 제공자에게 전달. 마찬가지로 이 때에도 API 키 등으로 증명 필요.
6. 인증 서비스 제공자는 받은 액세스 토큰을 보고 '이거 내가 보낸 거 맞구나'를 확인하고 나서 서버에 이 액세스 토큰 유효하다고 응답.
7. 서버는 인증이 완료되었음을 확인하고, 서버에서 사용할 서비스 액세스 토큰과 서비스 리프레시 토큰을 발급하여 앱에 전송
8. 앱은 받은 서비스 액세스 토큰과 서비스 리프레스 토큰을 암호화하여 저장 후 로그인에 사용.

## 3. [신규] Android 앱에서 웹 URL 딥링크를 안전하게 받아 올바른 화면으로 연결하려면 어떻게 구성하겠습니까? 일반 딥링크와 검증된 앱 링크의 차이, 라우팅과 입력 검증, 백 스택 처리까지 설명해 주세요.

`platform/android` · 실무 · 주제 대장 공백 — 지식 파일에 아직 없는 주제

### 내 답변

일반 딥링크와 검증된 앱 링크의 차이는 잘 모르겠음.

라우팅의 경우 웹 앱에서 하는 것처럼 기능과 요구에 따라 라우팅 테이블을 잘 구성하고, 해당 라우팅 테이블에서 불가능한 URL이 입력될 경우 오류를 반환할 수 있게 검증 과정을 추가해야 함.

입력, 특히 패스 파라미터와 쿼리 파라미터 등이 주어질 경우에도 해당 파라미터들이 PRD 또는 기획안에서 유효한 범위 내에 있는지 확인하고, 유효하지 않다면 오류를 반환하도록 구현.

그리고 사용자가 의도되지 않은 화면으로 이동하지 않도록 하면서 동시에 사용자는 앱을 켰을 때 홈 화면이 제일 먼저 보일 것을 고려하여 기본적으로 요구되는 화면을 미리 백 스택에 푸시해주면 좋음.

## 4. [JK-004] Java와 Kotlin의 공통 실행 기반과 상호 운용성을 먼저 설명하고, 널 안전성·비동기 처리·상용구 코드 측면의 차이를 비교해 주세요.

`lang/java-kotlin` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

Java와 Kotlin 모두 JVM 위에서 동작한다. Java는 그대로 바이트코드로, Kotlin은 먼저 Java로 컴파일되고 나서 바이트코드로 컴파일된다.

그래서 둘 다 결론적으로는 JVM 뒤에서 돌아가고, Kotlin이 Java를 한 번 거치는 만큼 Java 라이브러리도 그대로 사용 가능하다.

다만 둘 사이 차이점이 있다면 Java는 기본적으로 모든 자료형이 Nullable하지만, Kotlin은 Non-nullable하다는 것. 그래서 Kotlin에서는 Nullable한 자료형을 선언하려면 타입 뒤에 `?`를 붙여야 한다.

비동기 처리는 Java의 경우 스레드를 직접 사용하지만, Kotlin은 Java의 스레드를 베이스에 깔고 디스패칭하는 Coroutines로 비동기 처리를 진행한다.

## 5. [NET-001] TCP와 UDP가 어느 계층의 프로토콜인지 밝힌 뒤, 연결 방식과 재전송·순서 보장·흐름 제어·혼잡 제어의 차이를 설명해 주세요. 각 프로토콜의 용도와 QUIC·HTTP/3가 UDP를 사용하는 이유도 덧붙여 주세요.

`cs/network` · 기초 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-04) · 지난 지적: 전송 계층 규정과 신뢰성 메커니즘의 정확한 용어가 빠졌고, QUIC·HTTP/3 동향을 반대로 설명함

### 내 답변

둘 다 4계층이다.

설명에 앞서 둘의 철학을 먼저 알아야 한다. TCP는 신뢰성 있는 통신을 목적으로 하고, UDP는 빠른 전송과 개발자에게 통제권 부여를 목적으로 한다.

연결 방식은 TCP는 연결 통신, UDP는 비연결 통신을 지향한다. 전자는 연결이 수립되지 않으면 통신이 안 되지만, 후자는 애초에 연결을 수립할 필요가 없다.

재전송, 순서 보장, 흐름 제어, 혼잡 제어 모두 신뢰성을 중시하는 TCP에서는 보장된다. UDP에서는 보장되지 않는다. 만약 필요하다면, UDP 위에 있는 앱 계층에서 개발자가 직접 구현해야 한다.

최근 통신 프로토콜은 QUIC과 HTTP/3로 이어지고 있는데 이는 UDP 위에서 구현된다. 왜냐하면 TCP는 신뢰성 있는 통신을 목적으로 하기 때문에 다양한 유틸리티를 제공하지만, 연결 수립도 필요 없고 보내고 나면 신경 쓰지도 않는 가벼운 UDP보다 통신 속도가 느리기 때문이다. 그래서 QUIC은 UDP 위에 구현하되, 개발자가 필요에 따라 추가할 기능을 포함할지 말지를 결정할 수 있는 형태로 구현되어 있다.

## 6. [DI-001] 의존성 주입을 객체 생성과 전달 책임의 관점에서 정의하고, 인터페이스 분리 및 저장소 패턴과는 어떻게 다른지 설명해 주세요. 결합도와 테스트 가능성에는 어떤 영향을 줍니까?

`platform/di` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-06) · 지난 지적: 의존성 주입과 인터페이스 분리를 같은 개념처럼 설명했고, 저장소 패턴을 단순한 인터페이스·구현체 분리로 정의함

### 내 답변

DI는 특정 클래스가 필요로 하는 객체를 해당 객체 생성자 안에서 생성하는 게 아니라 외부에서 만들어서 넣어주는 것을 의미.

기존 방식대로라면 해당 클래스 고유 책임에 더해 외부 객체 생성 및 관리에 대한 책임도 졌지만, DI를 사용하면 외부 객체 관리 책임이 밖으로 빠지기 때문에, 해당 클래스는 그 고유의 책임에만 집중할 수 있게 됨.

인터페이스 분리와 저장소 패턴과는 다를 수 있는 것이, DI는 단순히 객체 생성에 대한 책임만 밖으로 돌리는 것이고 해당 객체와 그걸 사용하는 클래스가 어떻게 연결되는지에 관한 내용은 정하지 않기 때문.

다만 결합도를 낮추고 DI의 고유 장점인 책임 분리 및 명확화를 위해 보통 인터페이스를 같이 사용하기는 함. 특정 클래스가 필요로 하는 객체를 실제 구현체가 아니라 인터페이스로 넣어주면 필요에 따라 해당 인터페이스의 구현체를 바꿔 끼울 수 있기 때문.

결합도는 낮아짐. 왜냐하면 DI는 위에서 말했듯이 객체 생성 책임과 해당 객체를 사용하는 클래스의 고유 책임을 명확히 분리해주기 때문. 더 나아가 인터페이스까지 적용할 경우, 클래스는 오직 공개된 API만 알고 내부 구현은 전혀 몰라도 되기 때문에 결합도가 훨씬 더 낮아지는 이점이 있음. 테스트 가능성 역시 높아지는데 외부에서 객체를 주입해주기 때문에 인터페이스를 같이 사용할 경우 가짜 구현체(mocked implementation)를 대신 넣어줌으로써 테스트를 더 쉽게 할 수 있음.
