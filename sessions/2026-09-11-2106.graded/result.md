## 1. [CMP-024] Compose 성능 측정과 병목 추적 — 2점

**맞은 부분**

재구성 빈도와 한 프레임을 만드는 시간을 서로 다른 병목 후보로 보았고, 디버그 빌드가 아닌 출시 환경에 가까운 빌드에서 측정해야 한다는 방향도 맞았습니다.

**빠진 부분**

사용자가 체감하는 문제의 기준선은 재구성 횟수 자체가 아니라 프레임 마감 시한 초과와 끊김입니다. 실제 기기에서 반복 가능한 핵심 사용자 흐름을 정하고 `Macrobenchmark`의 `FrameTimingMetric`으로 `frameOverrunMs`와 `frameDurationCpuMs` 분포를 측정한다는 절차가 필요합니다. 이후 Android Studio 시스템 추적 또는 Perfetto에서 느린 프레임의 UI 스레드·`RenderThread`·Compose 구간을 확인하고, 필요하면 재구성 추적이나 사용자 정의 추적 구간으로 범위를 좁힌 뒤 같은 조건에서 개선 전후를 반복 측정해야 합니다.

**부정확한 부분**

“Android Studio의 여러 도구”라고만 하면 어떤 지표로 증상을 확인하고 어떤 도구로 원인을 찾는지 구분되지 않습니다. 재구성이 많아도 프레임 마감 시한을 지키면 끊김의 직접 원인이 아닐 수 있습니다.

**면접에서는 이렇게**

“먼저 출시 빌드에 가까운 `profileable`·`non-debuggable` 빌드를 실제 기기에서 실행하고, 끊김이 재현되는 사용자 흐름을 고정합니다. `Macrobenchmark`와 `FrameTimingMetric`으로 프레임 시간과 jank의 기준선을 반복 측정한 뒤, 시스템 추적에서 느린 프레임의 UI 스레드와 `RenderThread`, Compose 구간을 확인합니다. 그 결과에 따라 과도한 재구성, 메인 스레드 작업, 레이아웃·그리기 비용 중 원인을 좁히고 수정 전후를 같은 조건에서 다시 측정합니다.”

**상태** 오답 → 불안정 (2점)

## 2. [SEC-004] OAuth 2.0 인가 코드 흐름과 PKCE — 1점

**맞은 부분**

사용자, 앱, 자체 서버, 외부 인가 서버라는 참여 주체를 대략 구분했고, 외부 로그인 결과를 자체 서비스 토큰으로 바꾸는 실제 서비스 구성을 떠올린 점은 맞습니다.

**빠진 부분**

질문의 핵심인 인가 코드와 PKCE 흐름이 빠졌습니다. 앱은 무작위 `code_verifier`와 그 해시인 `code_challenge`를 만들고, 외부 브라우저의 인가 요청에 `client_id`, 정확히 등록된 `redirect_uri`, `state`, `code_challenge` 등을 보냅니다. 인가 서버는 리다이렉트로 짧게 쓰는 인가 코드를 돌려주고, 앱 또는 설계된 백엔드가 코드와 원래의 `code_verifier`를 토큰 엔드포인트에 제출해야 액세스 토큰을 받습니다. `state` 검증, 외부 사용자 에이전트 사용, 토큰의 자원 서버 사용도 설명해야 합니다.

**틀린 부분**

인가 코드 흐름에서는 로그인 직후 앱으로 액세스 토큰이 직접 돌아오는 것이 아니라 인가 코드가 돌아옵니다. 또한 배포된 네이티브 앱에 넣은 고정 API 키나 클라이언트 비밀은 추출할 수 있으므로 앱의 신원을 증명하는 비밀로 취급할 수 없습니다. 액세스 토큰을 인가 서버에 다시 보내 “내가 발급했는지” 확인하는 단계도 표준 인가 코드 흐름 자체는 아닙니다.

**면접에서는 이렇게**

“네이티브 앱은 비밀을 안전하게 보관할 수 없는 공개 클라이언트이므로 외부 브라우저와 인가 코드+PKCE를 사용합니다. 앱이 `code_verifier`와 `code_challenge`를 만들고 인가 요청을 보낸 뒤, 리다이렉트로 받은 코드와 `state`를 검증합니다. 이어 코드와 `code_verifier`를 토큰 엔드포인트에 제출하면 서버가 두 값의 대응을 확인하고 액세스 토큰과 필요한 경우 리프레시 토큰을 발급합니다. 코드를 가로챈 다른 앱은 `code_verifier`가 없어 코드를 사용할 수 없습니다.”

**상태** 미학습 → 오답 (1점)

## 3. [AND-029] 딥링크 처리 — 2점

**맞은 부분**

허용한 경로를 라우팅 표로 제한하고 경로·질의 매개변수를 신뢰하지 않은 입력으로 검증해야 한다는 점, 진입 화면만 띄우지 않고 자연스러운 뒤로가기 흐름을 구성해야 한다는 점을 짚었습니다.

**빠진 부분**

매니페스트의 `intent-filter`로 스킴·호스트·경로 범위를 좁히는 구성과 일반 웹 딥링크와 Android App Link의 차이가 빠졌습니다. App Link는 `https` URL과 `android:autoVerify="true"`를 선언하고 웹 도메인의 `/.well-known/assetlinks.json`에서 앱 패키지와 서명 인증서 관계를 검증하므로, 검증되지 않은 링크보다 해당 앱으로 안전하고 직접 연결할 수 있습니다. 인증이 필요한 목적지의 로그인 우회 방지, 식별자 존재 여부와 권한 확인, 외부 URL의 허용 목록, 중복 인텐트 처리도 필요합니다.

**부정확한 부분**

유효하지 않은 링크는 단순히 “오류를 반환”하는 것보다 안전한 기본 화면이나 명시적 오류 화면으로 보내는 앱 내 실패 정책이 필요합니다. 홈을 무조건 스택에 넣는 것도 정답은 아니며, 알림·외부 링크 진입 시 기대하는 뒤로가기와 상위 이동 정책에 맞춰 합성 백 스택 또는 기존 작업 재사용 여부를 정해야 합니다.

**면접에서는 이렇게**

“매니페스트에는 앱이 실제 처리하는 `https` 호스트와 경로만 선언하고 App Link는 `autoVerify`와 도메인의 `assetlinks.json`으로 소유 관계를 검증합니다. 받은 URI는 외부 입력으로 보고 허용 경로에만 매핑하며 형식·범위·존재 여부·사용자 권한을 다시 확인합니다. 인증이 필요하면 원래 목적지를 보관한 채 로그인으로 보내고, 성공 후 복귀시킵니다. 백 스택은 사용자가 외부에서 바로 들어왔는지 기존 작업에서 이동했는지에 맞춰 구성하고, 잘못된 링크는 안전한 기본 화면이나 오류 화면으로 처리합니다.”

**상태** 미학습 → 불안정 (2점)

## 4. [JK-004] Java와 Kotlin의 차이 — 2점

**맞은 부분**

Android에서 Java와 Kotlin이 모두 JVM 바이트코드를 대상으로 하며 상호 운용할 수 있다는 결론, Kotlin이 타입 체계에서 nullable과 non-null을 구분한다는 점, 코루틴이 JVM 스레드 위에서 실행된다는 점은 맞았습니다.

**빠진 부분**

질문에서 요구한 상용구 코드 비교가 빠졌습니다. Kotlin은 프로퍼티, 데이터 클래스, 기본 인자, 확장 함수 등으로 getter·setter, `equals`·`hashCode`, 여러 오버로드 같은 코드를 줄입니다. 코루틴도 단순한 디스패칭 기법이 아니라 중단 가능한 계산이며, 스레드를 막지 않고 기다릴 수 있다는 차이를 설명해야 합니다. Java에도 실행자, `CompletableFuture`, 가상 스레드 등 직접 스레드 생성 이외의 동시성 수단이 있습니다.

**틀린 부분**

Kotlin/JVM은 먼저 Java 소스로 변환된 뒤 컴파일되는 것이 아니라 Kotlin 컴파일러가 JVM 클래스 파일과 바이트코드를 직접 만듭니다. Java의 모든 자료형이 nullable한 것도 아닙니다. 원시 타입은 `null`이 될 수 없고 참조 타입은 언어 차원에서 null 가능성을 엄격히 구분하지 않는다고 말해야 정확합니다.

**면접에서는 이렇게**

“Java와 Kotlin은 Android에서 모두 JVM 바이트코드로 컴파일되며 양방향 상호 운용이 가능합니다. Kotlin은 Java를 거쳐 컴파일되는 것이 아니라 직접 JVM 바이트코드를 만듭니다. Kotlin은 타입에 null 가능성을 표시해 컴파일 시점에 많은 오류를 막고, 프로퍼티와 데이터 클래스 등으로 상용구를 줄입니다. 코루틴은 스레드 자체가 아니라 중단 가능한 작업의 추상화라 적은 스레드로 많은 대기 작업을 구조적으로 다룰 수 있지만, 실제 실행은 결국 JVM 스레드에서 이뤄집니다.”

**상태** 미학습 → 불안정 (2점)

## 5. [NET-001] TCP와 UDP — 3점

**맞은 부분**

두 프로토콜이 전송 계층에 속한다는 점과 연결형·비연결형의 차이를 먼저 밝혔습니다. TCP의 재전송·순서 보장·흐름 제어·혼잡 제어와 UDP가 이를 기본 제공하지 않는다는 점도 이전보다 정확한 용어로 설명했습니다. QUIC과 HTTP/3가 UDP 위에서 동작한다는 이전 오해도 바로잡았습니다.

**빠진 부분**

UDP가 메시지 단위의 데이터그램 전송이고 TCP가 순서 있는 바이트 스트림이라는 차이, UDP도 체크섬을 통한 오류 검출은 하지만 복구하지 않는다는 점을 덧붙이면 선택 기준이 더 명확해집니다. QUIC은 단순히 기능을 선택적으로 더하는 틀이 아니라 신뢰성, 혼잡 제어, 암호화, 다중 스트림을 사용자 공간에서 구현한 전송 프로토콜입니다.

**부정확한 부분**

UDP 자체가 언제나 TCP보다 빠르다고 단정하면 안 됩니다. 기본 헤더와 연결 설정 비용은 작지만, 애플리케이션이 신뢰성·혼잡 제어 등을 구현하면 비용이 생깁니다. QUIC이 UDP를 택한 핵심 이유도 “보내고 신경 쓰지 않아서”가 아니라 기존 운영체제와 중간 장비를 통과하면서 사용자 공간에서 빠르게 발전할 수 있고, 연결·암호화 설정을 통합하며 여러 스트림 사이의 전송 계층 head-of-line blocking을 줄일 수 있기 때문입니다.

**면접에서는 이렇게**

“TCP와 UDP는 전송 계층 프로토콜입니다. TCP는 연결형 바이트 스트림으로 재전송, 순서 보장, 흐름 제어와 혼잡 제어를 제공하고, UDP는 비연결형 데이터그램 전송으로 이런 복구·제어를 기본 제공하지 않습니다. 따라서 일반적인 신뢰성 전송에는 TCP를, 지연을 우선하거나 애플리케이션이 전송 정책을 직접 설계할 때는 UDP를 검토합니다. QUIC은 UDP 위에 신뢰성·혼잡 제어·TLS·다중 스트림을 구현해 배포와 발전을 쉽게 하고 연결 설정 지연과 스트림 간 간섭을 줄이며, HTTP/3가 이를 사용합니다.”

**상태** 불안정 유지 (3점)

## 6. [DI-001] 의존성 주입 — 3점

**맞은 부분**

사용 객체가 의존 객체를 직접 만들지 않고 외부에서 전달받는다는 정의가 정확합니다. 객체 생성·관리 책임을 구성 지점으로 옮기는 효과, 인터페이스 분리가 DI의 필수 조건은 아니라는 점, 가짜 구현을 주입해 테스트 대역으로 바꿀 수 있다는 점도 잘 설명했습니다.

**빠진 부분**

저장소 패턴이 무엇인지 별도로 설명하지 않았습니다. 저장소는 데이터 출처와 접근 방식을 감추고 도메인 또는 호출자에게 일관된 데이터 접근 계약을 제공하는 설계 패턴이고, DI는 그 저장소나 다른 의존 객체를 누가 만들어 전달할지에 관한 구성 방식입니다. 둘은 함께 쓸 수 있지만 서로 대체하지 않습니다.

**부정확한 부분**

DI만 적용하면 결합도가 자동으로 낮아진다고 말하면 과합니다. 구체 타입을 외부에서 주입해도 사용자는 여전히 그 구현 타입에 결합될 수 있습니다. DI는 우선 생성 결합을 분리하고, 인터페이스 같은 추상화와 함께 사용할 때 구현 결합과 교체 비용까지 낮춥니다. `mocked implementation`보다는 동작을 직접 제공하는 가짜 객체와 호출을 검증하는 목 객체를 구분해 말하는 편이 정확합니다.

**면접에서는 이렇게**

“의존성 주입은 객체가 필요한 의존성을 직접 생성하지 않고 외부의 구성 지점에서 생성해 전달받는 방식입니다. 그래서 사용 책임과 생성·수명 관리 책임을 분리하고 테스트에서 대역을 넣기 쉬워집니다. 인터페이스 분리는 구현 세부사항에 대한 의존을 줄이는 별도 설계 원칙이고, 저장소 패턴은 데이터 출처를 감춘 일관된 접근 계약입니다. DI는 이 인터페이스의 구현체나 저장소 객체를 선택해 주입하는 역할을 하며, 셋은 함께 사용할 수 있지만 같은 개념은 아닙니다.”

**상태** 불안정 유지 (3점)

이번 세션은 개념의 방향은 대체로 잡혀 있지만, 표준 흐름과 구체적인 측정 도구를 정확한 순서로 설명하는 힘이 부족했습니다. 특히 OAuth는 실제 서비스의 소셜 로그인 구성과 OAuth 인가 코드 규격을 섞었고, Compose는 도구명을 모호하게 말해 실무 질문의 통과선에 미치지 못했습니다. 반면 TCP/UDP와 DI는 이전 지적을 상당 부분 교정했으며, 이제 과도한 일반화와 빠진 비교 대상을 보완하면 4점에 가까워집니다.
