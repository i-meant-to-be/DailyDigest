## 1. [SEC-009] 인증서 고정 — 2점

**맞은 부분** 클라이언트에 미리 둔 정보와 서버 인증서를 비교한다는 방향, 교체 시 연결 장애가 생길 수 있다는 점은 맞습니다.

**빠진 부분** 어떤 공격을 막는지와 배포 순서가 없습니다. 앱 업데이트를 모든 사용자가 즉시 적용할 수 없으므로 서버와 클라이언트를 동시에 바꾸라는 대응만으로는 부족합니다.

**틀린 부분** 일반적인 인증서 이상 감지와 고정 검증을 구분해야 합니다. 정상적으로 신뢰되는 인증서라도 허용한 핀과 일치하지 않으면 거부하는 것이 추가 방어입니다. 공개 키를 고정했다면 같은 키로 인증서만 갱신할 때 반드시 핀이 바뀌는 것도 아닙니다.

**면접에서는 이렇게** “일반 TLS 검증에 더해 특정 인증서나 공개 키만 허용해, 신뢰된 CA가 발급한 다른 인증서를 이용한 중간자 공격도 제한합니다. 키 교체 시 구버전 앱이 접속하지 못할 수 있으므로 백업 핀을 미리 배포하고, 새 핀을 수용하는 앱을 충분히 배포한 뒤 서버 키를 교체합니다.” [Android 공식 문서](https://developer.android.com/privacy-and-security/security-config#CertificatePinning)

## 2. [DI-008] 테스트 의존성 교체 — 3점

**맞은 부분** 인터페이스에 의존하게 설계하고 가짜 구현으로 바꾸는 방법, 단위 테스트에서 생성자에 직접 넘기는 방법은 정확합니다. 플래그로 공급할 구현을 선택하는 설계 자체도 가능합니다.

**빠진 부분** Hilt 테스트에서 운영 바인딩을 테스트 전용 바인딩으로 교체하는 구체적인 흐름과 테스트 간 격리 설명이 없습니다.

**틀린 부분** `local.properties`는 앱에서 자동으로 읽는 환경 변수가 아닙니다. 플래그 방식이라면 빌드 설정으로 앱에 전달하는 과정이 필요합니다. Hilt가 그래프를 생성하는 시점과 공급 함수가 조건에 따라 객체를 반환하는 시점도 구분해야 합니다. 플래그를 켰다는 이유만으로 컴파일 시점에 바인딩 선언이 자동 교체되지는 않습니다.

**면접에서는 이렇게** “ViewModel은 Repository 인터페이스를 받게 하고, 단위 테스트에서는 가짜 객체를 생성자로 전달합니다. Hilt Android 테스트에서는 테스트 소스에 가짜 구현을 제공하는 모듈을 두고 운영 모듈을 교체합니다. 전체 테스트의 교체에는 `@TestInstallIn`, 개별 테스트에는 운영 모듈 제거 후 테스트 바인딩을 쓰는 방식이 있습니다. 테스트용 Application과 규칙을 설정해 해당 그래프로 실행합니다.” 이름을 외우지 않았다는 이유가 아니라 교체·실행 흐름의 불명확함으로 감점했습니다. [Hilt 공식 문서](https://developer.android.com/training/dependency-injection/hilt-testing)

## 3. [AND-034·신규] 프로세스 종료 복구 — 2점

**맞은 부분** 구성 변경에서는 ViewModel을 유지하지만 프로세스 종료에서는 ViewModelStore도 사라진다는 구분은 정확합니다. 작은 화면 상태에 `rememberSaveable`을 쓰는 방향도 맞습니다.

**빠진 부분** 저장을 완료한 데이터의 복구 방법이 없습니다. 화면 복구용 상태와 앱 데이터의 영구 저장은 수명이 다릅니다.

**틀린 부분** `rememberSaveable`을 앱 저장 공간에 직접 백업하고 다음 실행에서 수동으로 찾아 읽는 방식으로 설명했습니다. 일반 saved state는 시스템이 앱 프로세스 밖에서 보관하며 재생성 시 복원합니다. 임의의 재실행·강제 종료·작업 제거까지 보장하는 영구 저장소가 아닙니다. 커스텀 자료형은 Saver로 지원되는 형태로 변환할 수 있고 반드시 Parcelable로 만들어야 하는 것은 아닙니다. 어노테이션 이름은 감점 근거가 아닙니다.

**면접에서는 이렇게** “구성 변경은 같은 프로세스 안에서 ViewModel을 유지하지만 프로세스가 종료되면 새 ViewModel을 만들어야 합니다. 입력 중인 작은 값은 Compose의 저장 가능한 상태나 ViewModel의 SavedStateHandle로 복구합니다. 저장을 완료한 데이터는 DB·DataStore·파일 또는 서버에 보존하고 다시 조회합니다. 복구 상태에는 큰 데이터 전체보다 화면을 재구성하는 데 필요한 값이나 ID를 넣습니다.” [Android 공식 문서](https://developer.android.com/topic/libraries/architecture/saving-states)

이 문항은 AND-034로 등록했습니다. 2점이므로 지식 본문은 `(미작성)`으로 남겼습니다.

## 4. [CMP-008] DisposableEffect — 1점

**맞은 부분** 구독 해제를 빠뜨리면 누수가 생길 수 있다는 방향은 맞습니다.

**빠진 부분** 같은 효과 안에서 등록과 정리를 묶는 흐름, 키 변경 시 해제 후 재등록, Composition 이탈 시 해제를 설명하지 못했습니다.

**틀린 부분** 키 변경 시 코루틴을 취소·재시작하는 설명은 `LaunchedEffect`의 동작입니다. `DisposableEffect`는 코루틴 실행기가 아닙니다. 본문에서 등록하고 그 안의 `onDispose`에서 해제합니다. 호출이 Composition에서 빠지면 등록해 둔 정리가 실행됩니다. “해제 코드를 아예 작성하지 않았다”와 “효과 호출이 Composition에서 빠졌다”는 서로 다릅니다.

**면접에서는 이렇게** “`DisposableEffect(listenerOwner)` 본문에서 리스너를 등록하고 `onDispose`에서 같은 리스너를 해제합니다. 키가 같으면 일반 재구성만으로 다시 등록하지 않습니다. 키가 바뀌면 기존 것을 해제한 뒤 새 대상으로 등록하고, Composition을 떠나면 해제만 실행합니다.” [Compose 공식 문서](https://developer.android.com/develop/ui/compose/side-effects#disposableeffect)

## 5. [JK-003] val·var와 초기화 — 2점

**맞은 부분** 프로퍼티의 getter·setter 차이와 재대입 가능성, 읽기 전용 참조가 객체 내부 변경을 막지 않는다는 구분은 맞습니다.

**빠진 부분** 커스텀 getter를 가진 `val`은 접근할 때마다 값이 달라질 수 있다는 점, `const val`의 타입과 컴파일 시점 제약이 없습니다.

**틀린 부분** `lateinit`은 `val`에 쓸 수 없습니다. non-null이고 원시 타입이 아닌 `var`에 적용하며, 프로퍼티에는 커스텀 접근자를 둘 수 없습니다. 첫 접근 시 자동 초기화되는 기능도 아닙니다. 늦게 초기화하는 것은 개발자의 책임이고, 초기화 전 접근은 예외입니다. 첫 접근 시 계산하는 `val`에는 `lazy`를 사용할 수 있습니다. `val`은 선언과 동시에만 초기화해야 하는 것도 아닙니다. “모든 값이 힙에 고정된다”는 설명 역시 불변성의 근거가 아닙니다.

**면접에서는 이렇게** “`val`은 setter가 없는 읽기 전용 프로퍼티이고 `var`는 setter가 있어 재대입할 수 있습니다. 저장형 `val`의 참조를 다시 대입할 수 없어도 가변 객체 내부는 바뀔 수 있고, 계산형 getter의 반환값도 달라질 수 있습니다. `lateinit`은 non-null 참조형 `var`를 나중에 직접 초기화할 때 씁니다. `const val`은 최상위나 object·companion object의 원시 타입 또는 String 상수로, 컴파일 시점에 값을 알 수 있고 커스텀 getter가 없어야 하며 사용 지점에 값이 인라인됩니다.” [Kotlin 공식 문서](https://kotlinlang.org/docs/properties.html)

## 6. [NET-001] TCP·UDP·QUIC — 3점

**맞은 부분** 연결 여부, TCP의 네 가지 제어·보장 기능, UDP 자체에는 이 기능이 없다는 점, 추가 구현에 따라 성능이 달라진다는 방향은 맞습니다. QUIC이 UDP 위에서 신뢰성을 제공한다는 점도 이전보다 나아졌습니다.

**빠진 부분** TCP의 바이트 스트림과 UDP의 데이터그램 구분이 없고, QUIC의 ACK·손실 감지·데이터 재전송·혼잡 제어 흐름이 구체적이지 않습니다. “일부 포함”만으로는 어떤 보장을 제공하는지 알 수 없습니다.

**틀린 부분** TCP는 네트워크에서 패킷 자체가 순서대로 도착하도록 만들지 않습니다. 수신 측에서 순서를 복원해 애플리케이션에 바이트 스트림으로 제공합니다. UDP를 일반적으로 빠르다고 단정하기보다 연결 설정·헤더 부담이 작다는 사실과 실제 처리 성능을 구분해야 합니다. QUIC 구현체가 UDP 위에서 제어를 제공한다는 설명은 맞지만, 응용 개발자가 이 정책을 매번 직접 구현해야 한다는 뜻으로 말하면 부정확합니다.

**면접에서는 이렇게** “TCP는 연결을 수립하고 재전송·순서 복원·흐름 제어·혼잡 제어로 신뢰성 있는 바이트 스트림을 제공합니다. UDP는 메시지 경계를 유지하는 데이터그램 방식이며 전달·순서·제어를 기본 보장하지 않습니다. 실제 성능은 손실과 지연, 필요한 복구 방식에 달려 있습니다. QUIC은 UDP 위의 전송 프로토콜로, 구현체가 ACK와 손실 감지로 데이터를 복구하고 혼잡·흐름 제어를 제공합니다. 각 스트림 안에서 순서를 보장하면서 다른 스트림의 손실에는 독립적으로 진행할 수 있고 TLS도 통합합니다.” [QUIC 표준](https://www.rfc-editor.org/rfc/rfc9000.html)
