## 3. [신규] 입력 화면에서 앱을 백그라운드로 보낸 뒤 운영체제가 프로세스를 종료했고, 사용자가 다시 앱으로 돌아왔습니다. 화면 회전과 비교해 ViewModel만으로 복구할 수 없는 이유를 설명하고, 입력 중인 값과 저장을 완료한 데이터를 각각 어떻게 복구할지 설명해 주세요.

`platform/android` · 실무 · 주제 대장 공백 — 지식 파일에 아직 없는 주제: Configuration 변경 외의 프로세스 종료 복구

### 내 답변

구성 변경의 경우에는 구성 변경에 영향을 받지 않는 스코프에 저장된 `ViewModelStore`에 뷰 모델을 들고 있다가 복구하는 방식. 그러나 앱 프로세스가 꺼지는 경우에는 `ViewModelStore`도 살아남을 수 없기 때문에 데이터 복구를 보장할 수 없음.

이 경우 별도의 데이터 백업 및 복원 과정을 추가해야 하며, `rememberSaveable`에 커스텀 상태 저장 함수를 추가하여 `Bundle`의 형태로 데이터를 메모리가 아닌 저장 공간에 백업하도록 해야 함. (추가로 이때 `Bundle`이 지원하지 않을 수 있는 원시형이 아닌 커스텀 자료형의 경우 `@Parcelable` 어노테이션을 통해 파싱 가능하게 처리해주어야 함.) 그리고 앱이 다시 켜졌을 때 해당 공간에 백업 데이터가 있는지 확인하고 있다면 복원하는 식으로 구현.

## 4. [CMP-008] Compose 화면에서 외부 객체의 리스너를 등록하고 해제하려고 합니다. `DisposableEffect`를 어떻게 사용하며, 키가 바뀌거나 해당 호출이 Composition에서 빠질 때 각각 어떤 일이 일어나나요?

`platform/compose` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

해당 Composable이 구성(composition) 단계에 진입했을 때 구성 단계 개시와 함께 코루틴도 개시하는 `LaunchedEffect`에 리스너를 구독하는 코드를 추가하고, 구성에서 폐기(disposal)되었을 때 남은 리소스 정리를 돕는 `DisposableEffect`에 구독을 해제하는 코드를 추가해야 함.

키가 바뀔 경우 기존 코루틴은 중지되고 해당 키로 새로운 코루틴을 다시 시작하게 됨. 또한, `DisposableEffect`가 빠질 경우 화면은 사라졌음에도 불구하고 구독이 남게 되고 이건 더 이상 해제할 수 없어지기 때문에 메모리 누수로 이어질 수 있어 반드시 확실하게 해제해줘야 함.

## 5. [JK-003] Kotlin의 프로퍼티에서 `val`과 `var`는 접근자와 재대입 가능성이 어떻게 다른가요? `val`이 항상 불변 객체나 일정한 값을 뜻하는지도 설명하고, `lateinit`과 `const val`을 사용할 수 있는 조건을 비교해 주세요.

`lang/java-kotlin` · 기초 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-28) · 지난 지적: `lateinit` 적용 대상, 접근자와 계산형 프로퍼티, `const val`의 선언 위치·타입·컴파일 시점 조건을 잘못 이해함

### 내 답변

`val`과 `var`의 결정적 차이는 둘 다 Getter는 가지나 Setter는 `var`에만 있다는 점. 그래서 전자는 재대입이 불가능하지만 후자는 재대입이 가능함.

또한 재대입이 불가능하다고 해서 객체의 불변성이 보장되는 것은 아님. 모든 값들이 힙에 고정되는 형태의 정수, 실수와 같은 것들은 불변성이 보장되지만, 참조를 통해 지시되는 커스텀 자료형이나 리스트와 같은 것들은 참조의 불변성만 보장되지 참조가 가리키는 컨텐츠의 내용이 변경되는 것은 막지 못하기 때문.

`lateinit`은 반드시 선언과 동시에 초기화를 해야 하는 `val`을 늦게 초기화하고 싶을 때 사용함. 보통 무거운 객체의 초기화를 실제 사용 시점에 초기화하고 싶은 경우에 많이 사용하게 됨. `const val`의 경우 상수를 선언할 때 사용하는 것으로, 파일 최상단이나 클래스의 `companion object`에 선언될 수 있으며 마찬가지로 선언과 동시에 초기화되어야 함.

## 6. [NET-001] TCP와 UDP는 데이터 전달 방식과 기본 제공하는 보장·제어 기능이 어떻게 다른가요? UDP를 쓰면 항상 더 빠르다고 할 수 있는지, UDP 위에서 동작하는 QUIC은 신뢰성과 혼잡 제어를 어떻게 제공하는지도 설명해 주세요.

`cs/network` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-28) · 지난 지적: 기본 제어 기능을 구체적으로 설명하지 못하고 QUIC의 신뢰성·혼잡 제어·TLS·독립 스트림을 개발자 선택 사항으로 오해함

### 내 답변

TCP는 연결형, UDP는 비연결형이며, 전자는 통신에서의 신뢰성 보장을 주 목표로 두고 후자는 개발자의 자유로운 커스터마이징을 지원.

TCP는 혼잡 제어, 흐름 제어, 순서 보장, 재전송의 4가지 기능을 통해 패킷들이 순서대로 정확하게 도착할 것을 보장하지만 UDP는 이러한 기능이 전혀 없음. 그래서 UDP가 일반적으로는 빠르다고 볼 수 있긴 하지만, 만약 사용자가 UDP 위 응용 계층에서 필요에 따라 신뢰성 정책을 도입할 경우 TCP보다 UDP가 느려지는 상황도 생길 수 있다는 점은 주의해야 함.

QUIC은 UDP 기반 프로토콜이지만 TCP의 신뢰성 보장을 위한 통신 정책이 일부 포함된 프로토콜로, TCP가 아닌 만큼 UDP 위 응용 계층 쪽에서 추가적인 구현을 통해 해당 정책들을 제공함.
