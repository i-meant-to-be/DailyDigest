## 1. [DI-011] 순수 Dagger의 그래프와 Android 주입 — 1점

**맞은 부분** 컴포넌트 범위와 생성 방식을 직접 정해야 한다는 방향은 맞습니다.

**빠진 부분** 앱 전체와 화면 단위의 컴포넌트·하위 컴포넌트를 어디서 만들고 보관할지, Android가 생성하는 Activity·Fragment에 누가 언제 `inject`를 호출할지 설명하지 않았습니다. Hilt를 선택하면 이런 Android 생명주기 연결을 표준 구성으로 제공한다는 비교도 필요합니다.

**틀린 부분** "Dagger는 의존성 그래프 검증을 해 주지 않는다"는 반대입니다. Dagger는 컴파일 시점에 그래프의 필요한 바인딩과 스코프 관계를 검사합니다. 순수 Dagger에서 직접 맡는 것은 그래프의 *구성 및 Android 생명주기와의 연결*입니다.

**면접에서는 이렇게** "Dagger에서도 모듈과 컴포넌트를 선언하면 컴파일 시점 그래프 검증을 받습니다. Hilt가 없으면 애플리케이션과 화면별 컴포넌트의 계층·범위, 생성·보관 위치를 정하고, Android 구성요소의 생성 시점에 적절한 컴포넌트로 멤버 주입을 호출해야 합니다. 표준 생명주기 연결이 대부분이라면 Hilt가 반복 코드를 줄여 줍니다."

## 2. [SEC-007] AES-GCM의 IV 재사용 — 1점

**맞은 부분** IV가 암호화에 쓰이고, 유출 자체가 곧 키 노출을 뜻하지 않는다는 점은 맞습니다.

**빠진 부분** 같은 키에서 IV가 매 암호화마다 *고유*해야 하는 이유와 재사용 시 기밀성뿐 아니라 인증 무결성도 무너질 수 있다는 결과가 빠졌습니다. IV는 비밀 값일 필요가 없으며, 암호문과 함께 저장·전송할 수 있습니다.

**틀린 부분** 재사용하면 "비밀 키 하나만 남는다"는 설명은 위험을 과소평가합니다. 같은 키와 IV로 두 평문을 암호화하면 같은 키스트림이 재사용되어 암호문끼리의 XOR로 평문 사이의 관계가 드러납니다. GCM의 인증 태그도 공격받아 위조가 가능해질 수 있습니다.

**면접에서는 이렇게** "GCM의 IV는 비밀성이 아니라 같은 키에서의 고유성이 중요합니다. IV가 겹치면 카운터 모드 키스트림이 재사용돼 평문 정보가 새고, GCM의 인증도 손상돼 위조 위험이 생깁니다. 따라서 암호화마다 고유한 IV를 만들고 복호화할 수 있도록 암호문과 함께 보관합니다."

## 3. [CMP-025] `CompositionLocal` 사용 기준 — 0점

**맞은 부분** 현재 설명할 수 없다고 명확히 답했습니다.

**빠진 부분** `CompositionLocal`은 구성 트리의 아래쪽에 값을 암묵적으로 전달합니다. 테마·색상·서체처럼 하위 여러 곳에서 쓰고 중간 함수가 알 필요 없는 환경 값에 적합합니다. 특정 화면이나 자식만 쓰는 값은 일반 매개변수로 전달하는 편이 의존성이 드러나고 테스트하기 쉽습니다. 기본값 또는 제공 범위가 명확해야 합니다.

**면접에서는 이렇게** "여러 하위 Composable이 함께 쓰는 테마 같은 환경 값은 `CompositionLocalProvider`로 제공할 수 있습니다. 중간 계층에 의미 없는 매개변수만 계속 전달하게 되는 경우에 쓰되, 개별 화면의 상태나 이벤트는 명시적 매개변수로 전달합니다. 암묵적 의존성이 늘면 값의 출처를 추적하고 미리보기·테스트를 구성하기 어려워집니다."

## 4. [AND-009] UI State와 책임 분리 — 3점

**맞은 부분** ViewModel이 상태를 만들고 갱신하며 UI가 관찰해 화면을 그린다는 핵심 흐름과 불변 값 교체 방식의 예를 설명했습니다.

**빠진 부분** UI State를 먼저 "화면을 그리는 데 필요한 데이터의 스냅샷"이라고 정의했어야 합니다. `data class`, `StateFlow`, `copy`는 흔한 구현 방식일 뿐 필수 조건이 아닙니다. UI가 모든 상태를 읽기만 하는 것도 아닙니다. 입력 포커스·펼침 여부처럼 화면 요소에 국한된 상태는 UI가 소유하고, 사용자 이벤트는 ViewModel로 올릴 수 있습니다.

**면접에서는 이렇게** "UI State는 한 시점의 화면 렌더링에 필요한 값의 모음입니다. ViewModel은 데이터 원천과 사용자 이벤트를 처리해 화면 수준의 상태를 만들고, UI는 이를 관찰해 렌더링하며 이벤트를 다시 전달합니다. 화면 요소에만 필요한 임시 상태는 UI가 직접 가질 수 있습니다. `StateFlow`와 불변 데이터 클래스는 이 흐름을 구현하는 한 방법입니다."

## 5. [JK-004] Java와 Kotlin 비교 — 2점

**맞은 부분** JVM 상호 운용성, Kotlin의 nullable 구분, Java 참조 타입과 원시 타입의 null 가능성 차이를 짚었습니다.

**빠진 부분** 둘 다 JVM용 바이트코드로 컴파일되어 실행된다는 경로를 분명히 말하지 않았습니다. 상용구 감소는 `data class`의 생성 메서드, 프로퍼티 접근자, 기본 인자처럼 Java에서 직접 작성하기 쉬운 코드를 예로 들어야 합니다.

**틀린 부분** 코루틴은 Java 스레드 자체를 추상화한 스레드가 아니라 중단·재개할 수 있는 계산 단위입니다. 디스패처가 실행할 스레드를 정합니다. `let`이나 `val`/`var`가 반복문·조건문 자체를 줄인다는 예시는 질문의 상용구 비교를 뒷받침하지 못합니다.

**면접에서는 이렇게** "Java와 Kotlin은 JVM용 바이트코드로 컴파일되므로 상호 운용됩니다. Kotlin은 타입 수준에서 null 허용 여부를 구분하지만 Java 참조 타입은 기본적으로 null이 가능하고 원시 타입은 그렇지 않습니다. Kotlin 코루틴은 스레드와 다른 중단 가능한 작업 단위이며, `data class`와 프로퍼티·기본 인자 등으로 반복 코드를 줄입니다."

## 6. [NET-001] TCP·UDP와 QUIC — 2점

**맞은 부분** TCP의 연결성과 신뢰성, UDP의 비연결성과 기본 기능 차이를 구분했고, 응용 계층에서 복구를 구현하면 UDP 사용이 반드시 빠르지 않다는 조건을 짚었습니다. 이 속도 조건은 현재 원문보다 정확합니다.

**빠진 부분** TCP의 재전송·순서 보장·흐름 제어·혼잡 제어와 UDP가 기본으로 제공하지 않는 기능을 구체적으로 나열해야 합니다. QUIC이 UDP 위에서 패킷 손실 복구, 혼잡 제어, TLS 보안, 독립 스트림을 제공하는 이유도 설명해야 합니다.

**틀린 부분** QUIC을 "개발자가 필요한 신뢰성 정책을 선별하는 프로토콜"이라고 설명한 부분은 잘못됐습니다. QUIC은 신뢰성 있는 스트림과 혼잡 제어를 규약으로 정의합니다. UDP를 쓰는 이유는 사용자 공간에서 전송 기능을 발전시키고 기존 네트워크에서 배포하기 쉬우며, 독립 스트림으로 TCP 연결 전체의 순서 대기 문제를 줄일 수 있기 때문입니다.

**면접에서는 이렇게** "TCP는 연결을 맺고 재전송·순서·흐름·혼잡 제어를 제공하지만 UDP는 이런 보장을 기본으로 제공하지 않습니다. UDP가 항상 빠른 것은 아닙니다. 응용 프로그램이 손실 복구 등을 추가하면 비용이 생깁니다. QUIC은 UDP 위에서 신뢰성 있는 다중 스트림, 혼잡 제어와 TLS를 구현해 기존 UDP 경로를 활용하면서 연결 설정 지연과 스트림 간 대기를 줄입니다."
