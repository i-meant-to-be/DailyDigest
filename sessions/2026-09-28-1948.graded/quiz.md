## 4. [AND-009] Android UI State란 무엇이며, ViewModel과 UI는 이를 중심으로 어떤 책임을 나누나요?

`platform/android` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

UI State는 특정 화면의 뷰 모델에 걸리는 상태를 총칭하는 단어이다.

각 화면마다 UI State 데이터 클래스가 정의된다. 화면 갱신을 트리거하기 위해, UI State는 Compose 또는 Android가 추적할 수 있는 형태의 타입(`State`나 `StateFlow`)으로 선언되며, 갱신 시에는 기존 UI State 인스턴스의 `copy` 함수로 필요한 값만 선택적으로 수정한 후 재구성(Recomposition) 조건을 트리거하기 위해 기존 상태 인스턴스를 완전히 대체하는 식으로 갱신된다.

뷰 모델은 해당 UI State를 조작할 책임을 가지며, UI는 뷰 모델이 처리해준 UI State를 읽어 화면을 그리는 책임을 가진다. 그렇기 때문에 뷰 모델은 UI State 데이터를 쓸 수 있지만, UI는 오직 상태를 보는 것만 허용된다.

## 5. [JK-004] Java와 Kotlin이 JVM에서 실행되는 방식의 공통점을 짚고, null 안전성·비동기 처리·상용구 측면의 차이를 설명해 주세요.

`lang/java-kotlin` · 기초 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-11) · 지난 지적: Kotlin의 컴파일 경로, Java 참조 타입과 원시 타입의 null 가능성, 코루틴의 추상화와 상용구 감소를 정확히 설명하지 못함

### 내 답변

둘 다 결론적으로는 JVM에서 실행되기 때문에 Kotlin 코드 내에서 Java 기능을 사용하는 것이 가능하다.

그러나 Kotlin이 Nullable한 자료형과 그렇지 않은 자료형을 명확히 구분하는 것에 비해 Java는 Nullable 여부를 자료형 지정 시 명확하게 선언하도록 강제하지 않아 `null` 대응에 있어 다소 모호한 측면이 있다. 이 부분은 참조 타입에만 해당하며 모든 값들이 메모리에 저장되어 있는 원시 타입에는 해당하지 않는 부분이다. 또한, 비동기 처리에 관해서도 조금 차이가 있는데 Kotlin은 Java의 스레드를 추상화하여 더 쉽게 사용할 수 있도록 하는 Coroutine으로 비동기 작업을 처리한다는 점이 다르다. 마지막으로 Kotlin은 `by`, `val`과 `var`에서 가능한 Getter와 Setter 오버로드, `let` 등의 다양한 유틸리티를 통해 반복문, 조건문과 분기 등 코드 양을 줄이고 코드 흐름을 더 명확하게 보여줄 수 있다는 점에서도 차이가 있다.

## 6. [NET-001] TCP와 UDP의 연결 방식과 신뢰성 보장 차이를 설명하고, UDP가 항상 더 빠르다고 할 수 없는 이유와 QUIC이 UDP 위에서 신뢰성을 구현한 이유를 말해 주세요.

`cs/network` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-11) · 지난 지적: 성능 차이의 조건과 QUIC의 신뢰성·혼잡 제어·TLS·다중 스트림 및 배포상 이유를 설명하지 못함

### 내 답변

TCP는 연결형 프로토콜이며 전송 간 신뢰성 보장을 주 목표로 하고, UDP는 비연결형 프로토콜이며 신뢰성 보장보다는 개발자의 자율성 보장에 더 무게를 둔다.

보통 TCP의 신뢰성 보장을 위한 여러 정책으로 인해 제약이 거의 없는 UDP가 더 빠르지만, 만약 개발자가 UDP 위 응용 계층에서 직접 신뢰성 보장을 위한 정책을 구현한다면 경우에 따라 UDP가 TCP보다 느려지는 경우가 생길 수 있음은 고려해야 한다.

QUIC은 UDP 기반 새로운 통신 프로토콜로, TCP가 모든 신뢰성 정책을 무조건 채택하는 것과는 달리 개발자가 필요한 신뢰성 정책을 선별적으로 택할 수 있게 하여, UDP의 가벼움과 TCP의 신뢰성 사이에서 균형을 조정할 수 있는 프로토콜이다.
