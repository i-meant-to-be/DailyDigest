## 1. [SEC-011] 루팅된 기기나 디컴파일에 대해 클라이언트가 할 수 있는 것과 할 수 없는 것은 무엇인가요?

`platform/security` · 실무 · 답을 적어 둔 적 없는 문항

### 내 답변

할 수 있는 것은 R8 컴파일러의 난독화 옵션을 키는 것. 난독화 옵션을 키면 리버스 엔지니어링 후에도 코드가 읽기 어렵도록 꼬이게 됨. 그래서 코드 내부 구조를 파악하는 데 시간이 오래 걸리게 될 것.

반면 할 수 없는 것은 앱 데이터가 노출되는 것. 원래 바닐라 상태에서는 앱의 세부 데이터(정확히는 `/data/data` 디렉토리 내 설치된 앱 파일들)에 접근할 수 없지만 루팅 후에는 그게 가능해짐. 따라서 외부인이 앱 패키지 자체와 앱 실행에 필요한 데이터 전부를 열람할 수 있게 됨. 이것 자체는 루팅이 된 후에는 막을 수 없음.

`platform/android` · 실무 · 주제 대장 공백 — Gradle 빌드 속도를 줄이는 방법은 지식 파일에 아직 없는 주제

### 내 답변

가장 먼저 증분 빌드와 빌드 캐싱이 활성화되어 있는지 확인하고 그렇지 않다면 적용.

다음으로는 빌드 양상을 확인하고 가장 많은 시간이 쓰이는 부분을 여러 파트로 쪼갤 수 있는지 검토 후 가능하다면 여러 파트로 쪼갬. 기존에는 하나의 작은 변경이 통합된 전체 모듈에 영향을 미쳤었다면, 이런 식으로 모듈을 분리할 경우 특정 모듈의 변경 사항은 해당 모듈과 관련된 소규모 범위로만 제한되어 나머지 비변경 모듈의 빌드는 Gradle 특성상 스킵할 수 있게 되기 때문. 개선 여부를 확인하는 방법은 기존의 코드 변경이 모듈을 쪼갠 후에 다른 모듈의 재빌드를 얼마나 트리거하는지 확인하는 것.

다음으로는 빌드 스크립트를 재사용할 수 있는지를 검토하고 그럴 수 있다면 재사용 가능한 빌드 스크립트를 별도로 분리.

## 3. [CMP-014] Compose에서 Modifier의 순서가 중요한 이유는 무엇인가요? `clickable().padding(16.dp)`와 `padding(16.dp).clickable()`의 클릭 영역을 비교해 설명해 주세요.

`platform/compose` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

Modifier의 함수 적용 순서에 따라 실제 UI에 미치는 영향이 달라지기 때문.

질문의 예시를 살펴보면 전자 `clickable().padding(16.dp)`의 경우 클릭 영역이 먼저 결정된 후 여백이 들어가기 때문에, 뒤에 따라오는 여백이 클릭 가능한 부분에 영향을 주지 못함. 그러나 후자 `padding(16.dp).clickable()`의 경우 여백을 먼저 넣은 후에 남은 공간에 클릭 가능한 부분을 설정하는 것이기 때문에 여백이 영향을 미치게 됨.

## 4. [JK-004] JVM을 대상으로 하는 Java와 Kotlin의 공통점과 차이점을 설명해 주세요. 컴파일 결과, null 처리, 반복 코드를 줄이는 기능을 포함하고, Kotlin 코루틴과 스레드가 어떤 관계인지도 설명해 주세요.

`lang/java-kotlin` · 기초 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-28) · 지난 지적: JVM 바이트코드 컴파일 경로와 반복 코드 감소 사례를 설명하지 못함; 코루틴과 스레드의 관계를 정확히 구분하지 못함

### 내 답변

둘 다 JVM 위에서 동작하는 바이트코드로 컴파일된다는 공통점이 있음. 그렇기 때문에 Kotlin에서 Java 기능도 사용이 가능한 것. 그러나 다양한 부분에서 차이가 있는데, Kotlin은 Non-nullable한 자료형과 Nullable한 자료형을 연산자 `?`로 명확히 구분하는 것에 비해 Java는 이를 명확히 구분하지 않음. 또한 반복 코드를 줄일 수 있는 유틸리티가 Kotlin에 더 많은데, 대표적으로 Java에서는 별도 라이브러리를 추가해야 했던 Getter와 Setter가 Kotlin에는 기본적으로 탑재되어 있고, `toString`과 같은 유틸 함수나 DTO 등 데이터 처리에 적절한 여러 기본 함수(`copy`, `componentN` 등)를 기본 제공하는 `data class` 등이 여러 보일러플레이트를 줄여줌에 있어 큰 도움을 줌.

Kotlin의 코루틴은 Java가 관리하는 스레드 위에서 동작하는 비동기 처리 유틸리티로, 실행 중 정보가 스택의 형태로 구성되며 실제 메모리에 그대로 저장되는 스레드와는 달리 코루틴은 그 스냅샷이 `Continuation`이라는 특정 언어에 종속되는 자료형으로 힙에 올라가 관리되는 형태이기 때문에 엄밀히는 스레드라고 보기 어려움. Java 스레드와는 M:N의 관계를 가지며, 코루틴을 전략적으로 관리하는 Dispatchers가 코루틴을 필요에 따라 스레드에 올리거나 내리는 등으로 비동기 처리를 효율적으로 처리.

## 5. [DI-001] 의존성 주입이란 무엇이며, 객체가 의존성을 직접 생성할 때와 비교해 어떤 이점이 있나요? 저장소 패턴을 사용하는 예로 설명하고, DI 자체의 원칙과 DI 컨테이너의 객체 수명주기 관리 역할도 구분해 주세요.

`platform/di` · 기초 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-10-02) · 지난 지적: 저장소 패턴이 데이터 출처를 감추고 일관된 접근 계약을 제공한다는 역할을 설명하지 못함; DI 원칙과 컨테이너의 수명주기 관리 역할을 구분하지 못함 — 알지만 설명하지 못함

### 내 답변

DI란 특정 클래스에 필요한 인스턴스를 해당 클래스의 생성자 내에서 직접 생성하는 게 아니라 외부에서 넣어주는 것을 뜻함.

의존성을 직접 생성하려면 해당 클래스의 책임과 범위와는 관련이 없는 인스턴스에 대한 내용까지 알아야 하고 생성/파괴에 대한 책임도 져야 하지만, DI를 적용할 경우 단순히 외부에서 전해주는 걸 받기만 하면 되기에 이런 모든 책임을 덜 수 있고 클래스 고유의 책임을 다할 수 있어 응집도 상승.

저장소 패턴과 DI를 같이 사용하면 시너지가 나는데, 저장소 패턴은 데이터 소스를 인터페이스로 정의하고 해당 인터페이스를 구현하도록 작성된 구현체에서 실제 데이터를 넘기는 아키텍처로, 1) 저장소를 사용하는 객체가 저장소 구현에 대해 알 필요가 없어 결합도가 줄어든다는 장점 그리고 2) 저장소로서는 어떤 구현체를 사용하는지 노출하지 않고 숨길 수 있다는 장점이 있음.

DI의 원칙은 의존성을 외부에서 넣어준다는 것이며, 해당 의존성을 어떻게 생성하고 어떻게 관리하며 수명주기는 어떻게 맞출지를 고민하는 것은 DI 자체와는 큰 관련이 없음. Android 진영에서는 이 부분을 주로 Hilt 등과 함께 Android 생명주기와 맞추어 관리하는 방식을 취함.

## 6. [HIL-001] Hilit에서 기능 모듈을 `api`와 `impl`로 나누는 이유는 무엇인가요? 각 모듈의 책임, 기능 간 화면 이동 시 의존 방향, 앱 모듈의 역할을 설명해 주세요. 모듈 수가 늘어날 때 빌드 시간에 미치는 영향은 어떤 근거로 판단하겠습니까?

`project/hilit` · 실무 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-04) · 지난 지적: 앱은 각 기능의 네비게이션 트리를 합치고 기능의 impl끼리는 의존하지 않는다는 책임 구조를 명시하지 못함; 모듈 증가가 Gradle 빌드 시간을 반드시 늦춘다고 근거 없이 단정함

### 내 답변

네비게이션 라우팅 테이블을 제공할 책임을 기능 모듈에 두면서도, 해딩 기능 모듈의 전체 또는 핵심 기능이 모듈 밖에 노출되는 것을 막기 위함. 더해 코드 재사용성도 확보 가능.

프로젝트에서는 라우팅 테이블 구성 책임을 각 기능 모듈의 `api` 서브 모듈에 두었음. 기능 모듈의 실제 구현은 `impl` 서브 모듈에 두었고. 각 기능 모듈이 자신이 보유한 페이지에 따라 라우팅 테이블을 구성해두면 앱 모듈이 하위 기능 모듈들의 라우팅 테이블을 모아 합치는 식. 만약 기존 방식대로 기능 모듈을 다른 모듈에 섣불리 열어주었다면 공개되어서는 안 될 코드가 기능 모듈 외부에 노출될 수도 있고, 다른 모듈과 기능 모듈 간 결합도가 상승했을 것. 그러나 현재 구현처럼 페이지 정의 및 라우팅 테이블 관련 부분만 `api` 모듈로 따로 빼면, 기능 모듈과 해당 기능 모듈에 네비게이션으로 접근해야 할 다른 모듈이 단일 라우팅 테이블 정의를 공유할 수 있고, 실제 구현이 담긴 `impl` 모듈 내부 컨텐츠는 노출되지 않는다는 장점이 있음.
