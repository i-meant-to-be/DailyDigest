## 1. [SEC-011] 루팅·디컴파일 방어의 한계 — 2점

**맞은 부분**
난독화는 분석을 어렵게 하는 수단이며, 루팅된 환경에서는 일반적인 앱 저장소 접근 제한을 신뢰할 수 없다는 방향은 맞습니다. 난독화로 디컴파일 자체를 막는다고 주장하지 않은 점도 맞습니다.

**빠진 부분**
실무 질문이므로 방어의 한계를 인정한 다음 설계 대책까지 이어져야 합니다. 민감한 정보의 저장을 줄이고, 장기 비밀을 앱에 포함하지 않으며, 권한 검증과 중요 판단을 서버에서 수행하는 전략이 없습니다. 루팅 탐지 같은 보조 수단도 우회 가능하다는 조건과 함께 설명할 수 있습니다.

**틀리거나 과도하게 단정한 부분**
"앱 실행에 필요한 데이터 전부를 열람"한다는 표현은 범위가 너무 넓습니다. 일반 파일 접근, 실행 중 평문 관찰, 하드웨어 보호 키의 원문 추출은 서로 다릅니다. 하드웨어에 묶인 Keystore 키는 운영체제가 침해돼도 키 자체의 추출을 제한할 수 있습니다. 다만 공격자가 기기 안에서 키 사용을 악용하거나 앱이 처리하는 평문을 관찰할 가능성은 별개입니다. [Android Keystore 공식 문서](https://developer.android.com/privacy-and-security/keystore)

**면접에서는 이렇게**
"난독화는 역공학 비용을 높일 뿐 비밀을 보장하지 않습니다. 루팅된 기기에서는 일반 앱 파일과 실행 환경을 신뢰할 수 없으므로 민감한 저장을 최소화하고, 중요한 권한 판단은 서버에서 검증하겠습니다. 하드웨어 보호 키는 추출을 제한하는 데 도움을 주지만, 침해된 앱에서의 키 사용이나 평문 노출까지 막는다고 보지는 않겠습니다."

**상태** 미학습 → 불안정. 방어 수단 하나와 한계는 알지만, 보호 대상별 구분과 설계 대책이 부족합니다.

## 2. [AND-035] Gradle 빌드 시간 개선 — 2점

**맞은 부분**
증분 처리와 캐시 활용을 확인하고, 시간이 많이 드는 부분을 찾아 모듈 분리를 검토한다는 방향은 맞습니다. 변경 후 다른 모듈의 재빌드가 얼마나 발생하는지 보겠다는 관점도 유효합니다.

**빠진 부분**
첫 단계는 동일 조건에서 기준 시간을 측정하고 구성·컴파일·작업 실행 등 병목을 구분하는 것입니다. 변경이 없는 빌드와 특정 코드 변경 후 빌드를 나눠 반복 측정해야 합니다. 재실행 작업 수뿐 아니라 전체 소요 시간이 줄었는지를 확인해야 하며, 증분 빌드·작업 결과 캐시·구성 캐시가 각각 무엇을 재사용하는지도 설명하지 못했습니다.

**틀리거나 근거가 부족한 부분**
모듈 분리는 의존 방향과 변경 종류에 따라 재컴파일 범위를 줄일 수 있지만, 공개 계약 변경은 소비 모듈에 영향을 주고 모듈 증가 자체는 구성 비용을 늘릴 수 있습니다. 빌드 스크립트 분리는 중복 관리에 도움이 되지만 그것만으로 속도가 빨라진다는 근거는 없습니다. 불필요한 구성 작업을 줄였는지처럼 실제 효과를 연결해야 합니다. [Gradle 성능 개선 공식 문서](https://docs.gradle.org/current/userguide/performance.html)

**면접에서는 이렇게**
"먼저 같은 환경에서 변경 없는 빌드와 코드 수정 후 빌드를 반복 측정하고, 프로파일 보고서로 병목을 찾겠습니다. 증분 처리는 변경된 입력에 필요한 작업만 수행하고, 작업 결과 캐시는 같은 입력의 산출물을 재사용하며, 구성 캐시는 구성 단계 결과를 재사용합니다. 각 기능의 재사용 가능 조건을 확인하고 병목에 맞게 적용하겠습니다. 모듈 분리는 변경 전파를 줄일 때 검토하되, 구성 비용까지 포함한 전체 시간으로 효과를 판단하겠습니다."

**상태** 미학습 → 불안정. 신규 문항을 `AND-035`로 등록했으며, 2점이므로 원문 답은 규칙에 따라 `> (미작성)`으로 남겼습니다.

## 3. [CMP-014] Modifier 순서와 클릭 영역 — 3점

**맞은 부분**
순서에 따라 결과가 달라진다는 점과, `padding().clickable()`은 여백 안쪽에 클릭 동작을 적용한다는 설명은 맞습니다.

**빠진 부분**
첫 번째 순서에서 **여백도 클릭 영역에 포함된다**는 결론을 직접 말하지 않았습니다. "여백이 클릭 가능한 부분에 영향을 주지 못한다"는 말은 여백을 포함한다는 뜻인지, 클릭 영역이 여백만큼 커지지 않는다는 뜻인지 모호합니다. 두 번째는 여백을 제외한다고 명시하면 비교가 완성됩니다.

**설명에서 교정할 부분**
클릭 영역을 먼저 확정하고 이후 단계는 영향을 주지 못한다는 시간 순서보다는, 앞의 Modifier가 뒤쪽 내용을 감싸는 구조로 설명하는 편이 정확합니다. 답변을 두 영역을 반대로 외운 것으로 단정하지는 않았습니다. 이 문항의 3점은 결과를 명확히 비교하지 못한 설명에 대한 점수입니다. [Compose Modifier 공식 문서](https://developer.android.com/develop/ui/compose/modifiers#order-of-modifiers-matters)

**면접에서는 이렇게**
"앞의 Modifier가 뒤쪽을 감싸므로 순서에 따라 적용 영역이 달라집니다. `clickable().padding(16.dp)`는 여백을 포함한 전체 영역이 클릭되고, `padding(16.dp).clickable()`은 바깥 여백을 제외한 안쪽만 클릭됩니다. 그래서 배경이나 클릭 영역을 어디까지 적용하려는지에 따라 순서를 정합니다."

**상태** 미학습 → 불안정. 개념 방향은 맞지만 비교 결과를 명시하는 말하기 연습이 필요합니다.

## 4. [JK-004] Java·Kotlin과 코루틴·스레드 — 3점

**맞은 부분**
JVM 대상 바이트코드, nullable 타입의 구분, 기본 접근자와 데이터 클래스의 반복 코드 감소를 설명했습니다. 코루틴이 스레드 위에서 실행되는 별도의 추상화라는 구분도 이전 지적보다 보완됐습니다. 여러 코루틴이 여러 스레드를 공유할 수 있다는 방향은 맞습니다.

**틀린 부분**
Java의 getter·setter는 라이브러리 없이 직접 작성할 수 있습니다. 라이브러리는 작성을 자동화하는 선택 사항이므로 "별도 라이브러리를 추가해야 했다"고 하면 잘못된 비교가 됩니다.

코루틴은 스레드 호출 스택을 통째로 스냅샷으로 복사해 힙에 올리는 방식이 아닙니다. 중단 가능한 함수는 재개 지점과 필요한 지역 값을 보관하는 상태 머신으로 변환됩니다. `Continuation`은 재개를 이어 가는 구조이며, 중단 후 어떤 스레드에서 재개할지는 실행 문맥과 디스패처 정책에 달려 있습니다. 모든 코루틴이 항상 스레드 풀을 오가는 것은 아닙니다. [Kotlin 코루틴 명세](https://kotlinlang.org/spec/asynchronous-programming-with-coroutines.html)

**면접에서는 이렇게**
"JVM 대상 Java와 Kotlin은 바이트코드로 컴파일되며 상호 운용할 수 있습니다. Kotlin은 nullable 타입을 구분하고 기본 접근자와 데이터 클래스로 반복 코드를 줄입니다. Java에서도 접근자는 직접 작성할 수 있습니다. 코루틴은 스레드 자체가 아니라 스레드에서 실행되는 중단·재개 가능한 작업입니다. 중단 때 재개에 필요한 상태를 보관하고 스레드를 점유하지 않으며, 재개할 실행 위치는 디스패처 정책에 따릅니다."

**상태** 불안정 유지. 질문에 필요한 기초 설명은 보완됐지만, 추가한 내부 구현 설명에 개념 오류가 있어 4점은 아닙니다.

## 5. [DI-001] 의존성 주입과 저장소 패턴 — 3점

**맞은 부분**
의존 객체를 외부에서 전달받는다는 정의와, 소비 객체가 생성 세부사항을 덜 알아도 된다는 이점은 정확합니다. DI 원칙과 Hilt 등의 객체 생성·범위 관리 역할도 구분했습니다. DI는 생성자 주입 외의 형태로도 가능하지만, 생성자를 예로 든 것 자체는 감점하지 않았습니다.

**빠진 부분**
저장소 패턴 설명이 여전히 인터페이스와 구현체 일반론에 머물렀습니다. 예를 들어 화면 모델이 `UserRepository`를 통해 사용자를 조회하면, 데이터가 서버에서 오는지 로컬 DB에서 오는지와 동기화 정책을 저장소 구현이 감추고 일관된 접근 계약을 제공한다고 설명해야 합니다. 실제 구현 대신 가짜 저장소를 주입하는 테스트 예까지 연결하면 결합도 감소가 구체적으로 드러납니다.

**과도하게 단정한 부분**
DI가 생성·파괴에 대한 "모든 책임"을 없애지는 않습니다. 의존 객체의 생성 책임을 밖으로 옮겨도, 사용 계약에 따른 자원 정리나 잘못된 장기 참조 방지는 별도 문제입니다. 컨테이너의 객체 제공 범위를 일반 자원의 자동 해제와 혼동하면 안 됩니다. [Android 의존성 주입 공식 문서](https://developer.android.com/training/dependency-injection)

**면접에서는 이렇게**
"DI는 객체가 의존성을 직접 만드는 대신 외부에서 전달받게 하는 방식입니다. 화면 모델에 저장소를 주입하면 서버와 DB를 어떻게 사용하는지 몰라도 일관된 데이터 접근 계약을 사용할 수 있고, 테스트에서는 가짜 저장소로 교체할 수 있습니다. DI는 수동으로도 가능하며, 컨테이너는 의존성 그래프와 객체 제공 범위를 관리하는 도구입니다. 자원 정리까지 자동으로 해결한다는 의미는 아닙니다."

**상태** 불안정 유지. 컨테이너와 원칙의 구분은 개선됐지만 저장소의 구체적 역할과 자원 책임은 아직 불완전합니다.

## 6. [HIL-001] 기능 모듈의 api·impl 분리 — 2점

**맞은 부분**
외부에 필요한 계약만 제공해 구현과의 결합을 낮추려는 목적, 각 기능이 네비게이션을 책임지고 앱이 이를 합친다는 큰 구조는 맞습니다.

**틀린 부분**
등록된 프로젝트 원문 기준으로 `api`는 route key와 args 같은 **이동 계약**을 갖습니다. 화면·화면 모델·entry builder·DI와 네비게이션 진입점 구성은 `impl`에 있습니다. 따라서 실제 화면 진입점을 구성하는 라우팅 테이블까지 `api`가 맡는다는 설명은 계약과 구현을 섞은 것입니다. "라우팅 테이블"을 단순한 route 정의라는 의미로 썼다면 그 구분을 명시해야 합니다.

**빠진 부분**
기능의 `impl`이 다른 기능의 `impl`에 의존하지 않고 이동 대상의 `api`만 참조한다는 방향을 명시하지 않았습니다. 빌드 시간 영향을 묻는 마지막 질문에도 답이 없습니다. 코드 재사용성은 가능한 부수 효과지만, 이 구조의 핵심 근거를 대신하지는 못합니다.

**면접에서는 이렇게**
"이 분리는 파트너 개발자가 결정했지만, 이동 계약과 화면 구현을 분리한다는 점에서 지지합니다. `api`는 route와 인자 계약을 공개하고 `impl`은 화면과 진입점 구성을 담당합니다. 다른 기능으로 이동할 때는 그 기능의 `api`만 참조하고 `impl`끼리 의존하지 않습니다. 각 기능이 만든 네비게이션 구성을 앱에서 합칩니다. 모듈 증가로 구성 비용은 늘 수 있고 변경 전파는 줄 수 있으므로, 동일한 수정 전후의 재실행 작업과 전체 시간을 측정해 빌드 영향을 판단하겠습니다."

**상태** 불안정 유지. 큰 목적은 알지만 실제 계약과 구현의 책임을 정확히 구분하지 못했습니다.

---

이번에는 JVM 컴파일 경로와 DI 원칙·컨테이너 구분이 보완됐습니다. 남은 약점은 결과를 명시하지 않는 비교 설명, 계약과 구현의 책임 혼동, 효과를 측정할 조건 없이 개선 방법을 나열하는 설명입니다. 내부 구현을 자세히 말할 때는 스냅샷·파괴 책임처럼 강한 표현이 실제로 성립하는지 확인해야 합니다.
