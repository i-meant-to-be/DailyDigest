## 1. [CMP-025] `CompositionLocal` 사용 기준 — 3점

**맞은 부분**

중간 컴포저블이 쓰지 않는 값을 계속 전달하는 문제, 특정 컴포지션 하위 트리라는 범위, `CompositionLocalProvider`를 통한 제공, 테마·디자인 시스템이라는 대표 사례를 정확히 짚었습니다. 이전에 설명하지 못했던 “트리 범위 값 전달”의 성격은 이번에는 분명하게 설명했습니다.

**빠진 부분**

함수 서명이 길어진다는 이유만으로 선택해서는 안 됩니다. 여러 후손이 공통으로 소비하고, 중간 계층이 전달 책임을 질 이유가 없으며, 트리 문맥에 자연스럽게 속하는 횡단 관심사인지가 기준입니다. 특정 컴포저블이 반드시 필요로 하는 비즈니스 데이터나 동작은 명시적 매개변수로 드러내는 편이 재사용·테스트·미리보기에 유리합니다. 과용하면 의존성이 호출부에서 보이지 않고 값의 출처와 재구성 범위를 추적하기 어려워집니다.

**틀린 부분**

수정 가능한 값을 제공한다고 해서 `CompositionLocal` 자체가 자원 점유 경쟁을 일으키는 것은 아닙니다. 동시 접근 제어와는 별개의 문제입니다. 가변 상태를 제공한다면 상태 소유권과 Compose 상태 규칙을 지켜야 하지만, 이를 경쟁 상태에 대비하는 도구로 설명하면 개념 층위가 섞입니다.

**면접에서는 이렇게**

“`CompositionLocal`은 테마처럼 컴포지션 트리의 넓은 범위에서 공유되고 중간 노드가 전달할 이유가 없는 문맥 값을 제공할 때 적합합니다. 반대로 개별 컴포넌트의 필수 데이터나 이벤트는 매개변수로 명시해 의존성을 드러냅니다. 단순히 매개변수가 많다는 이유로 바꾸면 의존성이 숨고 재사용·테스트와 값 추적이 어려워지므로, 트리 문맥에 속하는 횡단 값인지로 판단합니다.”

**상태** 오답 → 불안정 (3점)

## 2. [AND-030] 런타임 권한 요청 흐름 — 2점

**맞은 부분**

`shouldShowRequestPermissionRationale`이 재요청 횟수가 아니라 추가 설명을 보여 줄 필요성을 나타낸다는 점, 요청 이력은 앱이 별도로 보관해야 한다는 방향은 맞았습니다. 지난 답변의 핵심 오해 하나는 바로잡았습니다.

**빠진 부분**

전체 흐름이 빠졌습니다. 기능 실행 전에 현재 권한을 먼저 확인하고, 이미 허용됐으면 즉시 기능을 실행해야 합니다. 허용되지 않았다면 등록해 둔 권한 요청 계약을 실행하고, 결과 콜백에서 허용이면 원래 작업을 계속하고 거부면 이유 설명·재요청·설정 안내 중 하나로 분기해야 합니다. 요청 횟수를 세는 것보다 “이 앱이 전에 요청을 실행한 적이 있는가”라는 이력이 핵심입니다.

**틀린 부분**

사용자가 설명 후 한 번 더 거부했다고 무조건 설정 화면으로 보내는 것은 아닙니다. 일반적으로 `rationale = true`이면 설명 후 사용자의 명시적 행동으로 다시 요청할 수 있습니다. `rationale = false`이면서 앱의 요청 이력이 없다면 최초 요청일 수 있고, 요청 이력이 있다면 더 이상 시스템 대화상자로 해결하기 어려운 거부로 추론해 설정 화면을 안내합니다. 플랫폼은 “영구 거부” 값을 직접 주지 않으므로 두 정보를 함께 봐야 합니다.

**면접에서는 이렇게**

“먼저 현재 권한을 확인하고 허용 상태면 기능을 실행합니다. 아니면 Activity Result 기반 요청을 보내고 결과에서 허용이면 원래 흐름을 재개합니다. 거부됐을 때 설명 필요 값이 참이면 기능에 권한이 필요한 이유를 설명한 뒤 사용자가 원할 때 다시 요청합니다. 거짓이면 앱이 전에 요청한 적이 없는지 확인해 최초 요청과 더 이상 대화상자로 해결하기 어려운 거부를 구분하고, 후자에만 설정 화면 이동을 안내합니다. 거부 상태에서도 가능한 대체 기능이 있으면 함께 제공합니다.”

**상태** 오답 → 불안정 (2점)

## 3. [SEC-009] 인증서 고정 — 0점

답을 모른다고 명시했으므로 오답입니다.

**핵심 개념**

기본 TLS 검증은 기기의 신뢰 저장소가 인정하는 인증 기관에서 발급되고 호스트 이름과 유효기간이 맞는 인증서를 신뢰합니다. 인증서 고정은 여기에 서버 인증서나 공개 키의 예상 값을 앱에 미리 제한하는 검증을 더합니다. 따라서 신뢰된 인증 기관의 오발급·침해나 사용자 기기에 추가된 인증서를 이용해도 예상 핀과 다르면 연결을 거부해 중간자 공격을 어렵게 합니다.

**운영 위험**

인증서 갱신, 키 교체, 인증 기관 변경 시 앱에 들어 있는 핀과 달라지면 정상 사용자 전체의 통신이 끊길 수 있습니다. 오래된 앱은 즉시 수정할 수도 없습니다. 그래서 현재 키와 별도의 백업 키를 함께 고정하고, 겹치는 기간을 두고 단계적으로 교체하며, 만료·실패를 관측해야 합니다. 위험 대비 효과가 필요한 고위험 서비스인지 먼저 판단하고 도입해야 합니다.

**면접에서는 이렇게**

“인증서 고정은 운영체제의 일반 CA 신뢰 검증에 더해 우리 서버가 사용할 인증서나 공개 키를 앱이 별도로 확인하는 방식입니다. CA가 침해되거나 단말에 악성 인증서가 설치된 상황의 중간자 공격을 줄이지만, 인증서 교체가 앱 배포와 어긋나면 정상 통신도 전부 막는 위험이 있습니다. 그래서 백업 핀, 겹치는 교체 기간, 모니터링과 단계적 배포까지 함께 설계해야 합니다.”

**상태** 미학습 → 오답 (0점)

## 4. [AND-031] 앱 번들과 동적 기능 모듈 — 0점

답을 모른다고 명시했으므로 오답입니다. 신규 문항은 `AND-031`로 등록했고, 답안 원문은 미작성 상태로 남겼습니다.

**핵심 개념**

Android App Bundle은 단말에 직접 설치하는 파일이 아니라 앱 마켓에 게시하는 형식입니다. 마켓은 번들에서 기기의 ABI·화면 밀도·언어 등에 맞는 기본 APK와 구성 APK를 만들어 필요한 코드와 자원만 전달합니다. 동적 기능 모듈은 기본 모듈과 분리한 기능을 설치 시점, 조건부 또는 사용자가 필요로 하는 시점에 추가로 전달해 초기 다운로드 크기를 줄입니다.

**설계 기준과 실패 처리**

용량이 크고 일부 사용자만 쓰며 늦게 받아도 되는 기능에 적합합니다. 로그인처럼 첫 실행의 핵심 기능이거나 분리로 줄어드는 크기가 작은 경우에는 복잡성의 이득이 적습니다. 앱은 기능이 아직 없다는 상태를 전제로 진행률·취소·재시도·저장 공간 부족·오프라인·설치 실패를 UI 상태로 다뤄야 하며, 설치 완료 전에는 해당 구현을 직접 참조해 실행한다고 가정해서는 안 됩니다.

**면접에서는 이렇게**

“AAB는 설치 파일 자체가 아니라 마켓이 기기별 최적화 APK를 생성하도록 코드와 자원을 묶어 올리는 게시 형식입니다. 동적 기능은 선택 기능을 기본 앱에서 분리해 설치 시점이나 사용 시점에 전달합니다. 초기 크기는 줄지만 모듈 경계와 설치 상태 관리가 복잡해지므로, 크고 선택적인 기능에만 적용합니다. 화면은 미설치·다운로드 중·설치 완료·실패를 명시적으로 모델링하고 오프라인과 재시도 경로를 제공해야 합니다.”

## 5. [HIL-002] 네비게이션 조립 모듈 결정 — 3점

**맞은 부분**

각 기능 모듈이 자기 네비게이션 트리 구성 책임을 갖는다는 구조, 별도 중앙 모듈이 모든 기능과 접점을 갖게 된다는 비용, 공통 계약 설계가 어려워질 수 있다는 대가를 설명했습니다. 프로젝트 결정을 단순 취향이 아니라 책임과 의존성 관점에서 말한 점은 좋았습니다.

**빠진 부분**

결정의 마지막 기준은 앱 모듈에 남는 조립 코드가 작아 별도 모듈로 떼어 낼 실익이 없었다는 점입니다. 별도 모듈은 의존성을 없애기보다 조립 책임과 모든 기능을 향한 의존성을 다른 곳으로 옮기고 모듈 하나를 추가합니다.

**틀린 부분**

각 기능이 자기 트리를 구성해도 앱 모듈의 네비게이션 책임이 완전히 없어지는 것은 아닙니다. 앱은 기능 모듈들이 제공한 트리를 최종적으로 합치는 조립 책임을 계속 갖습니다. 답변 후반은 이 책임도 사라지는 것처럼 읽혀 경계를 부정확하게 만들었습니다.

**면접에서는 이렇게**

“각 기능 모듈은 자기 화면과 네비게이션 트리를 구성하고, 앱 모듈은 그 결과를 합쳐 최상위 그래프를 만드는 역할만 합니다. 별도 네비게이션 모듈을 두어도 모든 기능을 향한 조립 의존성이 그 모듈로 이동할 뿐이고, 앱에 남는 합성 코드도 작았습니다. 따라서 모듈과 계약을 하나 더 유지할 비용보다 분리 이익이 작다고 판단했습니다.”

**상태** 미학습 → 불안정 (3점)

## 6. [DI-001] 의존성 주입과 저장소 패턴 — 3점

**맞은 부분**

객체가 필요한 의존성을 내부에서 만들지 않고 외부에서 받는다는 정의가 정확합니다. 구체 구현을 그대로 주입하면 생성 결합은 줄어도 구현 결합은 남는다는 구분도 이전보다 훨씬 정확해졌습니다.

**빠진 부분**

저장소 패턴은 모든 구현 결합을 해결하는 일반적인 인터페이스 도구가 아닙니다. 데이터 계층에서 호출자에게 일관된 접근 계약을 제공하고 원격·로컬·캐시 같은 데이터 출처와 조합 정책을 감추는 구체적인 역할을 가집니다. 구현체 대신 추상 계약에 의존하게 만드는 일반 원리는 의존성 역전이며, 저장소는 그 원리를 데이터 접근 경계에 적용한 한 형태입니다.

**틀린 부분**

객체의 관리·해제를 외부가 맡는 것은 DI라는 원칙 자체의 필수 효과가 아닙니다. 수동 주입에서는 호출자가 단순히 이미 만든 객체를 넘길 수도 있습니다. Hilt 같은 DI 컨테이너가 범위와 생명주기를 관리할 때 생성·보관·해제를 함께 맡는 것입니다.

**면접에서는 이렇게**

“의존성 주입은 객체가 필요한 협력자를 직접 생성하지 않고 외부에서 받게 해 생성 책임을 분리하는 방식입니다. 추상 타입을 주입하면 구현 교체와 테스트 대역 사용도 쉬워지지만, 구체 타입을 받으면 구현 결합은 남습니다. 저장소 패턴은 별개로 데이터 접근 계약을 제공해 원격·로컬 같은 출처를 감추는 패턴이고, DI는 그 저장소 구현을 사용하는 객체에 연결하는 수단입니다. 컨테이너를 쓰면 여기에 범위와 생명주기 관리가 더해질 수 있습니다.”

**상태** 불안정 유지 (3점)
