## 1. [CMP-025] Compose에서 `CompositionLocal`로 값을 전달하기에 적합한 경우는 언제인가요? 일반 매개변수 전달과 비교한 선택 기준과 잘못 사용했을 때의 문제도 설명해 주세요

`platform/compose` · 실무 · 이전 오답 · 지난 지적: 트리 범위 값 전달이라는 성격과 사용 기준을 설명하지 못함

### 내 답변

특정 Composable을 루트로 하는 트리에서 명시적 매개변수로 내리기에는 지나치게 비효율적 - 예를 들어 매개변수의 절대적 개수 자체가 늘어나 함수 서명이 지저분해지거나, 트리 내 특정 자식을 건너뛰면서도 매개변수가 전달되어야 할 때 등 - 일 경우 암시적 매개변수로 보내주기 위해 사용한다. 보통 `CompositionLocalProvider`로 스코프를 지정하고, 해당 스코프 아래에 위치하는 모든 Composable이 접근 가능하다. 목적의 특수함으로 인해 보통 테마나 디자인 시스템 정보 접근 등에 대표적으로 쓰인다.

일반 매개변수와는 달리 명시적으로 전달되는 것이 아니기에, 만약 해당 변수가 수정 가능하다면 어디서 왜 어떻게 수정되었는지를 파악하기 어렵다. 자원 점유에 관한 경쟁 상황에 대비할 필요가 있다.

## 2. [AND-030] 런타임 권한이 필요한 기능을 사용자가 실행했습니다. 권한 확인부터 요청 결과 처리, 거부 후 재요청, 설정 화면 안내까지의 흐름을 설명해 주세요. 최초 요청과 영구 거부를 구분할 때 `shouldShowRequestPermissionRationale`과 앱의 요청 이력을 어떻게 함께 사용해야 하나요?

`platform/android` · 실무 · 이전 오답(2026-09-28) · 지난 지적: 권한 요청의 전체 흐름을 설명하지 못했고, `shouldShowRequestPermissionRationale`을 재요청 가능 여부로 잘못 이해했으며, 최초 요청과 영구 거부의 구분 방법을 설명하지 못함

### 내 답변

Native API로 권한 요청 후 성공 시에는 정상 플로우로 넘어가고 실패 시에는 권한이 필요한지에 대한 추가 설명이 필요한데 이 필요성 여부를 나타내는 변수가 `shouldShowRequestPermissionRationale`. 다만 이 변수는 오직 추가 설명 여부에 관한 값만 반환하며 몇 번이나 재요청이 이루어졌었는지는 기억하지 않기 때문에, 재요청 횟수의 경우 앱 측에서 별도 카운팅 방법을 마련해야 함. 사용자가 추가 설명을 읽은 후에도 거부한다면 그 때부터는 시스템 설정으로 넘어가게 됨.

## 5. [HIL-002] Hilit 프로젝트에서 별도 `:navigation` 모듈을 만들지 않고 앱 모듈이 네비게이션을 조립하게 한 이유를, 기능 모듈과 앱 모듈의 책임 경계 및 분리 비용 관점에서 설명해 주세요

`project/hilit` · 실무 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

별도 네비게이션 모듈을 만들 경우 해당 모듈은 다른 전체 기능 모듈을 의존성으로 가지게 됨. 단일 모듈에서 네비게이션을 관리한다는 이점은 있겠으나, 다른 모든 기능 모듈과의 접점이 생기기 때문에 모듈 간 결합도가 증가하는 문제 발생.

Hilit 프로젝트에서는 Navigation 3를 채택하고, 트리 구성 책임을 기존처럼 앱 모듈 혹은 앱 모듈에 가까운 네비게이션 모듈이 하는 게 아니라, 각 기능 모듈로 옮겼음. 이렇게 할 경우 공통 네비게이션 계약 수립이 추상적이고 어려울 수 있다는 단점은 있지만, 이 계약 하에 각 모듈 계층에서 라우팅 테이블을 구성할 수 있게 되어 앱 모듈이 네비게이션이라는 추가 책임을 맡음으로서 결합도가 높아지거나 네비게이션을 위한 별도의 모듈을 생성할 일이 없어지게 됨.

## 6. [DI-001] 의존성 주입은 무엇이며 어떤 결합을 줄이나요? 의존성 주입만으로는 줄어들지 않는 구현 결합을 구분하고, 데이터 출처를 감추는 저장소 패턴과 역할이 어떻게 다른지도 설명해 주세요

`platform/di` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-11) · 지난 지적: 저장소 패턴의 접근 계약을 별도로 정의하지 못했고, 의존성 주입이 모든 결합도를 낮춘다고 과도하게 일반화함

### 내 답변

의존성 주입은 특정 클래스가 필요로 하는 매개변수를 해당 클래스가 생성하는 대신 외부에서 주입해주는 것을 의미.

해당 클래스는 클래스의 책임과는 거리가 있을 수 있는 매개변수 인스턴스의 생성 및 관리 책임을 맡을 필요가 없어지기에, 해당 클래스의 본연 책임에만 집중할 수 있게 됨.

다만 의존성 주입 시 인터페이스 등 추상 계약이 아닌 구현체로 넣어줄 경우, 생성 및 관리 책임만 덜어줄 뿐 해당 구현체와 이 구현체를 사용하는 클래스 간 책임에 다소 차이가 있어 결합도가 늘어나는 부분은 해결하기 어려움.

저장소 패턴은 이 지점을 풀어주는 도구로, 의존성 주입과 함께 사용할 경우 클래스가 인터페이스 등 추상 계약에만 의존할 수 있도록 함으로써, 클래스를 매개변수 인스턴스의 세부 구현으로부터 분리해줌.

정리하면 의존성 주입은 특정 클래스가 매개변수 인스턴스를 생성, 관리, 해제할 책임을 덜어주며, 저장소 패턴은 클래스-인스턴스 계약을 추상 계약으로 정립해 클래스가 구현체를 몰라도 동작하는 데 지장이 없도록 하여 더 근본적인 결합도 개선에 도움을 줌.
