## 1. [CMP-017] Compose에서 `Stable`과 `Skippable`은 각각 무엇을 의미하나요? — 2점

**맞은 부분**

매개변수가 2에서 1로 달라졌다면 화면에 그려지는 색이 우연히 같더라도 해당 함수의 실행을 결과만 보고 건너뛰지는 않는다는 결론은 맞았습니다.

**빠진 부분**

`Stable`은 재구성이 필요 없다는 뜻이 아니라, 같은 두 인스턴스에 대한 `equals` 결과가 유지되고 공개 속성이 바뀌면 Compose가 이를 알 수 있으며 공개 속성의 타입도 안정적이라는 타입 계약입니다. `Skippable`은 재구성 시점에 이전 호출과 비교해 매개변수가 모두 같으면 함수 실행을 생략할 수 있다는 함수의 성질입니다. 현재 기본인 강한 건너뛰기 모드에서는 안정 매개변수는 동등성으로, 불안정 매개변수는 참조 동일성으로 비교합니다.

**틀린 부분**

"추적 중인 상태 값이 변하면 항상 재구성한다"는 설명은 너무 넓습니다. 상태 변경은 재구성 대상을 무효화하지만, 실제 함수 실행을 건너뛸지는 해당 함수의 건너뛰기 가능 여부와 매개변수 비교로 결정합니다.

**면접에서는 이렇게**

"`Stable`은 Compose가 값의 변경을 신뢰성 있게 추적할 수 있다는 타입 계약이고, `Skippable`은 재구성 때 입력이 이전과 같으면 Composable 실행을 생략할 수 있다는 뜻입니다. `Int` 매개변수가 2에서 1로 바뀌면 값이 다르므로, 두 값이 같은 색을 만들더라도 Compose는 함수 결과를 미리 비교하지 않고 실행합니다."

**상태** 오답 → 불안정 (2점)

## 2. [SEC-004] 네이티브 앱에서 PKCE를 적용한 OAuth 2.0 인가 코드 흐름 — 1점

**맞은 부분**

최종적으로 액세스 토큰을 발급받는 흐름이라는 점과, 네이티브 앱에 고정 비밀을 넣으면 공격자가 추출할 수 있다는 방향은 짚었습니다.

**빠진 부분**

앱이 매 요청마다 무작위 `code_verifier`를 만들고, 그 값을 SHA-256과 Base64 URL 인코딩으로 변환한 `code_challenge`를 인가 요청에 보내는 단계가 없습니다. 로그인과 동의 후 앱에는 PKCE가 아니라 인가 코드가 돌아옵니다. 앱은 인가 코드와 원본 `code_verifier`를 토큰 엔드포인트에 보내고, 인가 서버는 둘의 대응을 검증한 뒤 토큰을 발급합니다.

**틀린 부분**

PKCE는 서버가 앱에 반환하는 값이 아니며, 앱이 받은 PKCE에 API 키를 붙이는 흐름도 아닙니다. 고정 클라이언트 비밀의 문제도 단순히 복호화 중 메모리에 남는다는 데 한정되지 않습니다. 여러 사용자에게 배포한 앱 바이너리 자체를 사용자가 분석할 수 있으므로 같은 비밀을 기밀로 간주할 수 없고, 앱 신원의 증명으로 받아들여서는 안 됩니다.

**면접에서는 이렇게**

"앱은 요청마다 `code_verifier`를 만들고 그 해시인 `code_challenge`와 `client_id`, 리디렉션 URI를 브라우저 기반 인가 요청에 보냅니다. 사용자가 인증·동의하면 앱은 인가 코드를 받고, 이를 원본 `code_verifier`와 함께 토큰 엔드포인트에 교환합니다. 서버는 verifier에서 challenge를 다시 계산해 일치할 때만 토큰을 발급하므로, 코드를 가로챈 앱은 verifier가 없어 교환하지 못합니다. 네이티브 앱에 포함된 고정 비밀은 바이너리에서 추출 가능하므로 클라이언트 인증 수단이 아닙니다."

**상태** 오답 유지 (1점)

## 3. [AND-007] Android 앱의 권장 아키텍처 — 2점

**맞은 부분**

관심사를 모듈별로 나누려는 방향, 앱 모듈의 조립 책임, 상태는 아래로 내리고 이벤트는 위로 올리는 단방향 데이터 흐름은 맞았습니다. 코루틴과 Flow를 작업 성격에 맞춰 선택해야 한다는 인식도 있습니다.

**빠진 부분**

권장 아키텍처의 기본은 모듈 개수가 아니라 UI 계층과 데이터 계층의 책임 분리입니다. UI 계층은 화면과 상태 보유자가 상태를 표시하고 사용자 이벤트를 받으며, 데이터 계층은 저장소를 통해 애플리케이션 데이터와 대부분의 비즈니스 로직을 제공합니다. 도메인 계층은 여러 `ViewModel`에서 재사용하거나 복잡한 로직을 단순화할 필요가 있을 때 두는 선택 계층입니다. 계층 간 갱신 관찰에는 Flow, 일회성 작업에는 `suspend` 함수를 사용하는 식의 계약까지 설명해야 했습니다.

**틀린 부분**

멀티 모듈은 규모에 따른 구현 선택이지 Android 권장 아키텍처의 전제 조건이 아닙니다. 도메인·데이터·네트워크 모듈을 한 단계로 묶어 모두 데이터 획득과 변환 책임을 가진다고 한 것도 계층 책임을 흐립니다. 단일 진실 공급원은 무조건 클라우드가 아니라 해당 데이터의 수정 권한을 가진 유일한 소스이며, 오프라인 우선 앱에서는 보통 로컬 데이터베이스가 맡습니다.

**면접에서는 이렇게**

"Android 앱은 최소 UI와 데이터 계층으로 나누고, 복잡하거나 재사용할 비즈니스 로직이 있을 때 도메인 계층을 추가합니다. 저장소가 데이터 소스를 감싸고 단일 진실 공급원에서 나온 데이터를 Flow로 노출하며, UI는 `ViewModel`의 불변 상태를 생명주기에 맞춰 수집합니다. 상태는 UI로 내려가고 사용자 이벤트는 상태 보유자로 올라가는 단방향 흐름을 유지합니다. 모듈 분리는 이 책임 경계를 물리적으로 강화하는 선택이지 필수 조건은 아닙니다."

**상태** 미학습 → 불안정 (2점)

## 4. [AND-030] Android 런타임 권한 요청 흐름 — 1점

**맞은 부분**

기능 실행 시 현재 권한을 확인하고, 없으면 시스템 권한 요청을 하며, 더 이상 대화상자로 해결할 수 없다면 설정 화면 안내를 고려한다는 큰 방향은 맞았습니다.

**빠진 부분**

`checkSelfPermission`으로 승인 여부를 확인하고, 필요하면 `shouldShowRequestPermissionRationale`에 따라 권한이 기능에 왜 필요한지 설명한 뒤 `ActivityResultContracts.RequestPermission`으로 요청하는 흐름이 필요합니다. 결과가 거부라면 기능을 축소하거나 대안을 제공해야 합니다. 설정 이동 안내는 권한이 꼭 필요한 기능을 사용자가 다시 선택했고 시스템 대화상자를 더 보여 줄 수 없는 상황에서 강요하지 않는 방식으로 제공해야 합니다.

**틀린 부분**

항상 "1회 재요청 가능하고 두 번째 거부부터 요청이 막힌다"는 고정 규칙은 아닙니다. Android 버전과 사용자의 선택에 따라 동작이 달라지며, `shouldShowRequestPermissionRationale`도 재요청 횟수를 알려 주는 API가 아닙니다. 최초 요청 전과 다시 묻지 않음 상태에서 모두 `false`일 수 있으므로 앱이 이전 요청 여부를 함께 관리해야 합니다.

**면접에서는 이렇게**

"사용자가 권한이 필요한 기능을 실행한 시점에 승인 여부를 확인합니다. 이미 승인됐으면 기능을 실행하고, 설명이 필요하면 근거 UI를 보여 준 뒤 Activity Result API로 요청합니다. 거부되면 기능을 안전하게 축소하고, 다시 요청할 수 있을 때만 사용자 행동을 계기로 재요청합니다. 더 이상 시스템 대화상자가 나오지 않는 상태라면 기능 필요성을 설명하고 설정 화면 이동 선택지를 제공합니다."

**상태** 미학습 → 오답 (1점)

## 5. [JK-005] Kotlin의 `data class` — 2점

**맞은 부분**

데이터 보관에 특화된 목적, `copy`, `equals`, `hashCode` 자동 생성, 주 생성자에 적어도 하나의 속성이 필요하다는 제약을 설명했습니다. `copy`에서 바꿀 값만 지정할 수 있다는 설명도 맞습니다.

**빠진 부분**

컴파일러는 `toString`과 구조 분해에 쓰는 `componentN`도 만듭니다. 자동 생성 함수는 클래스 본문의 모든 필드가 아니라 주 생성자에 선언한 속성만 사용합니다. `copy`는 내부 객체까지 복제하지 않는 얕은 복사라는 점도 실무 질문에서 자주 이어집니다. 정확한 선언 제약은 주 생성자에 하나 이상의 매개변수가 있고 모두 `val` 또는 `var`여야 하며, `abstract`, `open`, `sealed`, `inner`가 될 수 없다는 것입니다.

**틀린 부분**

일반 클래스의 `equals`가 해시 코드로 비교한다는 설명은 틀렸습니다. `Any.equals`의 기본 구현은 참조 동일성을 따르며, `hashCode`는 해시 기반 자료구조에서 후보를 좁히는 데 쓰일 뿐 동등성 자체를 판정하지 않습니다. `data class`는 다른 클래스의 상속 대상이 될 수 없지만 다른 클래스를 상속할 수는 있습니다.

**면접에서는 이렇게**

"`data class`는 값을 표현하는 클래스의 반복 코드를 줄입니다. 주 생성자의 속성을 기준으로 `equals`, `hashCode`, `toString`, `componentN`, 얕은 `copy`를 생성합니다. 주 생성자에는 하나 이상의 `val` 또는 `var`가 필요하고 `open`이나 `abstract`로 선언할 수 없습니다. 클래스 본문에만 둔 속성은 생성 함수들의 비교·복사 대상에서 제외됩니다."

**상태** 미학습 → 불안정 (2점)

## 6. [OS-001] 프로세스와 스레드의 차이 — 2점

**맞은 부분**

같은 프로세스의 스레드가 코드와 전역 데이터를 공유하고, 각 스레드는 스택·프로그램 카운터·레지스터 문맥을 따로 가진다는 핵심은 설명했습니다. 프로세스를 자원 소유 단위, 스레드를 운영체제 스케줄링 단위로 구분한 결론도 맞습니다.

**빠진 부분**

프로세스마다 독립된 가상 주소 공간과 코드·데이터·힙, 열린 파일 등의 자원을 가지고, 그 프로세스 안의 스레드끼리 이를 공유한다고 범위를 명확히 해야 합니다. PCB에는 프로세스 상태, 식별자, 스케줄링·메모리 관리·열린 파일 관련 정보 등이 저장된다는 설명도 필요합니다.

**틀린 부분**

"프로세스와 스레드는 코드, 전역 데이터를 공유한다"고 하면 서로 다른 프로세스끼리도 공유하는 것으로 들려 틀립니다. PCB가 프로세스의 주소 공간 안에 포함되는 것도 아닙니다. PCB는 운영체제 커널이 프로세스를 관리하기 위해 유지하는 자료구조입니다.

**면접에서는 이렇게**

"프로세스는 독립된 가상 주소 공간과 코드·데이터·힙, 파일 같은 자원을 가진 자원 소유 단위이고, 운영체제는 이를 PCB로 관리합니다. 같은 프로세스 안의 스레드는 그 자원을 공유하지만 각자 스택과 프로그램 카운터, 레지스터 문맥을 가집니다. 그래서 스레드는 독립적으로 실행되고 운영체제가 스케줄링하는 단위입니다."

**상태** 불안정 유지 (2점)

## 이번 세션에서 드러난 흐름

큰 방향이나 사용 경험은 떠올리지만, 용어의 정확한 정의와 프로토콜·API의 단계가 비어 있어 맞는 말과 틀린 말이 함께 나오는 경향이 두드러졌습니다. 특히 OAuth와 런타임 권한은 구현 경험의 인상으로 추측하지 말고 순서도처럼 단계와 분기 조건을 다시 학습해야 합니다. Compose·아키텍처·운영체제는 결론을 외우기보다 "무엇이 무엇을 소유하고, 누가 변경을 판단하는가"를 주어로 세워 설명하는 연습이 필요합니다.
