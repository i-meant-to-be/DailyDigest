## 1. [CMP-017] Compose에서 `Stable`과 `Skippable`은 각각 무엇을 의미하나요? 매개변수가 2에서 1로 바뀌었지만 결과 색상은 같은 경우, Compose가 재구성을 건너뛸 수 있는지도 근거와 함께 설명해 주세요

`platform/compose` · 실무 · 이전 오답(2026-09-10) · 지난 지적: `Stable`의 변경 추적 계약과 `Skippable`의 입력 동일성 조건을 혼동했고, 출력이 같으면 자동으로 실행을 생략한다고 잘못 이해함

### 내 답변

`Stable`은 재구성(Recomposition)이 필요 없는 경우, `Skippable`은 재구성을 생략할 수 있는 경우를 의미.

매개변수가 2에서 1로 바뀌었지만 결과 색상은 같은 경우, Compose는 재구성을 건너뛸 수 없음. 왜냐하면 재구성 조건 자체가 추적 중인 상태 값의 변화이기 때문에 그 결과가 결론적으론 동일하다고 하더라도 조건이 충족되어 재구성은 진행됨.

## 2. [SEC-004] 네이티브 앱에서 PKCE를 적용한 OAuth 2.0 인가 코드 흐름을 단계별로 설명해 주세요. `code_verifier`와 `code_challenge`의 역할, 고정된 클라이언트 비밀이 앱의 신원을 증명할 수 없는 이유도 포함해 주세요

`platform/security` · 실무 · 이전 오답(2026-09-11) · 지난 지적: 인가 코드 대신 액세스 토큰이 바로 돌아온다고 설명했고, PKCE의 구성 요소와 코드 가로채기 방지 원리 및 네이티브 앱 클라이언트 비밀의 한계를 알지 못함

### 내 답변

1. 앱이 제3자 인증 서비스에 API 키와 함께 로그인 요청
2. 제3자 인증 서비스는 API 키를 검증하고 유효한 경우 로그인 요청을 처리하고, 사용자의 신원이 확인되면 PKCE를 반환
3. 앱은 받은 PKCE에 API 키를 붙여 서비스 서버에 다시 인증 요청
4. 서비스 서버는 PKCE와 API 키를 제3자 인증 서비스에 다시 전달하여 이 인증 요청이 인증된 서비스와 사용자에게서 왔음을 검증받고, 제3자 인증 서비스는 유효한 경우 성공했음을 반환
5. 서비스 서버는 성공 응답을 확인한 후 액세스 토큰과 리프레시 토큰을 발급해 앱에 전달

`code_verifier`와 `code_challange`의 역할은 모르며, 고정된 클라이언트 비밀이 앱의 신원을 증명할 수 없는 이유는 암/복호화 과정에서 결국은 키 원본이 메모리에 남기 때문. 이 지점을 공격 시도하면 결국 뚫릴 수밖에 없음.

## 3. [AND-007] Android 앱의 권장 아키텍처를 계층별 책임과 데이터 흐름 중심으로 설명해 주세요. 단일 진실 공급원, 단방향 데이터 흐름, 코루틴과 Flow 사용 원칙도 함께 말해 주세요

`platform/android` · 실무 · 답을 적어 둔 적 없는 문항

### 내 답변

일단 아키텍처는 단방향으로, 그리고 순환 없이 구성되어야 한다는 전제 조건이 있다. Android 프로젝트에서는 멀티 모듈 아키텍처를 권장하며 그에 따른 예시 구성은 다음과 같다:

- 최상위는 앱 모듈. 앱 조립이 주 책임이다. 하위 기능 모듈과 기타 필요한 모듈을 통해 앱을 조립하고 빌드한다.
- 그 다음은 기능 모듈. 각 기능을 구현하는 게 주 책임이다. 하위에 위치한 데이터 관련 모듈을 활용하여 필요한 데이터를 정제하고 이를 UI로 내보낸다.
- 그 다음은 도메인 모듈, 데이터 모듈, 네트워크 모듈 등. 데이터를 페칭하고 앱에서 사용할 수 있는 형태로 변환하는 게 주 책임이다. 도메인 모델을 정의하고, 로컬 또는 리모트에서 데이터를 페칭해 오거나, 리모트와 통신하기 위한 네트워크 기능 등을 구현한다.
- 필요한 경우 여러 모듈에서 공유 가능한 암호화 또는 토큰 모듈, 테스트 모듈, 공용 기능 모듈 등을 추가로 구성할 수 있다.

그 외 중요한 사항으로는 SSoT(Single Source of Truth)가 있는데 이는 단일 진실 공급원이라고도 표현 가능하며 모든 데이터는 엄격하게 하나의 소스를 그 원천으로 간주해야 한다는 것이다. 예를 들어 연락처 앱을 개발한다고 할 때 이 앱 데이터가 로컬에도 있고 클라우드에 백업도 되어 있다면 보통 SSoT를 클라우드로 보고 여기에 데이터 동기화 기준을 맞춰야 한다. 단방향 데이터 흐름(UDF)이라는 원칙도 중요한데 이는 특히 Composable에서 상태를 관리할 때 중요하게 적용되는 원칙으로써 상태는 위(루트)에서 아래(서브 Composable)로, 신호는 아래에서 위로 올라가야 하며, 이 방향은 바뀌어서는 안 된다는 원칙을 말한다. 코루틴 사용 시에는 비동기 처리 작업의 특성에 맞는 `Dispatcher`를 사용해야 하며, 코루틴 취소로 인해 `CancelationException`이 발생할 경우 이 예외를 던질지 말지 로직을 신중히 구성해줘야 한다. Flow의 경우 종류가 매우 다양하다. 어떤 것은 Hot flow, 어떤 것은 Cold flow이며, 최신 값을 들고 있는 것도 있고 일단 값을 내보내면 유지하지 않는 경우도 있다. 따라서 필요한 상황에 맞는 Flow를 골라 사용해야 한다.

## 4. [신규] Android에서 런타임 권한이 필요한 기능을 실행하려 할 때, 권한 상태 확인부터 요청·거부·재요청·설정 화면 안내까지 어떤 흐름으로 처리해야 하나요?

`platform/android` · 실무 · 주제 대장 공백 — 지식 파일에 아직 없는 주제

### 내 답변

정확히 기억은 안 나지만 권한 상태를 확인할 수 있는 네이티브 API로 권한이 있는지 확인할 수 있다. 없으면 권한 요청을 보낸다.

만약 거부될 경우 1회 재요청이 가능하며 이 사양 역시 API 함수 내에 있었던 걸로 기억한다. 단, 재요청까지 거부될 경우 그 다음부터는 요청이 막히며, 사용자가 설정 화면에 가서 직접 권한을 조작할 수 있도록 유도해야 한다.

## 5. [JK-005] Kotlin의 `data class`는 일반 클래스와 비교해 어떤 목적과 특징을 가지나요? 컴파일러가 생성하는 함수와 선언 제약을 설명해 주세요

`lang/java-kotlin` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

`data class`는 DTO 등 데이터 묘사를 위한 클래스에 최적화되어 있음. 특히 일반 클래스와는 달리 컴파일러가 DTO에 필요한 함수를 사전 생성해두거나 기존 함수를 적절히 오버라이딩한다는 점에서 차이가 있음. 다만, 데이터 묘사가 주 목적인 만큼 `data class`로 선언된 클래스를 상속하는 행위는 금지되어 있음. 또한 생성자 없이도 선언 가능한 일반 클래스와는 달리 `data class`는 `()` 안에 반드시 생성자와 필요한 멤버 변수를 명시해줘야 함.

컴파일러가 자동으로 생성하는 함수로는 다음과 같은 것들이 있음:

- `copy`: 호출자가 잡고 있는 데이터를 그대로 가지고 있는 새로운 인스턴스를 반환. 필요한 경우 매개변수에서 바꾸고 싶은 변수만 특정하여 값을 바꿔줄 수 있음.
- `equals`: 두 인스턴스의 동일 여부를 판단하는 함수로 일반 클래스에서는 해시 코드로 비교했으나 `data class`에서는 전체 필드의 동등 여부를 비교하도록 수정하여 컴파일됨.
- `hashCode`: 전체 필드를 기반으로 해시 코드를 생성.

## 6. [OS-001] 프로세스와 스레드가 각각 소유하거나 공유하는 자원과 실행 문맥을 비교해 주세요. PCB와 스레드별 프로그램 카운터·레지스터·스택, 운영체제의 스케줄링 단위도 포함해 설명해 주세요

`cs/os` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-06) · 지난 지적: PCB를 주소 공간 포인터로 오인했고, 작업 분배와 운영체제 스케줄링을 혼동했으며 스레드별 프로그램 카운터·레지스터 설명을 누락함

### 내 답변

프로세스와 스레드는 코드, 전역 데이터를 공유. 프로세스 유지/관리를 위해 OS가 저장하는 데이터인 PCB(Process Control Block)는 프로세스 영역에만 포함. 반면, 스레드는 지역 작업을 위한 스택을 각 스레드별로 따로 가짐. 이 때 각 스레드는 각자마다 다른 코드에서 다른 작업을 수행해야 하기 때문에 PC도 전부 따로 가지며, 따라서 연산을 위한 레지스터 공간도 따로 가짐.

운영체제의 관점에서는 프로세스는 각 스레드가 공통으로 사용할 자원을 소유하므로 자원 소유권의 단위이며, 스레드는 나눠진 작업을 운영체제에 의해 분배받아 수행하므로 스케줄링 단위로 이해됨.
