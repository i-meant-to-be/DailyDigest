## 1. [SEC-001] Android KeyStore — 2점

**맞은 부분**

키를 별칭으로 조회하고, 키 재료를 애플리케이션 코드에 직접 노출하지 않은 채 암호 연산에 사용할 수 있다는 핵심 방향을 짚었습니다. 일반 파일에 키 바이트를 저장하는 것보다 키 탈취 위험을 낮춘다는 비교도 맞습니다.

**빠진 부분**

KeyStore는 키의 추출 방지뿐 아니라 키의 사용 조건을 운영체제가 강제할 수 있습니다. 사용자 인증 필요 여부, 사용 가능한 암호 연산, 유효 기간 등을 지정할 수 있고, 기기가 지원하면 TEE나 StrongBox 같은 보안 하드웨어 내부에서 키 생성과 연산을 수행할 수도 있습니다. 하드웨어 보호는 모든 키에 자동으로 보장되는 것이 아니라 생성 옵션과 기기 지원 여부를 확인해야 합니다.

**틀린 부분**

KeyStore가 “개발자의 악용” 자체를 막는다고 설명한 것은 위협 모델이 잘못됐습니다. 키 바이트를 읽지 못하더라도 해당 앱 코드가 키 사용 권한을 가지고 있으면 KeyStore에 복호화 연산을 요청할 수 있습니다. 또한 일반적으로 개발자는 KeyStore 자체에 평문을 넘겨 암호문을 바로 받는다고 표현하기보다, 별칭으로 얻은 비추출 키를 `Cipher` 같은 암호 API에 연결해 연산한다고 설명해야 정확합니다.

**면접에서는 이렇게**

“Android KeyStore는 키를 별칭으로 관리하고, 키 재료를 앱 프로세스 밖으로 내보내지 않은 채 암호 연산에 사용하게 합니다. 키 사용 목적과 사용자 인증 같은 제약을 운영체제가 강제하며, 지원 기기에서는 TEE나 StrongBox로 추출 저항성을 더 높일 수 있습니다. 일반 파일에 키 바이트를 저장하면 파일 접근이나 백업·디버깅·루팅 환경에서 키가 그대로 노출될 수 있지만, KeyStore는 키 자체의 추출을 어렵게 합니다. 다만 앱이 가진 복호화 권한의 오용까지 막아 주는 것은 아닙니다.”

**상태** 미학습 → 불안정 (2점)

## 2. [SEC-015] 운영 환경 로그 보안 — 2점

**맞은 부분**

이름·전자우편 주소·식별자 같은 개인정보와 암호 키·평문을 로그에서 제외해야 한다는 방향은 맞습니다. 불가피한 값은 마스킹해야 한다는 점도 언급했습니다.

**빠진 부분**

비밀번호, 액세스·리프레시 토큰, 세션 식별자, 인증 헤더, 쿠키, 결제 정보처럼 곧바로 계정 탈취나 재사용 공격으로 이어질 수 있는 값을 우선 언급해야 합니다. 진단 로그는 허용 목록 방식으로 필요한 필드만 구조화해 남기고, 민감 값 대신 상관관계 ID나 오류 코드처럼 재현에 필요한 비민감 정보를 써야 합니다. 운영 환경의 로그 수준, 접근 권한, 보존 기간과 삭제 정책도 함께 관리해야 합니다.

**틀린 부분**

모든 관련 타입의 `toString`을 “의미 없는 값”으로 반드시 재정의해야 한다는 주장은 지나치게 절대적입니다. 실수로 객체 전체를 출력하지 않는 설계와 중앙 마스킹·필터링이 우선이며, `toString` 재정의는 민감 데이터 타입에 적용할 수 있는 방어 수단 중 하나입니다. 암호문도 문맥에 따라 민감하거나 재사용 가능한 데이터일 수 있지만, 암호 키·토큰·평문과 위험이 동일하다고 뭉뚱그리면 안 됩니다.

**면접에서는 이렇게**

“운영 로그에는 비밀번호, 인증 토큰과 헤더, 세션·쿠키, 암호 키, 개인정보, 요청·응답의 민감 본문을 남기지 않습니다. 먼저 필요한 항목만 허용 목록으로 정하고, 사용자 값 대신 상관관계 ID와 오류 코드 같은 비민감 진단 정보를 구조화해 기록합니다. 일부 식별이 필요하면 최소 부분만 마스킹하거나 단방향 처리하고, 운영 로그 수준·접근 권한·보존 기간도 제한합니다. 객체 전체나 네트워크 본문을 습관적으로 출력하지 않도록 중앙 로깅 계층에서 필터링합니다.”

**상태** 미학습 → 불안정 (2점)

## 3. [AND-003] Context — 1점

**맞은 부분**

Application Context는 애플리케이션과, Activity Context는 해당 Activity와 생명주기를 함께한다는 구분은 맞았습니다. 장기 객체에는 더 긴 생명주기의 Context를 고려해야 한다는 방향도 잡았습니다.

**빠진 부분**

Context는 데이터와 상태를 저장하는 장소가 아니라 리소스, 시스템 서비스, 컴포넌트 실행 등 애플리케이션 환경과 Android OS 기능에 접근하는 인터페이스입니다. Activity Context는 화면 테마와 창에 연결되므로 대화상자 표시나 테마가 필요한 UI 생성에 적합하고, Application Context는 특정 화면과 무관한 장기 작업이나 앱 전역 객체에 적합합니다.

**틀린 부분**

메모리 누수의 참조 방향을 반대로 설명했습니다. Activity가 Application Context를 참조하는 것은 보통 Activity의 수명을 늘리지 않습니다. 문제는 싱글턴처럼 오래 사는 객체가 Activity Context나 Activity를 붙잡아, 화면이 종료된 뒤에도 GC가 Activity를 회수하지 못하는 경우입니다. DB 객체가 Activity Context를 썼다고 Activity 종료와 동시에 사용할 수 없게 되는 것도 아닙니다. 더 중요한 문제는 그 객체가 파괴된 Activity를 붙잡아 누수를 만들거나 불필요하게 화면 생명주기에 결합되는 것입니다.

**면접에서는 이렇게**

“Context는 앱의 상태 저장소가 아니라 리소스와 시스템 서비스 등 Android 실행 환경에 접근하는 인터페이스입니다. Application Context는 앱 수명과 같아 DB 같은 앱 전역 객체에 적합하고, Activity Context는 해당 화면의 테마와 창에 연결돼 UI 작업에 필요합니다. 오래 사는 싱글턴이 Activity Context를 보관하면 종료된 Activity를 계속 참조해 메모리 누수가 생기므로, 필요한 기능과 보관 기간에 맞춰 선택해야 합니다.”

**상태** 미학습 → 오답 (1점)

## 4. [CMP-001] Recomposition과 remember — 3점

**맞은 부분**

관찰 가능한 상태가 바뀌면 그 상태를 읽은 범위를 중심으로 Recomposition이 예약되고, `remember`가 Recomposition 사이에서 값을 보관한다는 핵심을 설명했습니다. `remember`가 초기값 재계산을 막는 역할과 `Disposal`이라는 용어도 이번에는 정확히 말했습니다.

**빠진 부분**

`remember`는 값을 Composition에 보관할 뿐, 상태를 관찰 가능하게 만들거나 Recomposition을 직접 일으키지 않는다는 문장을 명시해야 합니다. Recomposition의 원인은 Compose가 읽기를 추적한 `MutableState`의 값 변경입니다.

**틀린 부분**

“`MutableState`로 추적되는 상태가 `remember`를 통해 저장되기 때문에 변화를 추적한다”는 설명은 두 역할을 다시 섞습니다. 외부에서 전달받은 `MutableState`도 `remember` 없이 읽으면 변화가 추적됩니다. 또한 트리 전체를 내려가며 매번 대상을 찾는다고 단정하기보다, Compose가 이전 Composition에서 상태 읽기 위치를 기록하고 영향을 받은 재구성 범위를 무효화한다고 설명하는 편이 정확합니다.

**면접에서는 이렇게**

“Composition 중 Compose는 어떤 재구성 범위가 어떤 상태를 읽었는지 추적합니다. 관찰 가능한 `MutableState`가 바뀌면 그 값을 읽은 범위가 무효화되어 Recomposition 대상이 됩니다. `remember`는 이 변화를 감지하는 API가 아니라 Composition에 값을 저장해 Recomposition 사이에 유지하는 API입니다. Composable이 Composition에서 빠지면 해당 위치에 기억된 값과 효과가 정리되는 Disposal 단계로 넘어갑니다.”

**상태** 불안정 유지 (3점)

## 5. [DI-001] 의존성 주입 — 3점

**맞은 부분**

객체가 의존성을 직접 생성하지 않고 외부에서 전달받는다는 정의가 정확합니다. 생성 책임 분리, 결합도 감소, 인터페이스를 통한 구현 교체, 테스트에서 가짜 구현 주입까지 이전에 빠뜨린 핵심을 이번에는 설명했습니다.

**빠진 부분**

의존성 주입과 인터페이스 분리는 서로 잘 어울리지만 같은 개념은 아닙니다. 구체 타입도 주입할 수 있으며, 인터페이스에 의존할 때 호출자가 구현 세부사항이 아니라 계약에 의존하게 된다는 의존성 역전 관점을 분명히 하면 더 좋습니다.

**틀린 부분**

저장소 패턴을 “데이터 소스의 인터페이스와 구현체를 분리하는 패턴”으로 정의한 것은 부정확합니다. 저장소는 하나 이상의 데이터 소스를 조정하고 상위 계층에 데이터 접근 계약을 제공하는 추상화입니다. 또한 가짜 구현은 보통 미리 정한 동작을 수행하는 구현체이고, 호출 검증 중심의 목 객체와 동일한 뜻은 아닙니다.

**면접에서는 이렇게**

“의존성 주입은 객체가 필요한 의존성을 직접 만들지 않고 외부에서 전달받는 방식입니다. 생성 책임을 조립 지점으로 옮겨 클래스가 본래 역할에 집중하게 하고, 호출자가 구체 구현 대신 인터페이스라는 계약에 의존하도록 만들 수 있습니다. 예를 들어 ViewModel에 저장소 인터페이스를 주입하면 운영 코드에서는 실제 저장소를, 단위 테스트에서는 네트워크 없이 원하는 결과를 반환하는 가짜 저장소를 넣어 독립적으로 검증할 수 있습니다.”

**상태** 불안정 유지 (3점)

## 6. [JK-001] 중위 표기 함수 — 2점

**맞은 부분**

`a add b`가 `a.add(b)`와 같은 호출이며, 왼쪽이 리시버이고 오른쪽이 하나의 매개변수라는 구조는 이번에는 구분했습니다.

**빠진 부분**

선언에는 `infix` 키워드가 필요하고, 멤버 함수 또는 확장 함수여야 하며, 매개변수는 기본값이나 가변 인자가 없는 정확히 하나여야 합니다. 질문에서 요구한 선언 조건 중 핵심 두 가지를 다시 빠뜨렸습니다.

**틀린 부분**

리시버와 매개변수의 타입이 모두 같은 `T`여야 한다는 제약은 없습니다. 예를 들어 `infix fun String.repeat(times: Int)`처럼 서로 다른 타입도 가능합니다. “두 피연산자의 중간에 들어가는 함수”보다는 온점과 괄호를 생략해 중위 표기로 호출할 수 있는 멤버 또는 확장 함수라고 정의해야 정확합니다.

**면접에서는 이렇게**

“중위 표기 함수는 `a.add(b)`를 `a add b`처럼 온점과 괄호 없이 호출할 수 있게 `infix`로 선언한 함수입니다. 멤버 함수 또는 확장 함수여야 하고, 기본값과 `vararg`가 없는 매개변수를 정확히 하나만 가져야 합니다. 왼쪽 `a`가 리시버이고 오른쪽 `b`가 매개변수이며 두 타입이 같을 필요는 없습니다.”

**상태** 불안정 유지 (2점)

## 이번 세션에서 드러난 흐름

정의와 사용 경험은 대체로 떠올리지만, 개념 사이의 인과관계와 참조 방향을 단정할 때 오류가 생겼습니다. 특히 `Context`는 단순 표현 문제가 아니라 메모리 누수 원리를 반대로 이해한 상태라 다시 공부해야 합니다. DI는 이전 지적을 보완했지만, Compose와 중위 표기 함수는 알고 있는 조건을 빠짐없이 구조화해 말하는 연습이 더 필요합니다.
