## 1. [SEC-001] Android KeyStore는 어떤 보안 특성을 보장하며, 키를 일반 파일이나 설정 저장소에 보관하는 것과 무엇이 다른가요?

`platform/security` · 실무 · 답을 적어 둔 적 없는 문항

### 내 답변

키를 오직 별칭(alias)으로만 호출할 수 있고 해당 키를 직접 사용할 개발자조차도 키 값을 알 수 없다는 장점이 있음. 이 점이 일반 파일이나 설정 저장소에 보관하는 것과 다른 지점.

개발자는 특정 값을 암호화할 때 KeyStore를 불러 암호화할 키의 별칭만 불러주면 됨. 그럼 KeyStore가 해당 별칭에 대응되는 키로 알아서 암호화하고 사용자에게 반환해줌. 만약 키를 일반 파일로 저장한다면 사용자가 저장한 암호문을 개발자가 자신이 가진 키로 복호화하여 악용할 가능성이 있지만, KeyStore은 키를 직접적으로 노출하지 않는다는 점에서 보안상 이점을 가짐.

## 3. [AND-003] Android의 `Context`는 어떤 역할을 하나요? Application Context와 Activity Context의 생명주기와 사용처를 비교하고, 잘못 보관했을 때 생길 수 있는 문제까지 설명해 주세요.

`platform/android` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

Context는 앱 사용 중에 필요한 데이터와 상태 등 모든 맥락을 저장하는 곳. 크게 2가지로 나뉘는데 Application Context와 Activity Context. 전자는 앱과 생명주기를 함께하는 스코프로서 앱의 실행과 함께 생성되어 앱 종료 시 해제됨. 후자도 마찬가지로 Activity와 생명주기를 같이함. 그렇기 때문에 Context는 상황에 맞게, 즉 특정 기능이 앱 전체 스코프에서 사용된다면 Application Context를 제공하고, 만약 특정 화면이나 Activity에만 종속된다면 Activity Context를 제공해야 함.

만약 기능의 스코프에 맞지 않는 Context가 제공될 경우 메모리 누수가 생길 수 있음. 예를 들어, 특정 화면에서만 사용되는 기능에 Application Context를 붙였다고 가정하자. 이 화면을 유지/관리하는 Activity는 화면이 닫히면 메모리에서 해제되어야 함. 그러나 Activity가 자신보다 생명주기가 긴 Application 스코프의 Context를 쥐고 있음. 그래서 GC에 의해 추적 및 해제될 수가 없음. 반대로 앱 전체 스코프에서 유지되어야 할 DB 저장소 인스턴스 등은 Application Context가 아닌 Activity Context로 선언할 경우, 다른 Activity가 사용하려고 하니 이미 이전에 사용한 Activity가 해제하여 사용을 못 하는 상황이 생길 수도 있고, 매번 인스턴스를 새로 생성하고 해제하는 비용도 낭비임. 따라서 기능 생명주기에 맞는 Context를 붙여주는 것은 메모리 관리 측면에서 매우 중요.

## 4. [CMP-001] Compose에서 관찰 가능한 상태가 바뀐 뒤 Composable이 다시 실행되는 과정을 설명해 주세요. 이때 `remember`와 `MutableState`의 역할을 구분하고, Composable이 Composition에서 제거되는 단계의 정확한 명칭도 말해 주세요.

`platform/compose` · 기초 · 이전 오답 슬롯을 이전 불완전 답변으로 보충(2026-09-02) · 지난 지적: 존재하지 않는 `Decomposition` 대신 `Disposal`을 구분하지 못함; `remember`는 값을 보관할 뿐 Recomposition을 유발하지 않는다는 설명 누락

### 내 답변

Composable이 Composition을 통해 최초 렌더링된 이후 추적하는 상태가 변경될 경우 Recomposition이 발생함.

이 때 상태 값 변화를 추적할 수 있는 이유는 `MutableState`로 추적되는 상태가 `remember`를 통해 Composable의 생명주기동안 저장되기 때문. `remember` 덕분에 Composable이 Recomposition되어도 변경된 값이 Composition 당시의 초기값으로 초기화되지 않음. 이렇게 추적된 상태 값이 변화하면, Composable은 트리를 타고 내려가며 해당 상태 값에 영향을 받는 Composable만 선별적으로 추적하고, 해당 Composable에 대해서만 Recomposition을 실행함. 모든 화면이 다시 렌더링되는 것이 아니라 필요한 화면만 Recomposition을 하기 때문에 비용이 절약됨.

이렇게 Composition - Recomposition을 거친 Composable은 이제 그 목적을 다하여 파괴될 경우 Disposal 단계를 거쳐 최종적으로 제거됨.

## 5. [DI-001] 의존성 주입이 무엇인지 객체 생성 책임과 의존 방향 관점에서 설명해 주세요. 인터페이스에 의존하는 설계가 결합도와 단위 테스트에 어떤 이점을 주는지도 예를 들어 말해 주세요.

`platform/di` · 기초 · 이전 오답 슬롯을 이전 불완전 답변으로 보충(2026-09-02) · 지난 지적: 가짜 구현 주입을 통한 테스트 용이성과 인터페이스 의존 설명 누락

### 내 답변

DI는 Dependency Injection의 준말로 특정 클래스에 필요한 외부 의존성을 그 클래스 생성자에서 생성하는 게 아니라 밖에서 만들어서 주는 것을 뜻함.

밖에서 만들어 주는 것이 더 나은 방향인 이유: 클래스 생성자에서 필요한 의존성을 직접 생성할 경우, 해당 클래스의 본래 책임에 더해 원래 책임과는 큰 관련이 없는 의존성 생성 책임까지 더해짐. 이는 곧 연관성이 낮은 두 관심사가 하나의 클래스에 있다는 것이고, 즉 결합도의 상승을 뜻하므로 바람직한 아키텍처가 아님. 만약 이를 밖에서 만들어서 주면, 클래스는 자신의 본래 책임에만 집중할 수 있게 되고 외부 의존성 관리 책임은 다른 쪽으로 넘어가게 되므로 결합도가 낮아지고 응집도가 높아지는 결과로 이어짐.

DI는 Android 개발에서는 일반적으로 인터페이스로 필요한 의존성을 정의하고, 구현체로 의존성의 실제 동작을 구현하는 식으로 이루어짐. 이 방식 - 인터페이스와 구현체의 분리 - 은 특히 저장소 패턴을 통해 잘 드러나는데, 저장소 패턴은 데이터 소스의 인터페이스와 실제 구현체를 분리하는 패턴으로 1) 여러 데이터 소스가 존재할 시 이들을 쉽게 갈아낄 수 있게 해주고 2) 특히나 테스트 시에 실제 API나 데이터 소스가 준비되어 있지 않아도 가짜 구현체를 생성하여 모방된 응답(mocked response)을 뱉도록 구현할 수 있어 개발 초기 테스트와 아직 데이터 소스 측에서 구현되지 않은 내용을 빠르게 쳐내야 할 때 큰 도움이 됨.

## 6. [JK-001] Kotlin의 중위 표기 함수는 무엇이며 선언 조건은 무엇인가요? 호출식의 리시버와 매개변수를 구분해 예시와 함께 설명해 주세요.

`lang/java-kotlin` · 실무 · 숙지 상태 재점검 슬롯을 이전 불완전 답변으로 보충(2026-09-02) · 지난 지적: 리시버와 하나의 매개변수를 구분하지 못함; 멤버 함수 또는 확장 함수 조건 누락; 피연산자 용어 오용

### 내 답변

중위 표기 함수는 타입이 `T`로 같은 두 피연산자의 중간에 들어가는 함수로 예를 들어 `a add b`와 같은 것이 있을 수 있음.

호출식의 리시버는 왼쪽 피연산자 `T`에 달림. 그리고 매개변수는 오직 하나, 우측 피연산자인 `others: T`; 이 조건이 위반되면 컴파일이 실패됨. 왜냐하면 실질적으로는 `a add b`는 `a.add(b)`로도 표현할 수 있기 때문.
