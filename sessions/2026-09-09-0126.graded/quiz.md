## 1. [AND-002] `Activity`와 `Fragment`의 차이를 생명주기와 역할 관점에서 설명하고, 단일 `Activity`에 여러 `Fragment`를 두는 구성을 선택할 만한 기준도 말해 주세요

`platform/android` · 기초 · 이전 오답(2026-09-04) · 지난 지적: 개념을 답으로 꺼내지 못했고 단일 Activity + 여러 Fragment 구성의 판단 기준을 설명하지 못함

### 내 답변

둘 다 UI를 그릴 때 사용한다는 공통점이 있음. 그러나 큰 차이점은 생명주기를 OS가 직접 관리하는지 여부. 전자(`Activity`)는 OS에 의해 생명주기가 관리되지만 후자(`Fragment`)는 그렇지 않음.

이와 관련하여, 혼자서 생성 및 소멸될 수 없는 후자는 전자의 하위 UI로 포함될 수 있음. 그렇기에 보통 재사용성이 높고 단위가 작은 공용 컴포넌트를 후자로 구현하는 것이 보통 일반적.
반면 전자는 혼자 생성되는 것이 가능하기 때문에, 재사용 가능한 후자 컴포넌트들을 조합한 큰 단위의 화면으로 구현하게 됨. 그렇다고 해서 전자가 재사용 불가능하다는 건 아니며 경우에 따라 구현은 달라질 수 있음.

## 2. [AND-003] Android의 `Context`란 무엇이며 `Application Context`와 `Activity Context`는 언제 구분해 사용해야 하나요? 잘못 보관했을 때 메모리 누수가 생기는 참조 관계도 설명해 주세요

`platform/android` · 기초 · 이전 오답(2026-09-06) · 지난 지적: OS 기능 접근 인터페이스라는 정의, Activity Context가 필요한 UI 사용처, 장기 객체가 Activity를 붙잡는 누수 방향을 설명하지 못함

### 내 답변

컨텍스트는 앱이 OS와 소통하기 위한 일종의 창구로서 OS 네이티브 기능에 접근하기 위한 여러 API를 제공함.

컨텍스트는 앱 컨텍스트와 액티비티 컨텍스트의 2가지 종류가 존재. 전자는 생명주기가 앱과 함께하며, 후자는 생명주기가 액티비티와 함께한다는 차이점이 있음. 그럼 어떨 때 무엇을 사용해야 하느냐? 앱 전역에서 사용되는 공통 기능(Room DB 등)은 앱이 실행되는 내내 여러 범위에서 호출되는 만큼 앱 컨텍스트에 묶어주고, 반대로 특정 액티비티나 화면에 종속되는 기능은 액티비티 컨텍스트에 묶어주면 됨.

여기서 이 원칙을 지키지 않으면 메모리 누수가 발생할 수 있는데 문제가 되는 경우는 앱 컨텍스트가 액티비티 컨텍스트를 잡고 있는 경우. 원칙적으로 액티비티 컨텍스트는 대응되는 액티비티가 소멸될 경우 같이 사라져야 함. 그런데 만약 이 액티비티 컨텍스트를 앱 컨텍스트가 잡고 있다면? 액티비티 컨텍스트가 사용되는 액티비티는 소멸되었는데 정작 해당 액티비티에 묶여 있던 컨텍스트는 앱 컨텍스트가 잡고 있어 - 참조 관계가 살아남아 있어 - GC가 안 되는 문제가 발생.

따라서 액티비티 사용 시 기능의 범위와 특성에 따라 그 종류를 잘 선택해서 사용해야 함.

## 3. [SEC-003] Android 앱에서 액세스 토큰과 리프레시 토큰을 각각 어디에 어떤 방식으로 저장하시겠습니까? 두 토큰의 수명과 탈취 위험을 고려해 설명해 주세요

`platform/security` · 실무 · 답을 적어 둔 적 없는 문항

### 내 답변

두 토큰 다 DataStore에 저장할 것임. 단, 암호화를 해서. 이 때 암호화에 필요한 키는 Android KeyStore에서 발급 및 유지.

두 토큰 다 자격 증명에 사용되는 매우 중요한 토큰인데 그냥 같이 기기 내에 저장하는 이유는 실물 스마트폰 자체가 비교적 강력한 보안 수단이기 때문. 보통 웹 브라우저가 동작하는 Mac이나 데스크톱의 경우 다른 사람과 함께 사용하는 경우가 적지 않고, 무엇보다도 악성 JS 스크립트를 끼워 넣는 공격이 가능함. 그래서 웹 환경에서는 액세스가 탈취당할 것을 어느 정도 고려하여 그 수명을 매우 짧게(24~72시간 정도) 설정하고 리프레시를 그보다 길게(약 일주일) 설정하여, 액세스가 탈취되어도 금방 만료되어 피해가 더 커지지 않도록 하는 방식을 택함. 반면 스마트폰은 사람들이 남에게 잘 빌려주지 않고 보통 개인용으로 사용하기 때문에 정보 유출의 우려가 웹에 비해서는 비교적 크지 않음. 따라서 웹보다는 비교적 그 수명을 길게 설정해도 괜찮다고 봄.

다만 그렇다고 해서 스마트폰에서도 보안 위협이 아예 없는 것은 아니기 때문에, 수명의 경우 웹과 같거나 비교적 길게 두되, 스마트폰 환경과 사용 습성을 감안하여 둘 다 일주일 정도로 사용하면 적절할 것으로 생각함.

## 4. [신규] ProGuard 또는 R8의 난독화가 앱 보안에 어떤 도움을 주며, 왜 이것만으로 보안 경계를 만들 수는 없는지 설명해 주세요

`platform/security` · 실무 · 주제 대장 공백 — 지식 파일에 아직 없는 주제

### 내 답변

난독화는 빌드된 앱을 디컴파일했을 때 코드를 읽기 어렵게 하는 것을 의미.

난독화를 하지 않는다면 공격자가 내 앱을 받아서 디컴파일한 후 리버스 엔지니어링을 돌렸을 때 코드가 원본 그대로 나오기 때문에 이 앱이 어떤 로직을 사용하는지 투명하게 보여 공격자가 공격할 지점을 쉽게 찾을 수 있음. 그러나 난독화를 할 경우 리버스 엔지니어링을 해도 코드가 파악하기 어려운 상태로 나오기 때문에 공격자가 앱 로직 흐름을 파악하기 어려워짐.

그러나, 난독화를 한다고 해도 앱이 동작은 해야 하기 때문에 결국 어떻게든 원본 코드의 로직은 유지해야 한다는 결정적 한계점이 존재함. 따라서 결국 난독화된 코드를 정리하고 불필요한 항목들을 쳐내고 나면 원본 코드와 비슷한 결과물을 얻을 수 있을 것임. 이것이 난독화만으로는 보안 경계를 만들 수 없는 이유.

## 5. [CMP-004] Stateful Composable과 Stateless Composable의 차이를 설명하고, 상태 호이스팅이 재사용성과 테스트 가능성에 어떤 영향을 주는지 말해 주세요

`platform/compose` · 기초 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

스테이트풀 컴포저블은 상태 관리 책임을 가지는 컴포저블을 말하고, 반대로 스테이트리스 컴포저블은 상태 관리 책임이 없음.

상태 호이스팅, 즉 상태를 가능한 여러 하위 컴포저블의 공통 조상에 올리라는 원칙은 이 2가지 유형의 컴포저블과 밀접한데, 여기서 공통 조상이 보통 스테이트풀 컴포저블이 되고 하위 컴포저블이 스테이트리스 컴포저블이 되기 때문.

이 경우 하위 컴포저블은 정말 필요한 것 - 예를 들어 텍스트 필드의 값을 유지하는 경우 - 외에는 특정 도메인에 종속된 상태를 갖고 있지 않기에, 단순히 주어진 값으로 컴포저블을 렌더링하는 책임만 맡게 됨. 따라서 여러 컴포저블에서 재사용이 가능해지고, 주어진 값에 따라 렌더링이 잘 되는지만 보면 되기 때문에 테스트 용이성도 커짐.

## 6. [DI-002] Hilt가 수동 DI보다 제공하는 장점을 컴파일 시점 검증과 객체 스코프 관점에서 설명하고, 도입 비용이나 단점도 함께 말해 주세요

`platform/di` · 실무 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-02) · 지난 지적: 컴파일 시점 의존성 그래프 검증, 주요 스코프 이름, 도입 트레이드오프를 말하지 못함

### 내 답변

먼저 힐트는 의존성 그래프를 컴파일 시점에 검증함. 기존 수동 DI는 의존성 그래프를 빌드 타임에 확인하지 않았기 때문에 오직 런타임에서만 확인할 수 있었음. 힐트는 이 부분을 KSP로 빌드 타임에 검사하도록 강제함으로써 오류를 조기에 명확히 잡을 수 있는 기반을 개발자에게 마련해주었음. 또한 객체 특성에 따른 생명주기를 알아서 관리해줌. 예를 들어 싱글톤 스코프로 선언된 객체에는 싱글톤 컴포넌트로 지정된 객체가 접근할 수 있도록 함으로써, 스코프 범위에 따른 컴포넌트 접근을 개발자가 직접 구현해야 할 필요를 없애주었음.

다만 러닝 커브가 꽤 높고 컴파일 타임에 검사하는 비용이 꽤나 큰 편이라 빌드 시간이 증가하는 단점이 있음.
