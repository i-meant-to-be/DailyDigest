## 1. [AND-002] `Activity`와 `Fragment`의 차이 — 2점

**맞은 부분**

`Activity`의 생명주기를 운영체제가 관리하고, `Fragment`는 단독으로 존재하지 않고 호스트 `Activity`에 종속된다는 큰 방향은 맞았습니다. 둘 다 UI 구성에 쓰인다는 점도 짚었습니다.

**빠진 부분**

`FragmentManager`가 `Fragment`의 생명주기를 관리한다는 점, `Fragment` 자체 생명주기와 뷰 생명주기가 분리된다는 점이 없습니다. 단일 `Activity` 구성을 언제 선택할지에 대해서도 통합된 탐색 흐름, 목적지 간 상태 공유, 하나의 작업 단위 같은 판단 기준을 말하지 못했습니다.

**틀린 부분**

`Fragment`를 보통 작고 재사용 가능한 공용 컴포넌트, `Activity`를 이들을 조합한 큰 화면이라고 일반화하면 부정확합니다. `Fragment` 하나가 화면 전체 목적지가 될 수 있고, `Activity`도 화면 크기가 아니라 운영체제가 관리하는 애플리케이션 컴포넌트와 창의 경계로 이해해야 합니다.

**면접에서는 이렇게**

"`Activity`는 운영체제가 직접 생성과 생명주기를 관리하는 최상위 애플리케이션 컴포넌트이자 창의 진입점입니다. `Fragment`는 `Activity`가 호스팅하고 `FragmentManager`가 관리하는 UI 단위로, 자체 생명주기와 별도의 뷰 생명주기를 가지지만 호스트의 생명주기를 넘을 수 없습니다. 앱의 목적지들이 하나의 탐색 그래프와 작업 흐름을 이루고 상태나 전환을 공유한다면 단일 `Activity`에 여러 `Fragment`를 두기 좋고, 독립적인 진입점이나 작업 경계가 필요하면 별도 `Activity`도 검토합니다."

**상태** 오답 → 불안정 (2점)

## 2. [AND-003] `Context` 종류와 누수 — 3점

**맞은 부분**

`Context`를 앱이 Android OS 기능에 접근하는 창구로 정의한 점이 정확합니다. `Application Context`와 `Activity Context`의 생명주기 차이, Room 같은 장기 객체에 전자를 쓰는 이유, 짧은 생명주기의 객체를 장기 참조가 붙들면 GC되지 않는다는 방향도 이해했습니다.

**빠진 부분**

`Activity Context`가 필요한 대표 사례를 구체적으로 들지 못했습니다. 현재 `Activity`의 테마를 적용해 `View`나 `Dialog`를 만들거나 해당 창과 연결된 UI 작업을 할 때는 `Activity Context`가 필요합니다.

**틀린 부분**

누수를 만드는 주체를 `Application Context` 자체라고 표현한 부분은 잘못됐습니다. 일반적으로 문제는 싱글턴, 정적 필드, 장기 실행 작업처럼 앱보다 오래 살아남는 객체가 `Activity`, `View`, 리스너 또는 `Activity Context`를 참조하는 경우입니다. `Application Context`가 자동으로 `Activity Context`를 붙드는 것은 아닙니다.

**면접에서는 이렇게**

"`Context`는 앱 정보와 리소스, 시스템 서비스 등 Android OS 기능에 접근하는 인터페이스입니다. 앱 수명과 같은 저장소나 싱글턴에는 `Application Context`를 쓰고, 현재 화면의 테마나 창이 필요한 `View`·`Dialog`에는 `Activity Context`를 씁니다. 싱글턴 같은 장기 객체가 `Activity Context`를 보관하면 종료된 `Activity`까지 참조 사슬에 남아 누수되므로, 필요한 기능과 소유자의 생명주기를 맞춰야 합니다."

**상태** 오답 → 불안정 (3점)

## 3. [SEC-003] 액세스 토큰과 리프레시 토큰 저장 — 2점

**맞은 부분**

토큰을 평문으로 두지 않고 앱 전용 저장소의 암호문으로 보관하며, 암호화 키는 Android KeyStore에서 생성해 비추출성 보호를 받게 한다는 설계는 좋습니다. DataStore 자체가 암호화를 제공하는 것은 아니므로 별도 암복호화 계층이 필요하다는 전제도 답에 드러났습니다.

**빠진 부분**

리프레시 토큰 회전, 이전 토큰 재사용 탐지, 로그아웃·보안 사건 시 폐기 같은 서버 측 통제가 없습니다. 액세스 토큰은 가능한 짧게 유지하고 메모리에만 두되 앱 재시작 복원이 꼭 필요할 때만 암호화해 저장하는 식으로, 두 토큰의 노출 면을 다르게 가져가는 설명도 필요합니다.

**틀린 부분**

액세스 토큰의 24~72시간을 매우 짧다고 보기는 어렵고, 두 토큰을 모두 일주일로 맞추면 수명을 분리하는 이유가 약해집니다. 스마트폰이 개인용이라는 사실도 프로세스 변조, 루팅, 악성 앱, 백업·로그 유출 같은 위협을 없애지 않으므로 모바일이라는 이유로 토큰 수명을 늘려도 된다는 결론은 위험합니다. 정확한 수명은 플랫폼별 고정값이 아니라 서비스의 위험도와 서버 정책으로 정해야 합니다.

**면접에서는 이렇게**

"액세스 토큰은 피해 범위를 줄이도록 짧은 수명과 최소 권한을 주고 가능하면 메모리에만 둡니다. 재로그인 없는 세션 복원이 필요하면 앱 전용 저장소에 암호화해 보관할 수 있습니다. 더 오래 살아 있고 새 액세스 토큰을 만들 수 있는 리프레시 토큰은 반드시 암호화해 저장하고, 키는 Android KeyStore에 둡니다. 서버에서는 리프레시 토큰 회전과 재사용 탐지, 로그아웃·보안 사건 시 폐기를 적용합니다. 루팅되거나 앱 프로세스가 장악되면 사용 중인 평문은 노출될 수 있으므로 로컬 암호화만 신뢰하지 않습니다."

**상태** 미학습 → 불안정 (2점)

## 4. [SEC-016] ProGuard/R8 난독화와 보안 — 3점

**맞은 부분**

난독화가 코드의 의도와 흐름을 파악하는 비용을 올리지만, 실행 가능한 로직이 기기에 배포되는 이상 분석 자체를 막지는 못한다는 핵심을 정확히 설명했습니다. 난독화를 보안 경계로 볼 수 없는 이유도 논리적으로 연결했습니다.

**빠진 부분**

실제 보안 경계가 어디에 있어야 하는지까지 연결하면 답이 완성됩니다. 클라이언트에 포함한 비밀 값은 추출될 수 있다고 보고, 인증·권한 검증과 중요한 정책은 서버에서 강제해야 합니다. 또한 지나치게 넓은 `keep` 규칙은 난독화와 최적화 범위를 줄이고, 반대로 필요한 규칙이 없으면 리플렉션·직렬화·JNI 코드가 깨질 수 있다는 실무상 균형도 언급할 만합니다.

**틀린 부분**

난독화하지 않은 앱을 디컴파일하면 "원본 코드가 그대로 나온다"는 표현은 부정확합니다. 컴파일 과정에서 원래 소스 구조는 변환되며, 이름과 구조가 비교적 많이 남아 분석하기 쉬워진다고 말하는 편이 맞습니다.

**면접에서는 이렇게**

"R8은 사용하지 않는 코드를 제거하고 최적화하며 클래스·메서드·필드 이름을 짧고 의미 없게 바꿉니다. 이 때문에 역공학 비용은 올라가지만 APK에는 실행 가능한 코드와 데이터가 남고, 공격자는 정적 분석이나 후킹으로 동작을 관찰할 수 있습니다. 따라서 난독화는 방어를 겹쳐 적용하는 한 수단일 뿐이며, 비밀 값 저장이나 권한 검증을 대신하지 못합니다. 중요한 권한 판단은 서버에서 해야 하고 클라이언트에 장기 비밀을 넣지 않아야 합니다."

**상태** 미학습 → 불안정 (3점)

## 5. [CMP-004] Stateful·Stateless Composable — 3점

**맞은 부분**

상태 소유와 변경 책임의 유무로 두 종류를 구분했고, 상태를 공통 조상으로 올리면 하위 Composable이 입력에 따른 렌더링에 집중해 재사용성과 테스트 가능성이 높아진다는 인과도 정확합니다.

**빠진 부분**

Stateless Composable의 계약을 `value` 같은 상태 값과 `onValueChange` 같은 변경 요청 콜백의 쌍으로 명시하지 않았습니다. 상태를 무조건 가능한 한 높이 올리는 것이 아니라, 상태를 읽고 쓰는 컴포넌트들의 가장 낮은 공통 조상이나 적절한 상태 소유자까지 올린다는 기준도 필요합니다.

**틀린 부분**

큰 사실 오류는 없습니다. 다만 텍스트 필드가 값을 내부에 유지한다면 그 Composable도 그 상태에 대해서는 Stateful입니다. 외부 제어가 필요 없는 일시적인 UI 상태는 내부에 남길 수 있지만, 그 선택도 상태 소유권에 포함됩니다.

**면접에서는 이렇게**

"Stateful Composable은 상태를 소유하고 변경하며, Stateless Composable은 상태 값을 매개변수로 받고 변경 의도는 콜백으로 올립니다. 상태를 읽고 변경하는 컴포넌트들의 적절한 공통 소유자까지 호이스팅하면 하위 UI는 같은 입력에 같은 출력을 내는 형태가 되어 독립적으로 재사용하고 테스트하기 쉬워집니다. 다만 외부에서 제어할 필요가 없는 일시적 UI 상태까지 무조건 최상위로 올리지는 않습니다."

**상태** 미학습 → 불안정 (3점)

## 6. [DI-002] Hilt와 수동 DI — 2점

**맞은 부분**

Hilt가 생성하는 의존성 그래프를 컴파일 시점에 검증해 누락이나 잘못된 바인딩을 일찍 찾는다는 핵심과, 학습 비용·빌드 시간 증가라는 도입 비용을 이번에는 설명했습니다. 컴포넌트 수명과 객체 스코프가 연결된다는 방향도 잡았습니다.

**빠진 부분**

`@Singleton`, `@ActivityRetainedScoped`, `@ViewModelScoped`, `@ActivityScoped` 같은 대표 스코프와 각각의 생성 컴포넌트를 들지 못했습니다. 스코프는 해당 컴포넌트 인스턴스 안에서 같은 바인딩 인스턴스를 공유한다는 뜻이며, 기본 바인딩은 요청할 때마다 새로 생성되는 비스코프라는 점도 필요합니다.

**틀린 부분**

수동 DI도 생성자 매개변수와 타입 오류는 컴파일러가 잡으므로 오류를 오직 런타임에서만 알 수 있다는 설명은 지나칩니다. Hilt의 차이는 전체 바인딩 그래프를 생성·검증하고 Android 컴포넌트와 연결하는 데 있습니다. 또한 Hilt가 KSP 사용을 강제하는 것은 아니며 프로젝트 설정에 따라 KAPT 또는 KSP를 사용할 수 있습니다. `SingletonComponent`와 `@Singleton`의 관계도 접근 허용이 아니라, 컴포넌트 인스턴스당 같은 객체를 제공하고 하위 컴포넌트가 그 바인딩을 사용할 수 있는 구조로 설명해야 합니다.

**면접에서는 이렇게**

"Hilt는 Dagger 기반으로 Android 컴포넌트별 의존성 그래프와 생성 코드를 만들고 컴파일 시점에 바인딩 누락이나 순환 같은 오류를 검증합니다. `@Singleton`은 `SingletonComponent`, `@ActivityRetainedScoped`는 설정 변경을 넘는 `ActivityRetainedComponent`, `@ViewModelScoped`는 `ViewModelComponent` 인스턴스 범위에서 같은 객체를 제공합니다. 수동 DI보다 조립 코드와 생명주기별 컨테이너 구성이 줄지만, 어노테이션과 생성 코드를 익혀야 하고 빌드 시간이 늘며 작은 프로젝트에서는 설정 비용이 더 클 수 있습니다."

**상태** 불안정 유지 (2점)
