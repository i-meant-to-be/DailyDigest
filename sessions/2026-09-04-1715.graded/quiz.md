## 1. [SEC-008] 해시와 암호화는 어떤 점이 다르며, 비밀번호 저장에 솔트가 필요한 이유는 무엇인가요?

`platform/security` · 기초 · 답을 적어 둔 적 없는 문항

### 내 답변

암호화는 특정 값을 관련 없는 자가 읽을 수 없도록 숨기는 것을 말한다. 암/복호화를 위해서는 별도의 키가 필요하며, 키가 같으면 대칭 키, 키가 다르면 공개 키 암호화다. 암호화 함수는 알고리즘에 따라 다르지만 보통 연산 과정에 난수를 끼워넣는 경우가 많은데 이를 솔트라고 부른다. 비밀번호 저장을 위한 암호화 함수에 솔트가 사용되는 이유는, 솔트가 없는 경우 공격자에게 암호문만 있을 때 우연히 해당 암호문에 맞는 평문을 암호화 함수에 넣어 공격이 성립되는 상황을 방지하기 위함이다. 솔트가 있는 암호화 함수는 같은 입력을 넣어도 다른 결과가 나오기 때문에 방금 말한 공격 시나리오에 대비할 수 있다.

해시는 엄밀히 말해서 암호화보다는 특정 값이 손상되었는지 - 다시 말해 원본 그대로 유지되어 있는지 - 를 확인하기 위한 수단에 가깝다. 그래서 해시 함수는 솔트가 포함된 암호화 함수와는 다르게 입력이 같으면 항상 동일한 출력을 낸다. 그리고 또한 입력 값이 조금만 바뀌어도 출력에 미치는 영향이 매우 크다.

따라서 두 도구는 목적이 다르다: 암호화는 기밀성 유지, 해시는 정보 왜곡 방지가 주 목적이다.

## 3. [DI-003] Hilt의 `@Binds`와 `@Provides`는 각각 언제 사용하며, 선언 방식이 다른 이유는 무엇인가요?

`platform/di` · 실무 · 답은 정리했지만 아직 점검받지 않은 문항

### 내 답변

둘 다 외부 의존성을 제공해야 할 때 사용한다. 차이점은 Hilt가 만드는 방법을 알고 있는지 여부다.

`@Binds`는 묶는다는 뜻이다. 즉 Hilt가 만드는 방법을 아는 의존성을 묶어달라는 의미이다. 따라서 `@Binds`가 붙을 수 있으려면 해당 인스턴스의 생성자에는 `@Inject constructor`를 붙여 Hilt가 인스턴스를 만드는 방법을 알려 주어야 한다. 또한 Hilt가 만드는 방법을 알고 있으므로 인터페이스로만 선언해 주어도 무방하다. 실제 구현을 코드로 적어줄 필요가 없다는 말이다.

`@Provides`는 제공해준다는 뜻이다. 즉 Hilt가 만드는 방법을 모르는 외부 의존성을 제공해줘야 한다는 얘기다. 따라서 이 경우 `@Binds`와는 다르게 실제 인스턴스를 어떻게 제공할 수 있는지를 코드로 작성해줘야 한다.

## 4. [SEC-014] Android 앱의 디버그 키, 업로드 키, 앱 서명 키를 구분해 설명하고, 각 키를 잃어버렸을 때 배포에 어떤 영향이 있는지 말해 주세요.

`platform/security` · 실무 · 이전 오답 슬롯을 이전에 불완전하게 답한 문항으로 채움 · 지난 지적: 업로드 키와 앱 서명 키의 관계를 파이프라인 앞뒤 단계로 설명하지 못함; 자체 서명 키 분실 시 같은 패키지명으로 업데이트할 수 없다는 결과를 답하지 않음; 디버그 키와 릴리즈 키를 구분하지 못함

### 내 답변

기본적으로 Android Studio 상에서는 디버그 키와 릴리즈 키를 사용하게 된다.

디버그 키는 Android Studio에서 디버그 바이너리를 빌드할 때 서명하는 키이다.

업로드 키는 Play 스토어를 통해 앱을 배포하는 경우, 앱을 빌드한 사용자가 나임을 Play 스토어에 증명하기 위한 키이다. 보통 릴리즈 키를 사용한다. Play 스토어는 오직 내가 지정해 둔 업로드 키로 빌드한 앱 번들만 내가 개발한 것으로 간주하며, 만약 지정된 업로드 키가 아닌 다른 업로드 키로 서명해 올린다면 그건 내가 개발하지 않은 것으로 추정하고 업로드를 거부한다.

앱 서명 키는 업로드 키와 비슷하게 앱을 개발한 사람이 나임을 증명하기 위한 키이다. Play 스토어를 사용하는 경우 업로드 키가 정확하다면 Play 콘솔 내부에서 Google이 관리해주는 앱 서명 키로 앱을 대신 서명해준다. 만약 외부 스토어에서 배포하는 경우에는 릴리즈 키를 앱 서명 키로 사용하여 앱 번들을 빌드하고, 배포 시 이 앱이 내가 개발한 것임을 인증할 때 사용하게 된다.

## 6. [HIL-001] 멀티모듈 프로젝트에서 기능 모듈을 `api`와 `impl`로 분리하면 무엇을 얻고 어떤 비용을 치르게 되나요? 네비게이션 의존성을 예로 들어 설명해 주세요.

`project/hilit` · 실무 · 숙지 상태 재점검 슬롯을 답은 정리했지만 아직 점검받지 않은 문항으로 채움

### 내 답변

일단 이 프로젝트에서 각 기능 모듈의 라우팅 테이블 구성 책임을 중앙 앱 모듈이 아닌 기능 모듈 각각에게 나누었다는 점을 참고 바람.

장점은 다른 기능 모듈끼리 네비게이션을 처리해야 할 때 코드 작성이 편하고 모듈화의 이점인 낮은 결합도가 유지된다는 것. 만약 라우팅 테이블을 하나의 기능 모듈에 모두 몰아둘 경우, 라우팅 테이블 하나를 참고하기 위해 해당 모듈 전체를 의존성으로 붙여야 하는데, 이 경우 라우팅 테이블과 관련되지 않은 모듈의 메인 기능까지 의존성에 더하게 되기에 불필요하게 내부 코드를 노출하는 꼴이 됨. 그러나 `api`와 `impl`의 2개 모듈로 분리하게 되면 외부 모듈에서는 라우팅 테이블에만 접근하도록 할 수 있기 때문에 의존성 관계가 조금 더 깔끔해지는 이점이 있음.

문제점이 있다면 아무래도 원래대로라면 기능 모듈은 1개의 모듈인데 분리하면서 모듈 개수가 2개가 된다는 점. 이로 인해 Gradle 빌드 시간이 조금 지연될 수밖에 없어지는 트레이드오프는 존재한다.
