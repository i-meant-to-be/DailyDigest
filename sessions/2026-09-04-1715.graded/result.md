## 1. [SEC-008] 해시와 암호화는 어떤 점이 다르며, 비밀번호 저장에 솔트가 필요한 이유는 무엇인가요? — 2점

**맞은 부분**

암호화의 목적을 기밀성으로 잡고 키를 이용해 복호화할 수 있다는 점, 해시가 같은 입력에 같은 결과를 내며 작은 입력 변화가 큰 출력 변화를 만든다는 점은 맞았습니다.

**빠진 부분**

비밀번호는 일반 암호화가 아니라 복호화할 필요가 없는 비밀번호 해시 함수로 저장해야 합니다. 솔트는 사용자마다 생성하는 고유한 임의 값이며 비밀일 필요가 없습니다. 같은 비밀번호도 서로 다른 해시가 되게 하여 해시 중복 노출을 막고, 미리 계산한 사전·레인보우 테이블을 여러 사용자에게 재사용하지 못하게 만드는 것이 핵심입니다.

**틀린 부분**

솔트를 일반적인 암호화 함수의 연산에 들어가는 난수라고 정의한 것은 개념을 섞은 설명입니다. 공격자가 우연히 맞는 평문을 넣는 것을 막는다는 설명도 정확하지 않습니다. 공격자는 탈취한 해시에 대해 후보 비밀번호를 대량으로 대입하는 오프라인 추측 공격을 합니다. 해시의 주목적을 정보 왜곡 방지로만 한정한 것도 비밀번호 문맥에서는 부족합니다.

**면접에서는 이렇게**

“암호화는 키로 복호화할 수 있어 기밀성이 목적이고, 암호학적 해시는 임의 길이 입력을 고정 길이 값으로 바꾸는 단방향 함수입니다. 비밀번호는 복호화할 이유가 없으므로 Argon2id·scrypt·bcrypt 같은 느린 비밀번호 해시 함수로 저장합니다. 각 비밀번호에 고유한 솔트를 붙이면 같은 비밀번호도 결과가 달라져, 공격자가 미리 계산한 테이블을 재사용하거나 여러 계정을 한꺼번에 공격하기 어려워집니다.”

**상태** 미학습 → 불안정 (2점)

## 2. [CMP-022] Jetpack Compose에서 커스텀 레이아웃을 직접 구현할 때 측정과 배치는 어떤 순서로 이루어지며, 어떤 제약을 지켜야 하나요? — 1점

**맞은 부분**

레이아웃 과정에 자식의 측정과 배치가 포함되며 트리를 따라 처리된다는 큰 방향은 잡았습니다.

**빠진 부분**

핵심인 `Constraints`, `Measurable`, `Placeable`, `layout`, `place`의 관계가 없습니다. Compose에서는 부모가 자식에게 최소·최대 너비와 높이의 제약을 내려보내고, 자식은 그 범위 안에서 측정된 크기를 반환합니다. 부모는 그 결과로 자신의 크기를 정한 뒤 자식의 좌표를 배치합니다. 일반 측정 과정에서는 한 자식을 한 번만 측정해야 한다는 제약도 중요합니다.

**틀린 부분**

부모가 자신의 최종 빈 공간을 먼저 계산하고 자식에게 넘긴다는 설명은 순서가 정확하지 않습니다. 부모는 상위에서 받은 제약을 바탕으로 자식을 먼저 측정해야 그 결과를 이용해 자신의 크기와 자식의 위치를 결정할 수 있습니다.

**면접에서는 이렇게**

“`Layout`의 측정 블록에서 부모가 받은 `Constraints`를 자식 `Measurable`의 `measure`에 전달하면 `Placeable`이 반환됩니다. 부모는 자식들의 측정값으로 자신의 너비와 높이를 정하되 자신이 받은 제약 범위를 지켜야 합니다. 그다음 `layout(width, height)`의 배치 블록에서 각 `Placeable`을 `place`나 `placeRelative`로 배치합니다. 일반 측정에서는 각 자식을 한 번만 측정해야 하므로, 여러 크기를 탐색해야 한다면 intrinsic 측정 같은 별도 기능을 검토합니다.”

**상태** 미학습 → 오답 (1점)

## 3. [DI-003] Hilt의 `@Binds`와 `@Provides`는 각각 언제 사용하며, 선언 방식이 다른 이유는 무엇인가요? — 3점

**맞은 부분**

Hilt가 이미 만들 수 있는 구현체를 추상 타입에 연결할 때 `@Binds`를 쓰고, 생성 코드를 직접 알려 줘야 할 때 `@Provides`를 쓴다는 핵심 비교는 맞았습니다. `@Provides`에는 함수 본문이 필요하다는 점도 설명했습니다.

**빠진 부분**

`@Binds`는 모듈 안의 추상 함수로 선언하고 구현체 타입 매개변수 하나를 받아 인터페이스 같은 추상 타입을 반환한다는 시그니처를 명확히 말했어야 합니다. 반대로 `@Provides`는 일반 함수의 본문에서 인스턴스를 반환하며 필요한 의존성을 매개변수로 받을 수 있습니다.

**틀린 부분**

둘 다 외부 의존성을 제공할 때 쓴다는 시작 문장은 범위를 지나치게 좁혔습니다. 또한 `@Binds` 구현체에 반드시 `@Inject constructor`가 있어야 하는 것은 아닙니다. 그 구현체를 Hilt 그래프가 만들 수 있어야 할 뿐이며, 다른 `@Provides` 바인딩 등으로 제공될 수도 있습니다.

**면접에서는 이렇게**

“`@Binds`는 이미 그래프가 생성할 수 있는 구현체를 인터페이스에 매핑할 때 사용합니다. 그래서 `abstract fun bind(impl: Impl): Interface`처럼 본문 없는 추상 함수로 선언합니다. `@Provides`는 외부 라이브러리 객체나 빌더처럼 생성 절차를 코드로 적어야 할 때 사용하며, 함수 본문에서 객체를 만들어 반환합니다. 단순한 인터페이스-구현체 연결이면 생성 코드가 없는 `@Binds`를 우선하고, 직접 생성 로직이 필요하면 `@Provides`를 선택합니다.”

**상태** 미학습 → 불안정 (3점)

## 4. [SEC-014] Android 앱의 디버그 키, 업로드 키, 앱 서명 키를 구분해 설명하고, 각 키를 잃어버렸을 때 배포에 어떤 영향이 있는지 말해 주세요. — 2점

**맞은 부분**

업로드 키로 개발자의 업로드를 검증한 뒤 Google Play가 별도로 보관한 앱 서명 키로 배포 산출물에 서명한다는 파이프라인을 이전보다 정확히 설명했습니다. Play 외부에서는 개발자가 직접 앱 서명 키를 관리한다는 방향도 맞습니다.

**빠진 부분**

질문의 절반인 키 분실 결과를 전혀 답하지 않았습니다. 디버그 키는 다시 만들 수 있지만 기존 디버그 앱에는 덮어쓸 수 없어 삭제 후 설치해야 할 수 있습니다. Play 앱 서명을 사용한다면 업로드 키는 재설정을 요청할 수 있습니다. 반면 자체 관리하는 앱 서명 키를 잃으면 기존 앱과 같은 서명으로 업데이트할 수 없어 같은 패키지명의 기존 설치본에 새 버전을 배포할 수 없습니다. Play가 앱 서명 키를 관리하는 경우에는 Play의 보호·복구·키 업그레이드 절차가 적용됩니다.

**틀린 부분**

“릴리즈 키”를 업로드 키와 자체 관리 앱 서명 키 양쪽 의미로 사용해 역할 경계가 다시 흐려졌습니다. 업로드 키와 앱 서명 키는 같게 구성할 수도 있지만 Play 앱 서명을 사용하면 서로 다른 역할의 키로 분리하는 것이 핵심입니다.

**면접에서는 이렇게**

“디버그 키는 개발 도구가 로컬 디버그 빌드에 사용하는 키라 재생성할 수 있습니다. Play 앱 서명에서는 개발자가 업로드 키로 AAB에 서명해 제출하고, Play가 이를 검증한 뒤 안전하게 보관한 앱 서명 키로 사용자에게 배포될 APK를 서명합니다. 업로드 키를 잃으면 Play에 재설정을 요청할 수 있지만, 자체 관리 앱 서명 키를 잃으면 기존 앱과 동일한 서명을 만들 수 없어 같은 패키지명의 앱을 업데이트할 수 없습니다. 따라서 앱 서명 키는 접근 통제, 암호화된 백업, 키 교체 정책과 함께 관리해야 합니다.”

**상태** 불안정 유지 (2점)

## 5. [AND-001] Android의 4대 앱 컴포넌트를 열거하고, 각 컴포넌트의 역할을 설명해 주세요. — 2점

**맞은 부분**

`Activity`의 화면·사용자 상호작용 역할과 `ContentProvider`의 앱 간 데이터 공유 방향은 알고 있었습니다. 시스템 사건을 받는 컴포넌트의 역할도 대략 이해하고 있습니다.

**빠진 부분**

`Service`를 빠뜨렸습니다. `Service`는 사용자 인터페이스 없이 오래 걸리는 작업이나 다른 컴포넌트에 기능을 제공하는 컴포넌트이며, 실행 중인 작업이 곧 별도 스레드라는 뜻은 아닙니다. `ContentProvider`는 URI 기반으로 구조화된 데이터에 대한 조회·추가·수정·삭제 인터페이스를 제공한다는 설명이 더 정확합니다.

**틀린 부분**

정확한 이름은 `Event Receiver`가 아니라 `BroadcastReceiver`입니다. 기초 문항에서는 컴포넌트 이름 하나를 틀리고 하나를 누락하면 통과 답변으로 볼 수 없습니다.

**면접에서는 이렇게**

“Android의 4대 앱 컴포넌트는 `Activity`, `Service`, `BroadcastReceiver`, `ContentProvider`입니다. `Activity`는 사용자와 상호작용하는 화면 진입점이고, `Service`는 화면 없이 백그라운드 작업이나 바인딩된 기능을 제공합니다. `BroadcastReceiver`는 시스템이나 앱이 보낸 브로드캐스트를 수신하고, `ContentProvider`는 URI 기반 인터페이스로 앱 안팎에 구조화된 데이터를 안전하게 제공합니다.”

**상태** 미학습 → 불안정 (2점)

## 6. [HIL-001] 멀티모듈 프로젝트에서 기능 모듈을 `api`와 `impl`로 분리하면 무엇을 얻고 어떤 비용을 치르게 되나요? — 3점

**맞은 부분**

기능별로 네비게이션 구성 책임을 나눈다는 프로젝트 전제를 밝혔고, 외부에는 라우팅 계약만 노출해 구현 결합을 낮춘다는 핵심 장점을 설명했습니다. 모듈 수 증가라는 직접적인 비용도 짚었습니다.

**빠진 부분**

이 프로젝트에서는 `api`가 경로 키와 인자 계약을, `impl`이 화면·ViewModel·진입점 구성·DI를 소유합니다. 다른 기능으로 이동할 때 기능의 `impl`끼리 의존하지 않고 상대 기능의 `api`만 참조하며, 앱 모듈은 각 기능이 제공한 네비게이션 트리를 합치는 책임만 진다는 구조까지 명시했어야 답이 완결됩니다.

**틀린 부분**

`api`를 라우팅 테이블 자체라고 표현한 것은 다소 부정확합니다. 또한 모듈 수가 늘면 설정과 탐색 비용은 증가하지만 Gradle 빌드 시간이 반드시 느려진다고 단정할 수는 없습니다. 의존성 경계를 잘 나누면 변경 영향 범위가 줄어 증분 빌드나 병렬화에 유리할 수도 있습니다.

**면접에서는 이렇게**

“제가 결정한 구조는 아니지만, 각 기능이 자기 네비게이션 트리를 소유한다는 이 프로젝트의 책임 분배에는 적합하다고 봅니다. `api`에는 경로와 인자 같은 이동 계약만 두고, `impl`에는 화면·ViewModel·진입점 구성·DI를 둡니다. 다른 기능은 구현 모듈이 아니라 `api`만 의존하므로 구현 교체와 변경 격리가 쉬워지고, 앱 모듈은 기능별 트리를 조립하는 데 집중합니다. 대가는 기능마다 모듈이 늘어 설정·탐색·의존성 관리 비용이 커진다는 점입니다.”

**상태** 미학습 → 불안정 (3점)
