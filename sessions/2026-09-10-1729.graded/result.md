## 1. [DI-005] Hilt에서 `@Singleton`으로 지정한 객체의 생성 시점과 수명 주기를 설명해 주세요 — 2점

**맞은 부분**

`@Singleton` 객체가 보통 처음 필요해진 시점에 생성되고 앱 범위에서 같은 인스턴스를 공유한다는 방향은 맞았습니다. 지난 답변에서 혼동했던 객체의 실제 생성 시점을 이번에는 짚었습니다.

**빠진 부분**

질문이 요구한 두 시점을 분리하지 않았습니다. `SingletonComponent`는 `Application` 생성에 맞춰 만들어지지만, 그 안에 설치된 scoped 바인딩의 인스턴스는 해당 의존성이 처음 요청될 때 만들어집니다. 또한 여기서 singleton은 JVM 전체의 절대적 단일 객체가 아니라 **하나의 `SingletonComponent` 인스턴스당 하나**라는 뜻입니다.

**틀린 부분**

“그 객체를 참조하는 객체들이 모두 사라졌을 때 회수 가능”하다는 설명은 scoped 객체에는 맞지 않습니다. 일반 사용처의 참조가 없어져도 `SingletonComponent`가 인스턴스를 계속 보유합니다. 컴포넌트가 파기된 뒤 다른 강한 참조도 없어야 GC 대상이 되며, Android의 `SingletonComponent`는 통상 애플리케이션 프로세스와 함께 끝납니다.

**면접에서는 이렇게**

“Hilt의 `SingletonComponent`는 `Application` 생성 시 만들어지고 프로세스가 살아 있는 동안 유지됩니다. `@Singleton` 바인딩은 이 컴포넌트당 한 인스턴스로 캐시되며, 객체 자체는 보통 최초 의존성 요청 시 지연 생성됩니다. 이후 모든 하위 주입 지점이 같은 인스턴스를 공유하고, 컴포넌트가 파기된 뒤 남은 참조가 없어야 GC 대상이 됩니다.”

**상태** 오답 → 불안정 (2점)

## 2. [DI-010] Assisted Injection은 어떤 상황에 필요하며 생성자와 팩터리는 각각 어떤 역할을 하나요? — 3점

**맞은 부분**

객체 생성 시점에만 알 수 있는 값을 호출자가 제공해야 할 때 사용한다는 목적을 정확히 짚었습니다. 생성자에서 해당 매개변수를 표시하고 팩터리를 통해 객체를 만든다는 큰 흐름도 맞습니다.

**빠진 부분**

Assisted Injection의 핵심은 두 종류의 값을 결합하는 것입니다. `@AssistedInject` 생성자의 일반 매개변수는 Dagger가 그래프에서 공급하고, `@Assisted` 매개변수는 호출자가 팩터리의 `create`에 넘깁니다. 팩터리에는 `@AssistedFactory`를 붙이며, 생성 대상이 아니라 이 팩터리를 주입받아 사용합니다. `@AssistedInject` 타입은 직접 주입하거나 scope를 붙일 수 없다는 제약도 실무 답변에서 덧붙일 수 있습니다.

**틀린 부분**

“팩터리 메소드에서 객체를 만드는 과정을 코드로 제공한다”는 표현은 직접 구현한다는 의미로 들립니다. 개발자는 보통 추상 팩터리 계약만 선언하고, 실제 구현과 일반 의존성 결합은 Dagger가 생성합니다.

**면접에서는 이렇게**

“Assisted Injection은 repository처럼 DI가 아는 의존성과 화면 식별자처럼 실행 중에만 아는 값을 함께 받아 객체를 만들 때 사용합니다. 생성자는 `@AssistedInject`로 표시하고 런타임 값에 `@Assisted`를 붙입니다. `@AssistedFactory`의 추상 `create` 메서드는 그 런타임 값만 받으며, Dagger가 구현체를 생성해 나머지 의존성과 결합합니다. 호출자는 생성 대상 대신 팩터리를 주입받아 사용합니다.”

**상태** 오답 → 불안정 (3점)

## 3. [CMP-017] Compose에서 `Stable`과 `Skippable`은 각각 무엇을 의미하며 둘은 어떤 관계인가요? — 1점

**맞은 부분**

`Skippable`이 재구성 중 Composable 함수 실행을 생략할 수 있다는 방향만 맞았습니다.

**빠진 부분**

`Stable`은 Composable의 상태가 아니라 **타입에 대한 계약**입니다. 같은 두 인스턴스의 `equals` 결과가 안정적이고, 공개 속성이 바뀌면 Compose가 이를 알 수 있으며, 공개 속성의 타입도 stable이어야 합니다. `Skippable`은 컴파일러가 Composable 함수에 부여하는 성질로, 재구성 시 현재 매개변수와 이전 매개변수가 같으면 함수 실행을 건너뛸 수 있음을 뜻합니다. 현재 기본인 Strong Skipping에서는 restartable 함수 대부분이 unstable 매개변수를 받아도 skippable이 되지만, stable 값은 객체 동등성, unstable 값은 인스턴스 동일성으로 비교합니다.

**틀린 부분**

상태 변화의 영향을 받지 않는 Composable을 `Stable`이라고 정의한 것은 층위가 다릅니다. 또한 값이 2에서 1로 바뀌었지만 결과 색이 같다는 이유만으로 Compose가 실행 결과를 예측해 재구성을 자동 생략하지는 않습니다. Composable에 `Int`를 넘기면 입력이 달라졌으므로 다시 실행됩니다. 상위에서 색으로 변환한 값을 넘기거나 적절한 위치에서 `derivedStateOf`를 사용해야 동일한 파생 값에 따른 불필요한 작업을 줄일 수 있습니다.

**면접에서는 이렇게**

“Stable은 Compose가 값의 변경 여부를 신뢰성 있게 판단할 수 있다는 타입 계약이고, Skippable은 재구성 시 입력 비교 결과가 같으면 함수 실행을 생략할 수 있다는 Composable의 성질입니다. 따라서 안정성은 입력 비교 방식과 skipping 가능성에 영향을 줍니다. 다만 Strong Skipping이 활성화된 현재 환경에서는 unstable 매개변수가 있어도 restartable 함수 대부분이 skippable이며, stable 값은 `equals`, unstable 값은 `===`로 비교합니다.”

**상태** 미학습 → 오답 (1점)

## 4. [CMP-024] Compose 화면의 끊김이나 과도한 재구성이 의심될 때 성능 문제를 어떻게 측정하고 원인을 좁히겠습니까? — 1점

**맞은 부분**

문제가 발생하는 사용자 흐름을 정하고 개선 전후를 같은 방식으로 비교하려 한 점, lazy 목록의 key를 잠재 원인으로 본 점은 방향이 맞습니다.

**빠진 부분**

성능 측정은 디버그 빌드와 임의 로그가 아니라 출시 환경에 가까운 `profileable` 빌드, 가능하면 실제 기기와 고정된 시나리오에서 시작해야 합니다. `Macrobenchmark`와 `FrameTimingMetric`으로 여러 번 반복해 프레임 시간과 jank 기준선을 만들고, 느린 프레임은 Android Studio System Trace나 Perfetto 및 Compose composition tracing으로 어느 단계와 Composable이 시간을 쓰는지 좁혀야 합니다. 안정성 문제라면 Compose 컴파일러 보고서도 함께 볼 수 있습니다.

**틀린 부분**

재구성 횟수는 보조 단서일 뿐 화면 끊김의 성능 지표가 아닙니다. 재구성이 많아도 각 작업이 싸면 프레임을 놓치지 않을 수 있고, 재구성이 한 번이어도 무거운 작업이면 jank가 생길 수 있습니다. 모든 Composable에 Logcat 계측을 넣는 방식은 측정 대상을 교란하며, 추적 근거 없이 key부터 의심하면 실제 병목을 놓칩니다.

**면접에서는 이렇게**

“먼저 실제 기기의 출시 빌드와 같은 조건에서 재현 시나리오를 고정합니다. Macrobenchmark의 프레임 지표를 여러 번 측정해 기준선을 잡고, System Trace와 Compose composition tracing으로 느린 프레임이 composition·layout·draw 중 어디서 발생하는지 확인합니다. 그 뒤 재구성 범위, 불안정한 매개변수, 목록 key, 주 스레드 작업 같은 가설을 추적 근거에 따라 하나씩 검증합니다. 한 가지씩 수정한 뒤 같은 벤치마크를 반복해 프레임 시간 분포와 jank 감소 여부로 효과를 판단합니다.”

**상태** 미학습 → 오답 (1점)

## 5. [AND-008] Android `ViewModel`이 맡아야 할 역할과 맡지 말아야 할 역할을 설명해 주세요 — 3점

**맞은 부분**

ViewModel이 화면 상태를 만들고 관리하며 사용자 이벤트를 처리한다는 핵심은 맞았습니다. UI는 상태를 렌더링하고 의도를 전달하는 데 집중한다는 경계, 데이터 계층과 협력한다는 점, 구성 변경에도 같은 ViewModel이 유지된다는 점도 설명했습니다.

**빠진 부분**

“그 외에는 맡지 않는다”보다 경계를 구체적으로 말해야 합니다. ViewModel은 화면 단위 UI 상태와 UI 계층의 업무 로직을 담당하고, 데이터 변경은 repository나 use case에 위임합니다. 반대로 탐색, 애니메이션, `Snackbar` 표시처럼 UI 생명 주기와 직접 연결된 동작 및 `Activity`, `View`, 수명 주기가 짧은 `Context` 같은 객체를 보관해서는 안 됩니다. 구성 변경에는 살아남지만 프로세스 종료에는 살아남지 않으므로 필요한 최소 상태는 `SavedStateHandle`이나 영속 저장소로 복원해야 합니다.

**틀린 부분**

`ViewModelStore`가 별도의 “데이터”를 잡고 있는 것은 아닙니다. `ViewModelStoreOwner`에 연결된 store가 ViewModel **인스턴스 자체**를 유지하고 새 Activity가 같은 store의 인스턴스를 다시 얻는 구조입니다. ViewModel의 목적도 단순히 View의 Model 직접 접근을 막는 것보다는 화면 상태 보존, 관심사 분리와 단방향 데이터 흐름에 가깝습니다.

**면접에서는 이렇게**

“ViewModel은 화면 단위 상태 보유자입니다. repository나 use case에서 받은 데이터를 UI 상태로 변환해 노출하고, 사용자 이벤트 중 업무 로직이 필요한 부분을 처리하거나 다른 계층에 위임합니다. UI는 상태를 렌더링하고 UI 동작 로직을 맡습니다. ViewModel은 `ViewModelStoreOwner` 범위에서 구성 변경을 넘어 유지되지만 화면이 영구히 제거되면 정리되고, 프로세스 종료 복원은 별도 저장 수단이 필요합니다. 따라서 `Activity`나 `View`처럼 수명 주기에 묶인 객체를 보관하지 않습니다.”

**상태** 미학습 → 불안정 (3점)

## 6. [SEC-006] 대칭키 암호와 비대칭키 암호는 각각 언제 사용하며, 실제 보안 통신에서는 둘을 어떻게 함께 사용하나요? — 2점

**맞은 부분**

대칭키는 같은 비밀 키를 사용해 빠르고, 비대칭키는 공개키와 개인키를 사용해 키 배포와 서명에 유리하다는 큰 구분은 맞았습니다. 비대칭키 방식으로 통신 초기에 비밀을 안전하게 합의하고 실제 데이터는 빠른 대칭키 방식으로 보호한다는 하이브리드 구조도 파악했습니다. 지난 답변에서 빠졌던 서명과 혼합 사용을 이번에는 언급했습니다.

**빠진 부분**

대표 알고리즘과 각 역할을 분리해야 합니다. 대칭키 데이터 암호에는 AES-GCM이나 ChaCha20-Poly1305, 공개키 암호에는 RSA, 키 합의에는 ECDH/ECDHE, 서명에는 RSA-PSS·ECDSA·EdDSA 등이 쓰입니다. 현대 TLS에서는 보통 인증서의 공개키로 서버 서명을 검증하고 ECDHE로 공유 비밀을 합의한 뒤, 여기서 파생한 방향별 세션 키로 데이터를 암호화합니다.

**틀린 부분**

대칭키 설명 중 “N개의 비대칭 키”는 “상대마다 안전하게 공유할 대칭키”여야 합니다. 대칭키는 공개키·개인키로 된 키 쌍도 아닙니다. 또한 전자 서명은 개인키로 데이터를 암호화하고 공개키로 원문을 복호화하는 절차가 아니라, 메시지의 해시 등에 만든 **서명값을 공개키로 검증**하는 절차입니다. 하이브리드 통신 전체를 RSA 방식이라고 부르는 것도 부정확하며, 마지막에 “미리 교환한 비대칭 키”로 통신한다고 한 부분은 앞의 설명과 모순됩니다. 실제 데이터에는 합의·파생한 대칭 세션 키를 사용합니다.

**면접에서는 이렇게**

“대칭키 암호는 하나의 공유 비밀 키로 암복호화해 빠르므로 대량 데이터 보호에 적합하지만, 상대마다 키를 안전하게 공유·관리해야 합니다. 비대칭키 방식은 공개키와 개인키를 사용해 키 합의나 암호화, 전자 서명에 활용하지만 연산 비용이 큽니다. 그래서 TLS는 인증서와 서명으로 상대를 인증하고 ECDHE 같은 방식으로 공유 비밀을 합의한 뒤, 여기서 만든 대칭 세션 키와 AES-GCM 같은 알고리즘으로 실제 트래픽을 보호합니다. 서명은 암호문 복호화가 아니라 공개키를 이용한 서명값 검증입니다.”

**상태** 불안정 유지 (2점)

## 이번 세션에서 드러난 흐름

DI와 ViewModel은 사용 경험에서 나온 큰 방향은 잡혀 있지만, **컴포넌트가 무엇을 보유하는지, 누가 구현하고 누가 값을 제공하는지, 어느 수명 범위까지 유지되는지**를 정확한 주어로 설명하지 못해 2~3점에 머물렀습니다. Compose는 `Stable`·`Skippable`의 정의와 성능 측정 지표를 추측으로 연결한 것이 가장 큰 약점입니다. 보안은 지난번보다 하이브리드 구조와 서명까지 범위를 넓혔지만, 키 종류와 암호화·서명·키 합의의 동사를 섞어 써서 기초 문항 통과 수준에는 이르지 못했습니다.

우선순위는 Compose 두 문항의 개념 재학습, 보안 용어 교정, DI·ViewModel 답변의 수명 주기 문장 정리 순입니다.
