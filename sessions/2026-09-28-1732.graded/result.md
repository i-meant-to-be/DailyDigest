## 1. [AND-030] Android 런타임 권한 요청 흐름 — 1점

**맞은 부분**
거부 이후 `shouldShowRequestPermissionRationale`을 확인해야 한다는 API 이름은 기억했습니다.

**빠진 부분**
권한 기능 실행 전에 `ContextCompat.checkSelfPermission`으로 이미 허용됐는지 확인하는 단계, `ActivityResultContracts.RequestPermission`을 등록하고 결과를 처리하는 단계, 최초 요청과 영구 거부를 구분하기 위한 앱 자체 요청 이력이 모두 빠졌습니다. `shouldShowRequestPermissionRationale == true`는 재요청 가능 여부가 아니라 사용자가 이전에 거부했으므로 추가 설명을 보여 주는 편이 적절하다는 뜻입니다.

**틀린 부분**
일반적인 런타임 권한 요청은 `Intent`로 보내는 것이 아니라 권한 요청 계약을 실행합니다. 설정 화면은 단순히 재요청할 때 보내는 곳이 아니라, 이전 요청 이력이 있는데 rationale도 표시할 수 없어 시스템 대화상자로 다시 요청할 수 없는 상태 등을 판단해 안내하는 우회 경로입니다. 거부 횟수만으로 고정 판단해서도 안 됩니다.

**면접에서는 이렇게**
"먼저 `checkSelfPermission`으로 허용 여부를 확인합니다. 거부 상태라면 rationale이 필요할 때 기능 필요성을 설명한 뒤 Activity Result API의 `RequestPermission`을 실행합니다. rationale이 false인 경우에는 최초 요청일 수도 있고 다시 묻지 않음 상태일 수도 있으므로 앱이 이전에 요청했는지 별도로 기록해 구분합니다. 이전 요청 이력이 있고 시스템 요청을 다시 띄울 수 없다면 설정 화면 이동을 안내하며, 거부 시에는 기능을 안전하게 축소합니다."

**상태** 오답 유지 (1점)

## 2. [SEC-004] OAuth 2.0 인가 코드 흐름과 PKCE — 2점

**맞은 부분**
요청마다 무작위 `code_verifier`를 만들고 S256으로 `code_challenge`를 생성한다는 점, 탈취자가 인가 코드를 얻어도 verifier가 없어 토큰으로 교환하지 못한다는 방어 원리는 설명했습니다. 이전 답보다 핵심 이해가 분명히 좋아졌습니다.

**빠진 부분**
인가 요청에는 `code_challenge_method=S256`도 포함하고, 인증·동의가 끝나면 인가 서버가 리다이렉트 URI로 **인가 코드**를 반환합니다. 이후 공개 클라이언트는 그 인가 코드와 `code_verifier`를 토큰 엔드포인트에 보내고, 서버가 challenge와 대조한 뒤 토큰을 발급합니다. 질문의 공개 클라이언트 표준 흐름과 별도의 서비스 서버가 자체 세션 토큰을 만드는 구조를 구분해야 합니다.

**틀린 부분**
PKCE는 발급되어 앱으로 돌아오는 값이 아니라 인가 코드 흐름을 보호하는 확장 절차입니다. 답변의 4~7단계에서 인가 코드를 계속 "PKCE"라고 부른 것이 핵심 용어 오류입니다. 또한 모바일 공개 클라이언트 흐름을 묻는 질문에 서비스 서버가 반드시 토큰 교환을 대신하는 것으로 고정해 설명했습니다.

**면접에서는 이렇게**
"앱은 요청마다 높은 엔트로피의 verifier를 만들고, 이를 SHA-256과 Base64 URL 인코딩으로 변환한 challenge를 인가 요청에 보냅니다. 사용자가 인증과 동의를 마치면 앱은 리다이렉트 URI로 인가 코드를 받습니다. 앱이 인가 코드와 원본 verifier를 토큰 엔드포인트에 보내면 서버가 verifier에서 계산한 값과 저장된 challenge를 비교한 뒤 토큰을 발급합니다. 따라서 코드를 가로챈 공격자는 verifier가 없어 교환할 수 있고, 앱 바이너리에 고정 비밀을 넣을 필요도 없습니다."

**상태** 오답 → 불안정 (2점)

## 3. [DI-006] 멀티 모듈의 Hilt 모듈 배치 — 2점

**맞은 부분**
바인딩 함수가 인터페이스와 구현체 타입을 볼 수 있어야 하며, `Application`을 컴파일하는 모듈에서 전체 그래프가 모여야 한다는 방향은 잡았습니다.

**빠진 부분**
Gradle 모듈에서의 파일 위치와 `@InstallIn`으로 정하는 Hilt 컴포넌트 범위를 분리해 설명해야 합니다. 보통 바인딩은 구현의 소유 모듈 가까이에 두어 응집도를 유지하고, 앱 모듈은 그 모듈을 전이 의존성으로 포함합니다. 앱 모듈이 모든 Hilt 모듈과 생성자 주입 타입을 전이적으로 볼 수 있어야 하며, 동적 기능 모듈처럼 의존성 방향이 반대인 경우에는 Hilt가 직접 처리하지 못해 EntryPoint와 Dagger 컴포넌트 의존성을 사용합니다.

**틀린 부분**
Hilt가 필요에 따라 구현체를 임의로 바꾸기 때문에 모든 소스에 접근해야 한다는 설명은 정확하지 않습니다. 어떤 구현을 사용할지는 개발자가 작성한 바인딩이 정하고, Hilt는 클래스 경로에서 그 바인딩을 모아 그래프를 생성합니다. 이를 이유로 모든 모듈을 앱이나 루트에 몰아둘 필요는 없습니다.

**면접에서는 이렇게**
"Hilt 모듈은 바인딩이 속한 구현 모듈 가까이에 두되, 그 모듈이 인터페이스와 구현 타입을 모두 볼 수 있어야 합니다. `@InstallIn`은 파일 위치가 아니라 바인딩이 들어갈 컴포넌트와 수명을 정합니다. 최종적으로 `Application`을 컴파일하는 앱 모듈의 전이 의존성에 모든 Hilt 모듈과 생성자 주입 타입이 포함되어야 합니다. 동적 기능 모듈은 의존성 방향이 반대라 EntryPoint와 Dagger 컴포넌트 의존성이 별도로 필요합니다."

**상태** 미학습 → 불안정 (2점)

## 4. [DI-011] Hilt 없이 Dagger 사용 — 1점

**맞은 부분**
Hilt가 Dagger를 Android에 맞게 표준화한 도구이며, 순수 Dagger에서는 Android 생명주기와 그래프 연결을 개발자가 직접 구성해야 한다는 큰 방향은 맞았습니다.

**빠진 부분**
순수 Dagger에서는 `@Component`·`@Subcomponent`와 팩터리, 모듈 목록, 컴포넌트 보관 위치와 부모·자식 관계를 직접 선언하고 Android 구성요소에서 생성한 컴포넌트의 `inject`를 호출해야 합니다. Hilt는 `@HiltAndroidApp`, `@AndroidEntryPoint`, `@InstallIn`을 기반으로 표준 컴포넌트 계층과 생성·주입 코드를 만들어 줍니다. Dagger만 선택할 근거로는 비표준 컴포넌트 계층을 정밀하게 통제해야 하는 기존 코드, Android 밖에서도 공유하는 라이브러리, Hilt가 직접 처리하지 못하는 동적 기능 모듈 같은 조건이 필요합니다.

**틀린 부분**
컴파일 시점 그래프 검증은 Hilt만의 기능이 아니라 기반인 Dagger도 제공합니다. Hilt가 무겁기 때문에 작은 프로젝트에서는 Dagger가 낫다는 결론도 근거가 부족합니다. 작은 프로젝트라면 수동 주입이 더 단순할 수 있고, Dagger를 도입한다면 오히려 Hilt가 반복 설정을 줄이는 경우가 많습니다.

**면접에서는 이렇게**
"Dagger만 쓰면 컴포넌트 계층, 스코프, 생성 시점과 보관 위치, Android 구성요소의 주입 호출을 직접 설계합니다. Hilt는 이를 정해진 Android 컴포넌트 계층과 어노테이션으로 표준화해 반복 코드를 줄이고 테스트 교체도 지원합니다. 둘 다 컴파일 시점에 그래프를 검증합니다. 비표준 그래프 제어가 꼭 필요하거나 기존 Dagger 구조를 유지해야 할 때는 Dagger만 쓸 수 있지만, 일반적인 Android 앱은 Hilt가 기본 선택입니다."

**상태** 미학습 → 오답 (1점)

## 5. [CMP-005] `collectAsStateWithLifecycle` — 2점

**맞은 부분**
`StateFlow` 자체는 Android 생명주기를 모르므로 Compose에서 생명주기를 고려해 수집해야 한다는 핵심 이유는 맞았습니다.

**빠진 부분**
기본 최소 활성 상태는 `STARTED`입니다. 생명주기가 그 이상이면 수집하고, 아래로 내려가면 수집을 중단하며, 다시 `STARTED` 이상이 되면 재개합니다. 반환된 Compose `State`가 갱신될 때 이를 읽는 UI가 재구성되고, 비활성 화면에서 불필요한 수집과 작업을 줄이는 것이 목적입니다.

**틀린 부분**
Compose의 `State`가 Android 생명주기에 맞게 설계되어 자동으로 수집을 관리한다는 설명은 맞지 않습니다. `State`는 값 변경을 Compose에 알려 재구성을 유도하는 상태 보관 형식이지, 임의의 흐름 수집을 생명주기에 따라 중단하는 장치가 아닙니다. 또한 수집은 화면 파괴 시에만 해제되는 것이 아니라 기본적으로 `STARTED` 아래에서 중단됩니다.

**면접에서는 이렇게**
"`StateFlow`는 Android 생명주기를 모르기 때문에 단순 수집하면 화면이 보이지 않는 동안에도 수집 작업이 계속될 수 있습니다. `collectAsStateWithLifecycle`은 값을 Compose `State`로 바꾸면서 기본적으로 생명주기가 `STARTED` 이상일 때만 수집하고, 아래로 내려가면 중단했다가 다시 활성화되면 재개합니다. 그래서 UI 재구성과 생명주기 안전성을 함께 얻습니다."

**상태** 미점검 → 불안정 (2점)

## 6. [JK-003] `val`과 `var` — 2점

**맞은 부분**
일반적인 저장형 `val`은 재할당할 수 없지만 참조한 가변 객체의 내부는 바뀔 수 있다는 점을 이전보다 정확히 설명했습니다. `var`가 재할당 가능한 프로퍼티라는 방향도 맞습니다.

**빠진 부분**
접근자 관점에서 `val`은 getter만 있고 setter가 없는 읽기 전용 프로퍼티이며, `var`는 getter와 setter를 가집니다. 커스텀 getter는 단순히 메서드 호출 문법을 프로퍼티 문법으로 바꾸는 데 그치지 않고 접근할 때마다 값을 계산할 수 있으며 backing field가 없을 수도 있습니다. `const val`은 컴파일 시점 상수로서 최상위 또는 `object`·companion object에 두고 원시 타입이나 `String`의 상수식으로 초기화하며 호출 지점에 인라인됩니다.

**틀린 부분**
`val`은 선언 즉시 초기화만 가능한 것이 아니며 생성자나 초기화 블록에서 초기화하거나 커스텀 getter로 값을 제공할 수도 있습니다. `lateinit`은 `val`에 붙일 수 없고 조건을 만족하는 `var`에만 사용할 수 있습니다. 또한 `val list: List<T>`에는 `add`가 없으므로 내부 변경 가능 여부는 실제 객체뿐 아니라 노출된 정적 타입이 `MutableList`인지도 구분해야 합니다.

**면접에서는 이렇게**
"`val`은 getter만 있는 읽기 전용 프로퍼티이고 `var`는 getter와 setter가 있는 변경 가능한 프로퍼티입니다. 저장형 `val`은 재할당할 수 없지만 `MutableList` 같은 가변 객체를 참조하면 객체 내부는 바뀔 수 있습니다. 커스텀 getter를 가진 `val`은 접근할 때마다 계산되어 같은 값을 보장하지 않을 수도 있습니다. `const val`은 컴파일 시점에 값이 확정되는 최상위 또는 object의 원시 타입·String 상수이며, `lateinit`은 `var`에만 쓸 수 있습니다."

**상태** 불안정 유지 (2점)
