## 2. [SEC-004] 모바일 공개 클라이언트의 OAuth 2.0 인가 코드 흐름을 PKCE와 함께 단계별로 설명해 주세요. `code_verifier`와 `code_challenge`가 코드 가로채기를 어떻게 막는지도 포함해 주세요

`platform/security` · 실무 · 이전 오답(2026-09-18) · 지난 지적: PKCE를 API 키 검증으로 잘못 설명했고, verifier·challenge의 생성과 검증 및 앱에 고정 비밀을 둘 수 없는 이유를 설명하지 못함

### 내 답변

관계자는 앱, 서비스 서버, OAuth 인증 제공자로 구분.

1. 앱은 로그인 요청을 받으면 무작위 문자열 `code_verifier` 생성 후 이를 S256 방식으로 해싱하여 `code_challange`를 생성
2. 앱은 `code_challange`와 리다이렉트 URI를 인증 제공자에 전송하고 로그인 화면을 열어줌
3. 사용자는 로그인
4. 인증 제공자는 로그인 성공 시 PKCE를 발급하여 앱에 전달
5. 앱은 받은 PKCE와 `code_verifier`를 서비스 서버에 전달하며 서비스 로그인을 위한 토큰 발급을 요청
6. 서비스 서버는 `code_verifier`와 PKCE를 인증 제공자에게 보내 검증 요청
7. 인증 제공자는 `code_verifier`를 S256으로 해싱한 결과가 2번에서 받은 `code_challange`와 동일한지 확인하고 동일한 경우 토큰(액세스, 리프레시)을 발급해 서비스 서버에 전달 (이 때 오직 로그인 기능만 사용할 경우 OAuth 인증 제공자 측 액세스/리프레시 토큰은 사용하지 않고 버릴 수 있음)
8. 서비스 서버는 토큰이 발급된 것을 확인한 후, 서비스 로그인을 위한 액세스/리프레시 토큰을 발급하여 앱에 전달
9. 앱은 보안이 확보된 저장소에 토큰 저장 후 로그인 성공 시나리오 처리

`code_verifier`와 `code_challenge`는 PKCE 발급 요청과 그걸 검증하는 요청을 발행한 주체가 동일인임을 확인하는 장치로서, 공격자가 리다이렉트 URI 공격 등으로 PKCE를 가로채는 경우를 막아줌. 공격자는 OAuth 앱 리다이렉트 URI를 정상 앱의 것과 동일하게 설정하여 리다이렉트 요청을 가로채 PKCE를 뺏을 수 있는데, 탈취에 성공해도 공격자는 `code_challange`의 원본이 되는 `code_verifier`를 모르기 때문에 2번 과정에서 정상 앱이 보낸 원본을 검증 요청 시 보낼 수 없기 때문.

## 4. [신규] Android 프로젝트에서 Hilt 없이 Dagger만 사용한다면 의존성 그래프의 선언과 Android 구성요소 주입 방식이 어떻게 달라지나요? 각각의 장단점과 Dagger만 선택할 만한 경우도 설명해 주세요

`platform/di` · 실무 · 주제 대장 공백 — 지식 파일에 아직 없는 주제

### 내 답변

Dagger는 의존성 주입 그 자체를 담당하는 라이브러리이고 Hilt는 Dagger를 Android에 맞게 쓸 수 있도록 다듬어 둔 라이브러리라서, Dagger만 사용할 경우 생명주기 등 Android에 관한 내용을 직접 설정해줘야 함. 따라서 Dagger를 쓸 경우 의존성 주입 및 생명주기 관리를 개발자가 직접 해야 한다는 단점은 있지만, 대신 무거운 Hilt를 사용할 필요가 없음. Hilt는 의존성 그래프를 빌드 시간에 검사해주고 Android 생명주기에 맞는 여러 어노테이션 등 다양한 기능을 제공하지만 무거운 편.

그렇기 때문에 프로젝트 규모가 작아 의존성을 관리해야 할 부담이 적다면 Dagger를 가볍게 사용해보는 것도 고려할 수 있음.

## 5. [CMP-005] Compose에서 `StateFlow`를 단순히 수집하지 않고 `collectAsStateWithLifecycle`로 수집하는 이유와, 화면의 생명주기 상태가 바뀔 때 동작을 설명해 주세요

### 내 답변

## 6. [JK-003] Kotlin의 `val`과 `var`를 프로퍼티 접근자 관점에서 비교해 주세요. `val`이 참조하는 가변 객체, 커스텀 getter, `const val`과의 차이도 함께 설명해 주세요

`lang/java-kotlin` · 기초 · 숙지 상태 재점검 슬롯을 이전에 불완전하게 답한 문항으로 채움(2026-09-04) · 지난 지적: 읽기 전용 참조와 객체 내부 변경을 혼동했고, 커스텀 getter 및 `const val`과의 차이를 설명하지 못함

### 내 답변

`val`은 최초 할당 후 값 변경이 불가능하고 선언과 즉시 초기화가 강제됨. `var`은 최초 할당 후에도 값 변경이 가능. 단, `val`에 `lateinit`이 붙을 경우 지연 초기화는 가능함.

단, `val`로 설정한 변수에서 바꿀 수 없는 것은 해당 별칭(alias)에 대응하는 참조일 뿐이지, 해당 참조가 가리키는 객체의 세부 값은 변경될 수 있음을 인지해야 함. 예를 들어 리스트를 `val`로 설정할 경우, 다른 참조를 가진 리스트로 대체할 순 없지만, 원본 리스트에 값을 추가하거나 삭제하는 연산은 가능함.

또한, 커스텀 `get` 함수를 설정하게 되면 특정 연산식을 함수가 아니라 변수로서 다룰 수 있게 됨. 예를 들어 `user.getName()` 대신 `user.name`으로 값을 받을 수 있게 됨.

`const val`은 상수와 같이 사용되는 값에 적용하며 지연 초기화는 불가능하여 선언과 즉시 초기화를 해야 함.
